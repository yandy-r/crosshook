## Fixture and app contract

Fixture generation command:

```sh
cargo run --manifest-path src/crosshook-native/Cargo.toml -p crosshook-core --example bench_fixtures -- --seed 42 --out DIR [--empty]
```

Materialize canonical fixtures into an isolated launcher root with:

```sh
-- materialize --from canonical --root isolated
```

Canonical tree includes `DIR/config/crosshook/profiles` and settings, `DIR/data/crosshook/metadata.db`, cache/images portraits, `DIR/logs/launch-50k.log`, and a manifest. Portable paths use `@CROSSHOOK_BENCH_ROOT@`. Same-seed canonical contents must compare equal; materialized paths intentionally depend on root. Seeded timestamps/UUIDs are normalized through public SQL API in the example; production schema and user data remain unchanged. Cover fixture is one generated 600×900 JPEG copied 500 times (identical-pixel limitation).

Fixtures and test state are runtime-only artifacts in isolated roots. No TOML user settings or SQLite user metadata changes are permitted. No real game/trainer launch. Production behavior is untouched unless `CROSSHOOK_BENCH=1`; when unset, benchmark instrumentation does one no-op IPC call.

For readiness, app prints `READY <CLOCK_MONOTONIC ns>` after summary fetch and double `requestAnimationFrame`, including empty state. This does not promise cover decode/scan completion. `CROSSHOOK_BENCH_EXIT_AFTER_READY=1` exits through `AppHandle.exit`. Log replay uses `CROSSHOOK_BENCH_ROOT` and `CROSSHOOK_BENCH_LOG=ROOT/logs/...`, at no more than 5,000 lines/s; it never launches a real workload. Console drawer must be open to measure log rendering.

### Window presentation requirement

`READY` fires after a double `requestAnimationFrame`, and WebKitGTK only runs animation frames and paints while the compositor presents the window. A locked session, a display that is off or a minimized window leaves the webview blank and `READY` never arrives, even though the backend finishes bootstrap. This was the root cause of YAN-1985 on E1: the "blank webview under an isolated HOME" happened while the KDE session was locked, and HOME/XDG isolation and the NVIDIA driver played no part. Forcing the window minimized reproduces `READY_TIMEOUT` with empty stderr every time.

Before each launched capture (G1/G2/G3/G7/G8) the runner checks the session with logind `LockedHint` (`loginctl show-session auto`) and `org.freedesktop.ScreenSaver.GetActive`, and fails with `SESSION_LOCKED` instead of launching. If either probe reports a lock, the session counts as locked; with no probe available (no logind session or no screensaver service), the check is skipped. After a timeout the runner checks again and reports `SESSION_LOCKED` when the session locked mid-run; otherwise `READY_TIMEOUT` names the presentation requirement. G3 and G7 also check the lock before every sample and stop with `SESSION_LOCKED` instead of recording frozen samples; a G7 failure also stops its `perf` wakeup count at once. The probes never start anything: the ScreenSaver call needs an existing session bus (`DBUS_SESSION_BUS_ADDRESS` or `$XDG_RUNTIME_DIR/bus`, so `gdbus` cannot autolaunch a `dbus-daemon`) and a service that already owns the name (no bus activation). `loginctl show-session auto` resolves to the caller's session, and its `LockedHint` only counts when that session is graphical (`Type` `wayland` or `x11`). From ssh or a TTY the logind probe is unknown, so run the runner from a terminal inside the graphical session. A display that is off without a lock, or a window minimized by the user, cannot be probed and still ends in `READY_TIMEOUT`. Keep the session unlocked, the display on and the window visible for the whole capture, and turn off automatic screen locking and display power-off for long G3/G7 runs.

### Isolation requirements

All four XDG roots (`HOME` plus `XDG_CONFIG_HOME`, `XDG_DATA_HOME`, `XDG_CACHE_HOME`, and `XDG_RUNTIME_DIR`) must resolve inside the isolated fixture root; host-XDG overrides (`HOST_XDG_*`) stay disabled. Refuse real CrossHook data paths, symlink escapes, and custom `profiles_directory` roots (read from the real `settings.toml`). Preserve existing runtime/Wayland/DBus sockets. Never use `sudo`, drop host caches automatically, or start a real game/trainer. Guards run before any filesystem mutation; refusal prints `BENCH_REFUSE: …` and exits 10. Presentation G4/G9 also refuse with `INSTANCE_RUNNING` when `dev.crosshook.CrossHook` already owns the session bus (the bench window would hand off to that instance and receive the injected input), and with `INSTANCE_UNKNOWN` when the session bus cannot be asked. The check runs again immediately before every launch, so an instance started mid-run also exits 10.

For Flatpak, per-app data derives from the **launcher** `HOME` (`flatpak-context.c` / `flatpak_get_data_dir`); sandbox `--env=HOME=...` alone does not isolate the per-app data path. The runner launches with launcher `HOME=<root>/home`, `--nofilesystem=host:reset`, `--filesystem=<root>`, `--env=CROSSHOOK_FLATPAK_HOST_XDG=0`, and materializes fixture data under `<root>/home/.var/app/dev.crosshook.CrossHook`. It requires a fresh owned `crosshook-bench-*` launcher root. Isolation protects against host per-app data access; still inspect resolved paths before execution.

the key is released and the run fails), `RESIZE_NOT_OBSERVED`, `REPLAY_NOT_SETTLED`, `APP_EXIT` (the app exited while it was being driven), `UNKNOWN_SCENARIO`, `BENCH_ENV_INCOMPLETE` (the isolated root or config home is not in the launch environment), `SETTINGS_UNSAFE` (a leftover `settings.toml` in the isolated config home is not a regular file, or its real location is not inside the `crosshook-bench-*` root that holds `CROSSHOOK_BENCH_ROOT`; presentation runs add `run_id`, `collector` and `raw_dir`. Baselines use commit SHA, never a tag.

G1/G2/G3/G7/G8 (and G4/G9 with `--collect presentation`) launch the app inside isolated root; otherwise G4/G5/G6/G9 ingest observations and G10 measures inputs without launching app. G8 additionally requires fixtures and a `frame_ms` CSV; runner launches app with `CROSSHOOK_BENCH_LOG=<root>/logs/launch-50k.log` and `CROSSHOOK_BENCH_LOG_RATE=5000`, samples app process-tree memory for 11 seconds, and computes frame stats from input CSV. This replay measurement is implemented for Flatpak and native through common environment; visual frame-time production remains external.

Cold G1 requires explicit page-cache preparation before each iteration; `--cold-cache-ack` only acknowledges preparation — runner does not drop caches. On a dedicated, controlled benchmark host, an authorized operator may use:

```sh
sync && echo 3 | sudo tee /proc/sys/vm/drop_caches >/dev/null
```

**Security / system-impact warning:** this requires privileged access and drops page cache, dentries, and inodes system-wide. It affects all processes and other users, may cause significant I/O/performance impact, and is unsafe on shared or production hosts. Never automate it in the runner. Record host, operator, command, and timestamp. A warm-cache run is G2, never G1. Dry-run is available for all ten metrics and writes `status=dry-run` rows; dry-run CSVs are schema fixtures, not data.

## Presentation collector

`--collect presentation` measures when the compositor actually presented the app's frames. Wayland only gives presentation feedback to the client that owns a surface, so the runner preloads a bench-only shim into the app:

- **Source**: [`scripts/bench/presentation/wlpresent.c`](../../../scripts/bench/presentation/wlpresent.c), `wlfocus.c` (keyboard, pointer and configure tracking) and the shared header `wlpresent.h`, plus the vendored stable `presentation-time.xml` (MIT). It is never part of a release, the Flatpak manifest or any packaging script.
- **Build**: per run, into `<isolated root>/bench-tools/` by [`bench_shim.py`](../../../scripts/bench/bench_shim.py): host `cc` and `wayland-scanner` for native runs, `org.gnome.Sdk//50` for `--flatpak` (the runtime's glibc and libwayland differ from the host's). The `.so` and source hashes go into the provenance manifest. The shim needs libwayland-client >= 1.24 (`wl_proxy_get_interface`; Ubuntu 24.04 ships 1.22), checked with `pkg-config --atleast-version=1.24 wayland-client` on the host and inside the SDK. Missing tools fail with `MISSING_TOOL: cc|wayland-scanner|pkg-config|org.gnome.Sdk//50|libwayland-client >= 1.24`; `python3 scripts/bench/bench_shim.py --check` is the CI compile check.
- **Arming**: inert unless `CROSSHOOK_BENCH=1` and `CROSSHOOK_BENCH_PRESENT_DIR` is an absolute path. The runner scrubs inherited loader, debug and module variables (`LD_PRELOAD`, `LD_LIBRARY_PATH`, `LD_AUDIT`, `LD_DEBUG`, `LD_DEBUG_OUTPUT`, `LD_PROFILE`, `LD_PROFILE_OUTPUT`, `GLIBC_TUNABLES`, `WAYLAND_DEBUG`, `GTK_MODULES`, `GTK3_MODULES`, `GIO_EXTRA_MODULES`, `GST_PLUGIN_PATH`) and sets only its own `LD_PRELOAD` (forwarded through `flatpak run --env`). The shim starts no thread at load, so the app's single-thread startup check is unaffected; it initialises on the first `wl_surface.commit`. A process forked after init gets a pass-through shim (`pthread_atfork` disarms it and closes its log descriptor).
- **Known perturbation**: the shim runs on the app's render thread. Every commit costs one `write(2)` and every presented or discarded event costs another, a few microseconds each, plus a feedback object on the private queue. Initialisation does one blocking roundtrip on the private queue (registry bind and `clock_id`) inside the first commit. Both are inside the measured window, so compare presentation captures only with other captures taken with the same shim. The log stops after 500,000 records (`X log_cap`), which keeps it below the parser's 64 MiB limit.
- **What it does**: on every `wl_surface.commit` it first sends `wp_presentation.feedback` on a private event queue, then forwards the commit, and logs the compositor's answer. Timestamps are CLOCK_MONOTONIC, the same clock as `READY` and the runner; any other `clock_id` fails with `PRESENTATION_CLOCK`. A compositor without `wp_presentation` fails with `NO_PRESENTATION_GLOBAL` (the shim then writes `clock_id=-1` plus an `X no_presentation_global` record, and the parser checks that first).
- **Log format `wlpresent v1`** (`present/**/wlpresent-<pid>.log`, mode 0600, tab-separated): `H` header (pid, comm, `clock_id`, protocol version, app env snapshot); `S` surface role (`toplevel`, or `destroyed` when a toplevel `wl_surface` is destroyed, because the server may reuse its id); `C` commit (`commit_ns surface_id feedback_seq has_buffer`); `P` presented (`recv_ns feedback_seq presented_ns refresh_ns msc flags`); `D` discarded; `X` condition (`no_presentation_global`, `bind_failed`, `wrap_failed`, `log_cap`); `K` keyboard focus (`ns enter|leave surface_id`) and `M` pointer focus (same fields), from the `wl_keyboard`/`wl_pointer` enter and leave events; `G` toplevel configure geometry (`ns surface_id width height activated`), from `xdg_toplevel.configure`. The `K`/`M`/`G` records are the evidence the G4/G9 drivers act on (see [G4/G9 input drivers](#g4g9-input-drivers)). [`bench_present.py`](../../../scripts/bench/bench_present.py) parses it; roles are applied in log order, so a commit counts as a frame only if the latest `S` record for its surface before it says `toplevel` and it attached a buffer.
- **Refresh check**: whenever at least one presented toplevel frame exists, the median `refresh_ns` the compositor reports must be within 0.5 % of `--refresh-hz`, otherwise `REFRESH_MISMATCH` (exit 40); a compositor that reports no refresh period skips the check. Pass the mode you actually use (E1 runs at 180.06 Hz unless switched to 119.88 Hz).
- **G1/G2**: `--collect presentation` does not set `CROSSHOOK_BENCH_EXIT_AFTER_READY`; after `READY` the runner waits up to 2 s for a presented toplevel frame, then stops the app. Each row adds `first_present_ms` (launch to the first presented toplevel frame; this may be the window background before content), and the summary row adds `first_present_p50_ms`/`first_present_p95_ms`.
- **Raw run directory**: every presentation run writes `<output>/raw/<run_id>/` (0700, files 0600) with the shim logs, the metric CSVs, `meta.json`, `provenance.json` (schema `crosshook-bench-provenance/1`: run id, commit and dirty flag, variant, environment, boot id, fixture seed, binary sha256, shim hashes, status) and `SHA256SUMS`. It is written even when the capture fails. The `--binary` sha256 is taken before launch and re-checked before sealing. `provenance.json` itself must be listed and checksummed in `SHA256SUMS`, or `verify_capture` refuses with `STALE_CAPTURE`. `--capture-csv` only accepts a CSV listed in such a directory whose checksums, commit, variant, environment and boot id match the current run (`STALE_CAPTURE` otherwise). `verify_capture` also requires the run `status` to be `captured`, the working tree to have been clean (`dirty` false) and a known boot id; a failed run, a dirty tree or an unavailable boot id is `STALE_CAPTURE`. A run directory is never reused (`RAW_DIR_EXISTS`, `RAW_DIR_SYMLINK`), and each iteration gets a fresh present directory (`PRESENT_DIR_EXISTS`).
- **Flatpak user installs**: the isolated launcher `HOME` would hide a `--user` installation, so the runner sets `FLATPAK_USER_DIR` to the real per-user installation, but only when it is a real directory (not a symlink) owned by the current user. Only the installation is shared; per-app data still derives from the isolated `HOME`.
- **Flatpak overrides**: `--flatpak` runs record the SHA-256 of `overrides/global` and `overrides/dev.crosshook.CrossHook` from that installation (regular files only; absent ones are omitted) as `flatpak_overrides` in `meta.json` and `provenance.json`, because an override changes the sandbox the numbers were measured in.

Validated on E1 (2026-11-16): native G2 (5 iterations) `first_present_ms` p50 about 220 ms against `ready_ms` p50 about 1015 ms; Flatpak G2 loads the SDK-built shim inside the sandbox. G5/G8 presentation producers need frontend markers (YAN-1007 Phase 3) and keep refusing `--collect presentation`.

### G4/G9 input drivers

`--collect presentation --metric G4|G9` launches the isolated app once per scenario and iteration, drives it, and computes frame intervals only from the shim's presented timestamps, windowed by the runner's own input stamps. It needs KDE Plasma (KWin) on the session bus, `gdbus`, and a user-writable `/dev/uinput`; it never uses `sudo`. Quit CrossHook first (`INSTANCE_RUNNING`, or `INSTANCE_UNKNOWN` when the bus cannot say), keep the session unlocked, and do not touch the keyboard or mouse after `BENCH_NOTICE` appears.

- **uinput access**: without write access to `/dev/uinput` the runner fails with `INPUT_DEVICE_DENIED` and points here. Grant your user an ACL temporarily with `sudo setfacl -m u:$USER:rw /dev/uinput` (lost on reboot or when the node is recreated), or persistently with a udev rule such as `KERNEL=="uinput", SUBSYSTEM=="misc", TAG+="uaccess"` in `/etc/udev/rules.d/70-uinput.rules`, then `sudo udevadm control --reload && sudo udevadm trigger /dev/uinput`. The runner itself never calls `sudo`. Only G4 opens the device; G9 resizes through KWin.
- **Input**: a private uinput device (`crosshook-bench`) advertises only the wheel, Ctrl, K, Enter and the letters of `settings` (the Ctrl+K palette chord); every key down is paired with its up, and closing the device (also on abort) releases everything. A key is recorded as held before its down is written, and a write the kernel cuts short fails with `INPUT_WRITE_SHORT`, so a down that may have reached the device is always released. `bench_capture.stop()` holds SIGTERM, SIGHUP and SIGINT while it tears the app's process group down and delivers the first one afterwards, so a second signal during an abort cannot orphan the app.
- **Window control**: KWin's D-Bus window list (`/WindowsRunner` `Match`, `/KWin` `getWindowInfo`) finds exactly one window whose host pid is in the app's process tree. One-shot KWin scripts (int-only JS, written 0600 into the 0700 `bench-tools` dir, always unloaded and then deleted) place it at 1280×900 logical under the current cursor and activate it; the placement is verified through `getWindowInfo`. G9's per-step resizes are not (a `getWindowInfo` round trip would not fit in 33 ms): the shim's `G` configure records are their witness (`RESIZE_NOT_OBSERVED`). Scripts share one pid-filter preamble and are written inside the cleanup scope, and a failed unlink never masks the error that is propagating.
- **Focus witness**: the shim also logs keyboard (`K`) and pointer (`M`) enter/leave and toplevel configure geometry (`G`). The witness runs before every injected event: before each key the driver checks that the app is alive and that the keyboard enter on the bench toplevel is current, and before each timed notch that the pointer enter is current (`FOCUS_LOST` otherwise, so at most one event is sent after focus is lost). The driver reads those records incrementally (only the lines the shim appended since the last read), so the pointer check before each timed notch is cheap enough for the 33 ms scroll cadence (the key checks run between keys and have no cadence). The witness is only as good as the log: any `X` record that ends the shim's evidence (`log_cap`, `bind_failed`, `wrap_failed`, `no_presentation_global`) stops the run with `PRESENT_LOG_INCOMPLETE: <reason>`, and during the timed scroll a log that has not grown for 2 s fails with `FOCUS_LOST: presentation log stopped growing`, because a scroll commits frames (the idle waits before the scroll are not watched). The session-lock probe spawns processes, so it runs at most every 300 ms (and before the priming notch). KWin sends the pointer enter only on the first wheel event, so one untimed priming notch precedes the timed scroll; the wheel device sends exactly one notch per call.
- **Arm step**: that notch goes to whatever is under the cursor, so before it a one-shot KWin script finds the window by pid and sets `keepAbove = true` only if it is the active window, not minimized, and `workspace.cursorPos` lies inside its `frameGeometry` (otherwise `keepAbove = false`). The driver polls `getWindowInfo` for `keepAbove` for 1 s; if it never reads true it raises `POINTER_NOT_OVER_WINDOW: the bench window is not active under the cursor` and sends no notch. `keepAbove` also stops other windows from covering the bench window for the rest of the run.
- **G4**: `library` scrolls the start page; `settings` first opens the palette (Ctrl+K, `settings`, Enter); `console` writes an isolated `settings.toml` with the drawer expanded (the other scenarios delete any such file first, and the collector removes it again when the metric finishes, even on failure, and before G9, so it never leaks into later scenarios or metrics; the file is only ever written or deleted when its resolved path lies inside the `crosshook-bench-*` root that holds `CROSSHOOK_BENCH_ROOT`, otherwise `SETTINGS_UNSAFE`), replays the 50k-line fixture log (so it needs `--fixtures`: `FIXTURES_REQUIRED` before any launch), and waits until the app stops presenting (`REPLAY_NOT_SETTLED` after 25 s). The timed scroll is 180 notches at 33 ms, alternating 10 down and 10 up so short pages never reach their end and go idle. Rows: one per scenario, pooled over iterations.
- **G9**: KWin resize steps for 5 s of wall time, paced at a target of 30 steps/s (about 150 when KWin keeps up), between 1120×780 and 1400×880 logical (inside one layout breakpoint class); at least 10 distinct configured sizes are required (`RESIZE_NOT_OBSERVED`). Each step is a KWin script round trip, so a slow KWin achieves fewer steps rather than a longer run; the frame window runs from the first step to the last step plus a 300 ms tail. The achieved step count and driven duration are recorded per iteration in `provenance.json` under `drive_stats` (`{metric: {scenario: [{iteration, injected, driven_s}]}}`, `injected` being notches for G4 and steps for G9), since the CSV schema has no column for them.

Validated on E1 (2026-11-16, 180.06 Hz) as baseline B evidence, not a gate:

| Run        | Iterations | p50 / p95 ms per scenario                                |
| ---------- | ---------- | -------------------------------------------------------- |
| Native G4  | 2          | library 211 / 418, console 125 / 403, settings 117 / 344 |
| Native G9  | 2          | resize 33 / 39                                           |
| Flatpak G4 | 4          | library 139 / 494, console 128 / 446, settings 594 / 755 |
| Flatpak G9 | 2          | resize 33 / 39                                           |

Scrolling presents at roughly 2–9 fps on E1, so one iteration of about 6 s of timed scrolling yields only 12–54 frame intervals. That is why `CAPTURE_TOO_SHORT` requires 30 pooled intervals per scenario instead of a count that suits a 120 Hz cadence: use at least 2 native or 4 Flatpak iterations to clear it. Each iteration must also yield at least 5 intervals on its own (`CAPTURE_TOO_SHORT: <scenario> iteration <n>: <k> frame intervals, need 5`), so a pooled count cannot hide an iteration that barely presented. The discard check (`DISCARD_RATE`) counts only presentations committed inside the timed window.

## External capture CSV schemas

Real G4/G5/G6/G8/G9 ingest raw observations from `--capture-csv` (one CSV per run; select only metrics whose required columns that CSV carries). Header must match; values must be finite and non-negative.

| Metric | Required columns                  | Notes                                                                                                                                                                                                                                           |
| ------ | --------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| G4     | `frame_ms`                        | Adds `over_interval_percent`: share of intervals over 1.5 refresh periods (`1.5 × 1000/--refresh-hz`), i.e. a missed vblank. Presented intervals land on whole refresh periods, so a one-period threshold would count every frame at 119.88 Hz. |
| G5     | `latency_ms`, optional `scenario` | Per-row scenario (`unspecified` when absent); appends `summary` row with p95.                                                                                                                                                                   |
| G6     | `stall_ms`                        | Counts `> 16 ms` and `> 50 ms`; `duration_s` from `--duration` (300 when only G6 is selected).                                                                                                                                                  |
| G8     | `frame_ms`                        | Frame statistics external; memory growth is measured from the live replay session (no `memory_growth_mb` column).                                                                                                                               |
| G9     | `frame_ms`                        | Same statistics as G4.                                                                                                                                                                                                                          |

Missing file/column → `CAPTURE_REQUIRED`/`CAPTURE_SCHEMA` failure; empty data → `EMPTY_CAPTURE`. The runner never invents samples or derives frame times from compositor rAF proxies.

## Raw provenance recipe

Real G4/G5/G6/G8/G9 captures must come from a runner-written raw run directory, `<output>/raw/<run_id>/`, holding `provenance.json` and `SHA256SUMS` (see [Presentation collector](#presentation-collector)). `--capture-csv` rejects every other CSV with `STALE_CAPTURE`: a hand-made directory, a CSV copied elsewhere, a different commit, variant, environment or boot, a dirty tree or a run that did not end `captured`. G4/G9 are produced directly by `--collect presentation`; G5/G6/G8 have no producer yet, so **G5/G6/G8 cannot be captured for real yet**; only their dry-run schema fixtures and the ingest path exist. Do not assemble `provenance.json` or `SHA256SUMS` by hand to get past the check.

Evidence that still belongs beside any real run, in the run's output location and recorded rather than assumed: exact command line, stdout/stderr, tool versions, display mode and refresh rate, and the SHA-256 of every raw artifact. External tools are prerequisites, not runner dependencies; their availability varies by host.

- Screen recordings: `gpu-screen-recorder` where supported, or a compositor-aware tool. If transcoding or inspection is needed, use `ffmpeg` on the preserved original and keep both files; encoded output is not the timing source.
- Input events: `ydotool` can inject keystrokes and pointer events, but an injection timestamp alone is not a photon timestamp. Record events and presentation timestamps from a monotonic clock in the same clock domain, and correlate each injected scenario to the measured first presentation change before emitting G5 observations.
- G6 scheduler evidence, with the UI-thread identity mapping retained:

```sh
perf sched record -o "$OUT/perf.data" -- <isolated-app-command>
perf sched timehist -i "$OUT/perf.data" > "$OUT/stalls.timehist"
```

Limitations (honest scope of these tools):

- The [presentation collector](#presentation-collector) observes true presentation timestamps, and drives G4/G9 itself; its G5/G8 drivers are not implemented yet, so there is still **no complete G5/G8 frame-time recipe**. Leave `frame_ms`/`latency_ms` unproduced rather than approximating. An encoded fixed-rate stream (gpu-screen-recorder/ffmpeg at `-f N`) duplicates or drops frames on a fixed cadence: duplication counts can indicate dropped frames, but per-frame `frame_ms` **cannot** be derived from such a stream.
- Keystroke-to-photon (G5) requires correlating the input event timestamp with the first presentation change. ydotool gives injection time only; encoded video adds an unknown pipeline latency. Measure by pairing input-event monotonic timestamps with per-frame presentation timestamps; encoded recordings only bound the latency, they do not measure it.
- `perf sched timehist` attributes scheduling delays; map stalls to the UI thread explicitly and record the mapping with the artifact.

Runtime-only test data in temp/isolated directories.
