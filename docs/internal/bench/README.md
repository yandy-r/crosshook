## Fixture and app contract

Fixture generation command:

```sh
cargo run --manifest-path src/crosshook-native/Cargo.toml -p crosshook-core --example bench_fixtures -- --seed 42 --out DIR [--empty]
```

Materialize canonical fixtures into an isolated launcher root with:

```sh
-- materialize --from canonical --root isolated
```

Canonical tree includes `DIR/config/crosshook/profiles` and settings, `DIR/data/crosshook/metadata.db`, cache/images portraits, `DIR/logs/launch-50k.log`, and a manifest. Portable paths use `@CROSSHOOK_BENCH_ROOT@`. Same-seed canonical contents must compare equal; materialized paths intentionally depend on root. Seeded timestamps/UUIDs are normalized through public SQL API in the example; production schema and user data remain unchanged. Cover fixture is one generated 600×900 JPEG copied 500 times (identical-pixel limitation).

Fixtures and test state are runtime-only artifacts in isolated roots. No TOML user settings or SQLite user metadata changes are permitted. No real game/trainer launch. Production behavior is untouched unless `CROSSHOOK_BENCH=1`; when unset, benchmark instrumentation does one no-op IPC call.

For readiness, app prints `READY <CLOCK_MONOTONIC ns>` after summary fetch and double `requestAnimationFrame`, including empty state. This does not promise cover decode/scan completion. `CROSSHOOK_BENCH_EXIT_AFTER_READY=1` exits through `AppHandle.exit`. Log replay uses `CROSSHOOK_BENCH_ROOT` and `CROSSHOOK_BENCH_LOG=ROOT/logs/...`, at no more than 5,000 lines/s; it never launches a real workload. Console drawer must be open to measure log rendering. `CROSSHOOK_BENCH_SCENARIO` selects one G5 scenario (including the opt-in `health_table`), the G4 `health_scroll` scenario or the G8 `replay_scroll` scenario, and arms the app's `BENCH_*` markers (see [G5 input-to-photon driver](#g5-input-to-photon-driver), [G8 single-session driver](#g8-single-session-driver) and [Health-table supplemental](#health-table-supplemental)). With `replay_scroll` the replay waits for a `GO` line on stdin instead of starting at READY.

### Window presentation requirement

`READY` fires after a double `requestAnimationFrame`, and WebKitGTK only runs animation frames and paints while the compositor presents the window. A locked session, a display that is off or a minimized window leaves the webview blank and `READY` never arrives, even though the backend finishes bootstrap. This was the root cause of YAN-1985 on E1: the "blank webview under an isolated HOME" happened while the KDE session was locked, and HOME/XDG isolation and the NVIDIA driver played no part. Forcing the window minimized reproduces `READY_TIMEOUT` with empty stderr every time.

Before each launched capture (G1/G2/G3/G7/G8) the runner checks the session with logind `LockedHint` (`loginctl show-session auto`) and `org.freedesktop.ScreenSaver.GetActive`, and fails with `SESSION_LOCKED` instead of launching. If either probe reports a lock, the session counts as locked; with no probe available (no logind session or no screensaver service), the check is skipped. After a timeout the runner checks again and reports `SESSION_LOCKED` when the session locked mid-run; otherwise `READY_TIMEOUT` names the presentation requirement. G3 and G7 also check the lock before every sample and stop with `SESSION_LOCKED` instead of recording frozen samples; a G7 failure also stops its `perf` wakeup count at once. The probes never start anything: the ScreenSaver call needs an existing session bus (`DBUS_SESSION_BUS_ADDRESS` or `$XDG_RUNTIME_DIR/bus`, so `gdbus` cannot autolaunch a `dbus-daemon`) and a service that already owns the name (no bus activation). `loginctl show-session auto` resolves to the caller's session, and its `LockedHint` only counts when that session is graphical (`Type` `wayland` or `x11`). From ssh or a TTY the logind probe is unknown, so run the runner from a terminal inside the graphical session. A display that is off without a lock, or a window minimized by the user, cannot be probed and still ends in `READY_TIMEOUT`. Keep the session unlocked, the display on and the window visible for the whole capture, and turn off automatic screen locking and display power-off for long G3/G7 runs.

### Isolation requirements

All four XDG roots (`HOME` plus `XDG_CONFIG_HOME`, `XDG_DATA_HOME`, `XDG_CACHE_HOME`, and `XDG_RUNTIME_DIR`) must resolve inside the isolated fixture root; host-XDG overrides (`HOST_XDG_*`) stay disabled. Refuse real CrossHook data paths, symlink escapes, and custom `profiles_directory` roots (read from the real `settings.toml`). Preserve existing runtime/Wayland/DBus sockets. Never use `sudo`, drop host caches automatically, or start a real game/trainer. Guards run before any filesystem mutation; refusal prints `BENCH_REFUSE: …` and exits 10. Presentation G4/G5/G8/G9 also refuse with `INSTANCE_RUNNING` when `dev.crosshook.CrossHook` already owns the session bus (the bench window would hand off to that instance and receive the injected input), and with `INSTANCE_UNKNOWN` when the session bus cannot be asked. The check runs again immediately before every launch, so an instance started mid-run also exits 10.

For Flatpak, per-app data derives from the **launcher** `HOME` (`flatpak-context.c` / `flatpak_get_data_dir`); sandbox `--env=HOME=...` alone does not isolate the per-app data path. The runner launches with launcher `HOME=<root>/home`, `--nofilesystem=host:reset`, `--filesystem=<root>`, `--env=CROSSHOOK_FLATPAK_HOST_XDG=0`, and materializes fixture data under `<root>/home/.var/app/dev.crosshook.CrossHook`. It requires a fresh owned `crosshook-bench-*` launcher root. Isolation protects against host per-app data access; still inspect resolved paths before execution. After each Flatpak launch (`stop()`) and at the end of a Flatpak run, the runner inspects `flatpak ps` and stops any `dev.crosshook.CrossHook` sandbox or portal subsandbox proved to belong to that launch/run (matched by isolated `instance-path`, PID ancestry, isolated subsandbox environment, or pre-launch baseline exclusion with process start time when no baseline or concurrent user `dev.crosshook.CrossHook` instance exists — failing closed on unattributed subsandboxes otherwise, and never matching by app ID alone).

With `--collect presentation` it is the [single-session driver](#g8-single-session-driver). In CSV mode it also requires a `frame_ms` CSV; the runner launches the app with `CROSSHOOK_BENCH_LOG=<root>/logs/launch-50k.log` and `CROSSHOOK_BENCH_LOG_RATE=5000`, samples app process-tree memory for 11 seconds, and computes frame stats from the input CSV. CSV-mode G8 is implemented for Flatpak and native through common environment; its frame times stay external.

Cold G1 requires explicit page-cache preparation before each iteration; `--cold-cache-ack` only acknowledges preparation — runner does not drop caches. On a dedicated, controlled benchmark host, an authorized operator may use:

```sh
sync && echo 3 | sudo tee /proc/sys/vm/drop_caches >/dev/null
```

**Security / system-impact warning:** this requires privileged access and drops page cache, dentries, and inodes system-wide. It affects all processes and other users, may cause significant I/O/performance impact, and is unsafe on shared or production hosts. Never automate it in the runner. Record host, operator, command, and timestamp. A warm-cache run is G2, never G1. Dry-run is available for all ten metrics and writes `status=dry-run` rows; dry-run CSVs are schema fixtures, not data.

## Recipes

Every capture on E1, native and Flatpak. The per-metric sections below explain what each driver does and list its codes; they point here for commands. Results are baseline B evidence, not a gate.

### Prerequisites

- [ ] **Release build.** Native runs need `./scripts/build-release-binary.sh`; use the path it prints after `Built release binary:` as `--binary`. Flatpak runs need `./scripts/build-flatpak.sh --rebuild --strict --install`, which rebuilds the binary and installs the bundle as a user install (the runner shares that installation through `FLATPAK_USER_DIR`). The build must carry the bench markers and probes of the tree under test: a build without them ends in `BEGIN_TIMEOUT`.
- [ ] **Fixtures.** Generate the canonical tree with the command in [Fixture and app contract](#fixture-and-app-contract), `--seed 42` and no `--empty`, so it holds 500 profiles. The health scenarios need at least 300 live health rows.
- [ ] **Clean working tree.** A dirty tree is recorded in `meta.json` and provenance, and the run is then no `--capture-csv` evidence.
- [ ] **KWin and `gdbus`** on the session bus (G4/G5/G8/G9; `UNSUPPORTED_COMPOSITOR`, `MISSING_TOOL: gdbus`).
- [ ] **`/dev/uinput` ACL** for your user (G4/G5/G8; see [uinput access](#g4g9-input-drivers)). Without it the run fails with `INPUT_DEVICE_DENIED` (exit 40).
- [ ] **Shim tools.** Native: `cc`, `wayland-scanner` and `pkg-config` with libwayland-client 1.24 or newer. Flatpak: `org.gnome.Sdk//50`.
- [ ] **No running CrossHook**, native or Flatpak. G4/G5/G8/G9 refuse with `INSTANCE_RUNNING` (exit 10) otherwise.
- [ ] **Unlocked session, display on, window visible.** Turn off automatic screen locking and display power-off for long runs, and run from a terminal inside the graphical session, not from ssh or a TTY (see [Window presentation requirement](#window-presentation-requirement)).
- [ ] **No real XDG roots in the environment.** The runner refuses an inherited `XDG_*` that points at a real default location or holds a CrossHook store, so every command below runs through the `bench_e1` wrapper, which unsets them.
- [ ] **`--refresh-hz` set to the panel's active mode**: 180.06 on E1, 119.88 after switching to the 120 Hz-class mode (`kscreen-doctor -o` shows it). A mismatch is `REFRESH_MISMATCH` (exit 40).
- [ ] **Hands off the keyboard and mouse** from `BENCH_NOTICE` until the run ends.

## Presentation collector

`--collect presentation` measures when the compositor actually presented the app's frames. Wayland only gives presentation feedback to the client that owns a surface, so the runner preloads a bench-only shim into the app:

- **Source**: [`scripts/bench/presentation/wlpresent.c`](../../../scripts/bench/presentation/wlpresent.c), `wlfocus.c` (keyboard, pointer and configure tracking) and the shared header `wlpresent.h`, plus the vendored stable `presentation-time.xml` (MIT). It is never part of a release, the Flatpak manifest or any packaging script.
- **Build**: per run, into `<isolated root>/bench-tools/` by [`bench_shim.py`](../../../scripts/bench/bench_shim.py): host `cc` and `wayland-scanner` for native runs, `org.gnome.Sdk//50` for `--flatpak` (the runtime's glibc and libwayland differ from the host's). The `.so` and source hashes go into the provenance manifest. The shim needs libwayland-client >= 1.24 (`wl_proxy_get_interface`; Ubuntu 24.04 ships 1.22), checked with `pkg-config --atleast-version=1.24 wayland-client` on the host and inside the SDK. Missing tools fail with `MISSING_TOOL: cc|wayland-scanner|pkg-config|org.gnome.Sdk//50|libwayland-client >= 1.24`; `python3 scripts/bench/bench_shim.py --check` is the CI compile check.
- **Arming**: inert unless `CROSSHOOK_BENCH=1` and `CROSSHOOK_BENCH_PRESENT_DIR` is an absolute path. The runner scrubs inherited loader, debug and module variables (`LD_PRELOAD`, `LD_LIBRARY_PATH`, `LD_AUDIT`, `LD_DEBUG`, `LD_DEBUG_OUTPUT`, `LD_PROFILE`, `LD_PROFILE_OUTPUT`, `GLIBC_TUNABLES`, `WAYLAND_DEBUG`, `GTK_MODULES`, `GTK3_MODULES`, `GIO_EXTRA_MODULES`, `GST_PLUGIN_PATH`) and sets only its own `LD_PRELOAD` (forwarded through `flatpak run --env`). The shim starts no thread at load, so the app's single-thread startup check is unaffected; it initialises on the first `wl_surface.commit`. A process forked after init gets a pass-through shim (`pthread_atfork` disarms it and closes its log descriptor).
- **Known perturbation**: the shim runs on the app's render thread. Every commit costs one `write(2)` and every presented or discarded event costs another, a few microseconds each, plus a feedback object on the private queue. Initialisation does one blocking roundtrip on the private queue (registry bind and `clock_id`) inside the first commit. Both are inside the measured window, so compare presentation captures only with other captures taken with the same shim. The log stops after 500,000 records (`X log_cap`), which keeps it below the parser's 64 MiB limit.
- **What it does**: on every `wl_surface.commit` it first sends `wp_presentation.feedback` on a private event queue, then forwards the commit, and logs the compositor's answer. Timestamps are CLOCK_MONOTONIC, the same clock as `READY` and the runner; any other `clock_id` fails with `PRESENTATION_CLOCK`. A compositor without `wp_presentation` fails with `NO_PRESENTATION_GLOBAL` (the shim then writes `clock_id=-1` plus an `X no_presentation_global` record, and the parser checks that first).
- **Log format `wlpresent v1`** (`present/**/wlpresent-<pid>.log`, mode 0600, tab-separated): `H` header (pid, comm, `clock_id`, protocol version, app env snapshot); `S` surface role (`toplevel`, or `destroyed` when a toplevel `wl_surface` is destroyed, because the server may reuse its id); `C` commit (`commit_ns surface_id feedback_seq has_buffer`); `P` presented (`recv_ns feedback_seq presented_ns refresh_ns msc flags`); `D` discarded; `X` condition (`no_presentation_global`, `bind_failed`, `wrap_failed`, `log_cap`); `K` keyboard focus (`ns enter|leave surface_id`) and `M` pointer focus (same fields), from the `wl_keyboard`/`wl_pointer` enter and leave events; `G` toplevel configure geometry (`ns surface_id width height activated`), from `xdg_toplevel.configure`. The `K`/`M`/`G` records are the evidence the G4/G9 drivers act on (see [G4/G9 input drivers](#g4g9-input-drivers)). [`bench_present.py`](../../../scripts/bench/bench_present.py) parses it; roles are applied in log order, so a commit counts as a frame only if the latest `S` record for its surface before it says `toplevel` and it attached a buffer.
- **Refresh check**: whenever at least one presented toplevel frame exists, the median `refresh_ns` the compositor reports must be within 0.5 % of `--refresh-hz`, otherwise `REFRESH_MISMATCH` (exit 40); a compositor that reports no refresh period skips the check. Pass the mode you actually use (E1 runs at 180.06 Hz unless switched to 119.88 Hz).
- **G1/G2**: `--collect presentation` does not set `CROSSHOOK_BENCH_EXIT_AFTER_READY`; after `READY` the runner waits up to 2 s for a presented toplevel frame, then stops the app. Each row adds `first_present_ms` (launch to the first presented toplevel frame; this may be the window background before content) and `first_content_ms` (launch to the first toplevel frame presented at or after `READY`), and the summary row adds `first_present_p50_ms`/`first_present_p95_ms` and `first_content_p50_ms`/`first_content_p95_ms`. Without a frame at or after `READY` within 2 s the run fails with `NO_CONTENT_FRAME`. See [First-content supplemental](#first-content-supplemental). Commands: [Recipes](#recipes).
- **Raw run directory**: every presentation run writes `<output>/raw/<run_id>/` (0700, files 0600) with the shim logs, the metric CSVs, `meta.json`, `provenance.json` (schema `crosshook-bench-provenance/1`: run id, commit and dirty flag, variant, environment, boot id, fixture seed, binary sha256, shim hashes, status) and `SHA256SUMS`. It is written even when the capture fails. The `--binary` sha256 is taken before launch and re-checked before sealing. `provenance.json` itself must be listed and checksummed in `SHA256SUMS`, or `verify_capture` refuses with `STALE_CAPTURE`. `--capture-csv` only accepts a CSV listed in such a directory whose checksums, commit, variant, environment and boot id match the current run (`STALE_CAPTURE` otherwise). `verify_capture` also requires the run `status` to be `captured`, the working tree to have been clean (`dirty` false) and a known boot id; a failed run, a dirty tree or an unavailable boot id is `STALE_CAPTURE`. A run directory is never reused (`RAW_DIR_EXISTS`, `RAW_DIR_SYMLINK`), and each iteration gets a fresh present directory (`PRESENT_DIR_EXISTS`).
- **Flatpak user installs**: the isolated launcher `HOME` would hide a `--user` installation, so the runner sets `FLATPAK_USER_DIR` to the real per-user installation, but only when it is a real directory (not a symlink) owned by the current user. Only the installation is shared; per-app data still derives from the isolated `HOME`.
- **Flatpak overrides**: `--flatpak` runs record the SHA-256 of `overrides/global` and `overrides/dev.crosshook.CrossHook` from that installation (regular files only; absent ones are omitted) as `flatpak_overrides` in `meta.json` and `provenance.json`, because an override changes the sandbox the numbers were measured in.

Validated on E1 (2026-11-16): native and Flatpak G2 (figures in [First-content supplemental](#first-content-supplemental)); Flatpak G2 loads the SDK-built shim inside the sandbox. G5 is driven by the app's frontend markers (see [G5 input-to-photon driver](#g5-input-to-photon-driver)); G8 is one launch per iteration with a memory sampler (see [G8 single-session driver](#g8-single-session-driver)).

### G4/G9 input drivers

`--collect presentation --metric G4|G9` launches the isolated app once per scenario and iteration, drives it, and computes frame intervals only from the shim's presented timestamps, windowed by the runner's own input stamps. It needs KDE Plasma (KWin) on the session bus, `gdbus`, and a user-writable `/dev/uinput`; it never uses `sudo`. Quit CrossHook first (`INSTANCE_RUNNING`, or `INSTANCE_UNKNOWN` when the bus cannot say), keep the session unlocked, and do not touch the keyboard or mouse after `BENCH_NOTICE` appears. Commands: [Recipes](#recipes).

- **uinput access**: without write access to `/dev/uinput` the runner fails with `INPUT_DEVICE_DENIED` and points here. Grant your user an ACL temporarily with `sudo setfacl -m u:$USER:rw /dev/uinput` (lost on reboot or when the node is recreated), or persistently with a udev rule such as `KERNEL=="uinput", SUBSYSTEM=="misc", TAG+="uaccess"` in `/etc/udev/rules.d/70-uinput.rules`, then `sudo udevadm control --reload && sudo udevadm trigger /dev/uinput`. The runner itself never calls `sudo`. G4, G5 and G8 open the device; G9 resizes through KWin.
- **Input**: a private uinput device (`crosshook-bench`) advertises only the wheel, Ctrl, K, Enter and the letters of `settings` (the Ctrl+K palette chord), plus `q`, Backspace, Left and Right for G5; every key down is paired with its up, and closing the device (also on abort) releases everything. A key is recorded as held before its down is written, and a write the kernel cuts short fails with `INPUT_WRITE_SHORT`, so a down that may have reached the device is always released. `bench_capture.stop()` holds SIGTERM, SIGHUP and SIGINT while it tears the app's process group down and delivers the first one afterwards, so a second signal during an abort cannot orphan the app.
- **Window control**: KWin's D-Bus window list (`/WindowsRunner` `Match`, `/KWin` `getWindowInfo`) finds exactly one window whose host pid is in the app's process tree. One-shot KWin scripts (int-only JS, written 0600 into the 0700 `bench-tools` dir, always unloaded and then deleted) place it at 1280×900 logical (1600×1000 for the G4 `console` scenario and G8) under the current cursor and activate it; the placement is verified through `getWindowInfo`. G9's per-step resizes are not (a `getWindowInfo` round trip would not fit in 33 ms): the shim's `G` configure records are their witness (`RESIZE_NOT_OBSERVED`). Scripts share one pid-filter preamble and are written inside the cleanup scope, and a failed unlink never masks the error that is propagating.
- **Focus witness**: the shim also logs keyboard (`K`) and pointer (`M`) enter/leave and toplevel configure geometry (`G`). The witness runs before every injected event: before each key the driver checks that the app is alive and that the keyboard enter on the bench toplevel is current, and before each timed notch that the pointer enter is current (`FOCUS_LOST` otherwise, so at most one event is sent after focus is lost). The driver reads those records incrementally (only the lines the shim appended since the last read), so the pointer check before each timed notch is cheap enough for the 33 ms scroll cadence (the key checks run between keys and have no cadence). The witness is only as good as the log: any `X` record that ends the shim's evidence (`log_cap`, `bind_failed`, `wrap_failed`, `no_presentation_global`) stops the run with `PRESENT_LOG_INCOMPLETE: <reason>`, and during the timed scroll a log that has not grown for 2 s fails with `FOCUS_LOST: presentation log stopped growing`, because a scroll commits frames (the idle waits before the scroll are not watched). The session-lock probe spawns processes, so it runs at most every 300 ms (and before the priming notch). KWin sends the pointer enter only on the first wheel event, so one untimed priming notch precedes the timed scroll; the wheel device sends exactly one notch per call.
- **Arm step**: that notch goes to whatever is under the cursor, so before it a one-shot KWin script finds the window by pid and sets `keepAbove = true` only if it is the active window, not minimized, and `workspace.cursorPos` lies inside its `frameGeometry` (otherwise `keepAbove = false`). The driver polls `getWindowInfo` for `keepAbove` for 1 s; if it never reads true it raises `POINTER_NOT_OVER_WINDOW: the bench window is not active under the cursor` and sends no notch. `keepAbove` also stops other windows from covering the bench window for the rest of the run.
- **G4**: `library` scrolls the start page; `settings` first opens the palette (Ctrl+K, `settings`, Enter); `console` places the window at 1600×1000 with the cursor at (800, 860), because the console renders only in the wide layout (see [G8 single-session driver](#g8-single-session-driver)), writes an isolated `settings.toml` with the drawer expanded (the other scenarios delete any such file first, and the collector removes it again when the metric finishes, even on failure, and before G9, so it never leaks into later scenarios or metrics; the file is only ever written or deleted when its resolved path lies inside the `crosshook-bench-*` root that holds `CROSSHOOK_BENCH_ROOT`, otherwise `SETTINGS_UNSAFE`), replays the 50k-line fixture log (so it needs `--fixtures`: `FIXTURES_REQUIRED` before any launch), and waits until the app stops presenting (`REPLAY_NOT_SETTLED` after 25 s). The timed scroll is 180 notches at 33 ms, alternating 10 down and 10 up so short pages never reach their end and go idle. Rows: one per scenario, pooled over iterations.
- **G9**: KWin resize steps for 5 s of wall time, paced at a target of 30 steps/s (about 150 when KWin keeps up), between 1120×780 and 1400×880 logical (inside one layout breakpoint class); at least 10 distinct configured sizes are required (`RESIZE_NOT_OBSERVED`). Each step is a KWin script round trip, so a slow KWin achieves fewer steps rather than a longer run; the frame window runs from the first step to the last step plus a 300 ms tail. The achieved step count and driven duration are recorded per iteration in `provenance.json` under `drive_stats` (`{metric: {scenario: [{iteration, injected, driven_s}]}}`, `injected` being notches for G4 and steps for G9), since the CSV schema has no column for them.

### G5 input-to-photon driver

`--collect presentation --metric G5` launches the isolated app once per scenario and iteration, injects one key per trial and measures from that key to the compositor's presentation of the frame that shows the change. It has the same prerequisites as G4/G9: KWin on the session bus, `gdbus`, a user-writable `/dev/uinput` (see [G4/G9 input drivers](#g4g9-input-drivers)), no running CrossHook, an unlocked session, and no keyboard or mouse use after `BENCH_NOTICE`. The default scenarios need `--fixtures`, but the runner does not gate on it for them: the favorite, optimization and D-pad targets are library cards, and a failed setup or a missing target makes the app send no mark, so the run ends with `MARK_TIMEOUT`. It also needs a build that carries the markers; a build without them never prints `BENCH_BEGIN` (`BEGIN_TIMEOUT`). The opt-in `health_table` scenario is gated: without `--fixtures` it fails with `FIXTURES_REQUIRED` before any launch.

The latency is always `latency_ms = (presented_ns - inject_ns) / 1e6`, with `inject_ns` read from `CLOCK_MONOTONIC` immediately before the key-down write. The app's marks and the clock offset only decide **which** presented frame answers the key; they are never part of the duration.

- **Markers**: the app writes one integer-only line per marker on stderr: `BENCH_CLOCK <ns> <seq> <t_perf_us>`, `BENCH_BEGIN <ns> <scenario>` and `BENCH_MARK <ns> <scenario> <seq> <phase> <t_perf_us>`, where `<phase>` is one of `armed`, `render`, `focus_lost`, `console_hidden`, `follow_on`, `follow_off`, `health_ready` or `health_rows_too_few`. `<ns>` is the backend's `CLOCK_MONOTONIC` stamp taken at the write; `<t_perf_us>` is the webview's `performance.now()` in microseconds. They come from the Tauri commands `bench_clock`, `bench_begin` and `bench_mark`. The backend emits them only with `CROSSHOOK_BENCH=1` and a valid `CROSSHOOK_BENCH_SCENARIO`, which the runner forwards through `--env` for Flatpak. It validates the scenario (it must be the active one), the phase, `seq` (at most 1,000,000) and the time (finite, 0 to 86,400,000 ms) before writing, and writes at most 100,000 marks and 100,000 clock samples per process (one `BENCH_ERROR: marker cap reached` line after that). An unknown scenario value prints one `BENCH_ERROR:` line and arms nothing. After `READY` the runner reads stderr on a daemon thread instead of draining it; any other line is discarded, and a malformed `BENCH_*` line is recorded, never guessed at.
- **Probe**: `bench_ready` returns the scenario name, and only then is the frontend probe loaded with a dynamic import. In production and in every non-bench session it returns nothing, so the probe adds no listeners or timers. The probe syncs the clock, calls `bench_begin` (once), runs the scenario setup, then repeats per trial: focus the target, send `armed`, wait for the first matching DOM change, and send `render` after the next animation frame, carrying the `performance.now()` read inside the callback that saw the change. A real window blur sends `focus_lost`; a failed setup or a missing target sends no mark at all, so the runner reports `MARK_TIMEOUT`. The probe never injects input and never calls `preventDefault`. Its `seq` restarts at 0 in every launch.
- **Scenarios**: each focuses its target, and the runner injects the key listed for trial `n` (starting at 0, alternating when two keys are listed).

  | Scenario              | Target                                                                                                                                       | Change the probe waits for                                                | Key per trial  |
  | --------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------- | -------------- |
  | `search`              | Library search input (`Search games`)                                                                                                        | Library content outside the toolbar changes after the input value changed | `q`, Backspace |
  | `toggle_favorite`     | First favorite toggle on the library                                                                                                         | Its `aria-pressed` attribute changes                                      | Enter          |
  | `toggle_optimization` | First enabled launch-optimization checkbox (see setup below)                                                                                 | Its `change` event                                                        | Enter          |
  | `dpad`                | First library card                                                                                                                           | Focus moves to another element inside the focus scope                     | Right, Left    |
  | `route_switch`        | The tab trigger of the route that is not active (library or settings), focused without activating it (Radix would otherwise switch on focus) | The route content root's children change                                  | Enter          |

  `search` types `q` because no fixture name (`Bench Game NNNN`) contains it, so each `q` flips the grid from the full list to the empty state and each Backspace flips it back. The toggle, `dpad` and `route_switch` keys alternate states the same way, which is why `--trials` must be even. `toggle_optimization` first reaches its checkbox through DOM activations: library card "View details", then the hero "Launch options" tab, then the "Optimizations" sub-tab. Each step waits up to 10 s; a step that cannot be reached sends no mark, so the runner reports `MARK_TIMEOUT` for the missing `armed`.

- **Clock mapping**: `performance.now()` is floored to 1 ms. The probe sends sequential `bench_clock` samples, each stamped just before its call, until it has 20 fast round trips (a gap of at most 2 ms between consecutive samples), or for up to 30 s or 400 samples, and never fewer than 20 samples. The wait matters because the app stays busy after `READY` (the Flatpak build with 500 profiles stays busy for about 11 s, with IPC round trips of about 110 ms), and a slow pair cannot pin the offset. The runner pairs adjacent samples: the round trip is at most the gap between their JS stamps, and the offset is the backend `ns` minus the midpoint of the two stamps. It keeps only the pairs within 1 ms of the best round trip (at least 5 of them, from at least 10 pairs, and a best round trip of at most 4 ms), takes the median of their offsets and sets `uncertainty` to half the slowest kept round trip plus 1 ms (the timer floor). Otherwise `CLOCK_SYNC_FAILED`. A `render` mark maps to `render_ns = t_perf_us * 1000 + offset`.
- **Frame selection**: candidates are toplevel commits with a buffer, made at or after `inject_ns`. The chosen frame is the first one committed at or after `render_ns + uncertainty` that was presented (not discarded) before the deadline, `inject_ns` plus the mark timeout. A candidate committed inside `[render_ns - uncertainty, render_ns + uncertainty)` cannot be told apart from the change frame, so the trial is `ambiguous` and has no latency. A trial with no such frame by the deadline is `timeout`. A `render` mark that lies before the injected key by more than the uncertainty cannot belong to that key (the clock mapping or the marks are off), so the trial is `early`: it is recorded, selects no frame, has no latency and prints one `BENCH_NOTICE` on stderr per scenario and iteration. The selection waits until the log shows a decision, since the shim logs commits in time order.
- **Quiet gate**: before each key the runner waits until no toplevel commit has been made for `max(250 ms, 2 x p50 frame interval)` (the p50 is over the gaps of at most 200 ms between the last 30 presented frames, so idle time and the runner's own quiet waits cannot inflate it; with no such gap the 250 ms floor applies), so a late frame from the previous trial cannot be taken for the change. The wait fails with `NOT_QUIET` after `max(10 s, 2 x the mark timeout)`: 20 s native with the default `--timeout`, 40 s Flatpak.
- **Mark timeout**: the larger of 5 s (native) or 20 s (Flatpak) and `--timeout / 6`, so 10 s native and 20 s Flatpak with the default `--timeout 60`. It bounds every `armed` and `render` wait and the frame deadline, except that the first `armed` wait (trial 0) gets it plus 40 s because the probe's setup runs after `BENCH_BEGIN` (up to four waits of up to 10 s for `toggle_optimization`: the three steps and the final wait for the checkbox), or plus 80 s for `health_table` (its 60 s row wait and 20 s of slack); `BENCH_BEGIN` gets it plus 35 s for clock sync. Mark waits run in 250 ms slices that re-check the app, the session lock and `focus_lost` marks.
- **Input and focus**: keys go out only while the shim shows keyboard focus on the bench toplevel (the [focus witness](#g4g9-input-drivers) G4 uses), and each trial re-checks that the app is alive and the session unlocked. A `focus_lost` mark (every one is kept, whatever its `seq`), a lost keyboard focus, a locked session or an app exit stops the run before the next key (`FOCUS_LOST`, `SESSION_LOCKED`, `APP_EXIT`). The window is placed under the cursor and armed with `keepAbove`, as in G4. The runner does not set `CROSSHOOK_BENCH_LOG` for G5, so there is no log replay.
- **Status**: a scenario row is `partial` when more than 10 % of **all** its trials are not measured (`ambiguous`, `timeout` and `early` added together), otherwise `captured`, so dropping slow or odd trials cannot bias the row toward fast ones. The row reports the three counts in its `ambiguous`, `timeout` and `early` columns. Fewer than 10 measured trials fail the run with `CAPTURE_TOO_SHORT: <scenario>: <n> measured trials, need 10`. A `partial` row makes the run's `meta.json` and provenance status `partial`, so the run is no longer a `captured` run for `--capture-csv`.
- **State**: `toggle_favorite` and `toggle_optimization` change the isolated profile. Before such a scenario the runner copies the profile TOML directory and `metadata.db` with its `-wal` and `-shm` files into `g5-state/`, and puts them back after every iteration while the app is stopped, also after a failure (abort signals are held while it restores). The runner deletes `g5-state/` only if it created it: an existing one is refused and left alone. Every path is resolved first and refused unless it lies inside the `crosshook-bench-*` root; symlinks are never followed, copied or restored (`STATE_UNSAFE`).
- **Outputs**: `G5.csv` has one row per scenario, pooled over iterations, with the columns `scenario`, `p50_ms`, `p95_ms`, `p99_ms`, `measured`, `ambiguous`, `timeout`, `early`, `status`. Per-trial evidence goes in `raw/<run_id>/observations/G5-<scenario>.csv` (`seq`, `inject_ns`, `render_ns`, `commit_ns`, `presented_ns`, `latency_ms`, `uncertainty_ms`, `status` of `measured`, `ambiguous`, `timeout` or `early`; `seq` counts across iterations), rewritten after every iteration so a later failure keeps the evidence, and sealed in `SHA256SUMS`. `provenance.json` records `trials` and, under `drive_stats.G5.<scenario>`, `{iteration, injected, driven_s, uncertainty_ms}` per iteration.
- **Errors**: the new codes are in the exit-code list above. Besides the clock and state codes, `MARK_TIMEOUT` and `BEGIN_TIMEOUT` mean the app stopped arming or never started the probe, and `EVENT_STREAM_ENDED` means its stderr closed first.

Commands are in [Recipes](#recipes): quit CrossHook first, the build must include the markers, and Flatpak needs the rebuilt local Flatpak installed.

### G8 single-session driver

`--collect presentation --metric G8` launches the isolated app once per iteration and measures, from that one launch, the frames presented while the console replays 50,000 log lines and the memory of the app's process tree. It has the same prerequisites as G4/G9 (KWin on the session bus, `gdbus`, a user-writable `/dev/uinput`, no running CrossHook, an unlocked session, no keyboard or mouse use after `BENCH_NOTICE`; see [G4/G9 input drivers](#g4g9-input-drivers)). It needs `--fixtures` (`FIXTURES_REQUIRED` before any launch) and a build that carries the G8 scenario and probe. Its one scenario is `replay_scroll`.

- **Scenario and deferred replay**: the runner sets `CROSSHOOK_BENCH_SCENARIO=replay_scroll` on top of the G4 console setup (an isolated `settings.toml` with the drawer expanded, `CROSSHOOK_BENCH_LOG`, `CROSSHOOK_BENCH_LOG_RATE=5000`; Flatpak receives them only through `--env`). With that scenario READY does not start the replay: it parks the replay plan. The frontend probe calls `bench_begin`, which takes the parked plan once and starts the replay after the go signal. The G4 `console` scenario sets no scenario, so its replay still starts at READY and writes no `BENCH_REPLAY` lines.
- **Go signal**: the app waits up to 120 s for exactly `GO\n` on stdin. It then replays at 5,000 lines/s and writes `BENCH_REPLAY <ns> start <total>` before the first line and `BENCH_REPLAY <ns> done <sent>` after the last (integers only). EOF, a timeout or any other bytes write one `BENCH_ERROR: GO_SIGNAL_FAILED: <reason>` and replay nothing. Stdin is used because the pipe is the runner's alone, so the webview cannot forge the signal (a priming wheel notch could be forged by a stray wheel or by JS). The app reads it on a plain thread with `poll(2)`, only when bench mode is on and a plan is parked; it never uses `tokio::io::stdin`. The runner launches the app with a stdin pipe (`GO_STDIN_MISSING` if there is none) and closes it on every exit path. Stdin was checked to pass through `flatpak run` (`echo GO | flatpak run --command=head org.gnome.Sdk//50 -c 16`), and the Flatpak capture below used it.
- **Probe**: `bench_ready` returns `replay_scroll` and the replay probe runs instead of the G5 probe (no clock sync). It waits up to 30 s for a visible console log: the `console-drawer` section present and not collapsed, its toggle `aria-expanded="true"`, and the console body in the DOM. If there is none it sends the `console_hidden` mark and never calls `bench_begin`, and the runner fails with `CONSOLE_NOT_VISIBLE` before any `GO`. Otherwise it sends a `follow_on` or `follow_off` mark (scrolled to within 24 px of the bottom, the console's own follow threshold) and calls `bench_begin`. Both are `BENCH_MARK` lines with scenario `replay_scroll` and `seq` 0. The runner keeps the first such mark as `follow` (`on` or `off`); `BENCH_BEGIN` without one is `REPLAY_MARK_MISSING`. The probe also registers one persistent window `blur` listener when it starts (before the console wait, never `once`, registered a single time however often the probe is started) that sends `focus_lost` with scenario `replay_scroll` and `seq` 0 on the first blur and nothing after that. It stays registered for the life of the page, past `bench_begin`, so a blur during the replay reaches the runner; only an abort removes it. This is the app-side witness behind `FOCUS_LOST` in the exit codes above and in step 7.
- **Window**: 1600×1000 logical with the cursor at (800, 860) inside it, over the console drawer. The console renders only in the wide layout (1440 px and wider); at 1280×900 the shell shows only a status bar.
- **Steps**:
  1. Place the window and wait for `BENCH_BEGIN` (mark timeout plus 35 s, `BEGIN_TIMEOUT`).
  2. Require the console and read the follow mark.
  3. Baseline idle gate: wait until no toplevel frame was presented for 1 s, for up to 25 s (100 s under Flatpak), or `BASELINE_NOT_IDLE`. The baseline gate keeps the G4 figure of 1 s because the replay is still parked, so nothing paces frames at more than 1 s; the settle gate in step 8 is longer.
  4. Start the sampler and hold a 3 s `baseline` phase. The runner checks every 0.5 s that the app is alive and the session unlocked.
  5. Priming: arm the window under the cursor and send one untimed wheel notch, as in G4. No pointer enter within 1 s is `POINTER_NOT_OVER_WINDOW`.
  6. Send `GO`. The `replay` phase starts when `BENCH_REPLAY start` arrives (within the mark timeout, or `REPLAY_NOT_STARTED`).
  7. Scroll: one notch every 33 ms, alternating 10 down and 10 up, until `BENCH_REPLAY done`. Before each notch the runner checks that the app is alive, the session is unlocked, no `focus_lost` mark arrived and the pointer enter is current, and that the presentation log has grown within 10 s (a replay frame can take over 2 s). No `done` within 4 x the nominal replay time plus 30 s (70 s for 50,000 lines) is `REPLAY_NOT_DONE`; a replay that finishes before the first notch is `REPLAY_NOT_SCROLLED`.
  8. `settle` phase: wait for the window to go idle again: no toplevel frame for 3 s (`SETTLE_IDLE_S`), within 25 s native or 100 s Flatpak, else `REPLAY_NOT_SETTLED`. Replay frames can be more than 1 s apart (a frame can take over 2 s), so the G4 gate of 1 s would call the window idle between two frames of the replay; G4 keeps its 1 s.
  9. `tail` phase: hold 3 s, then stop the sampler.
- **Frame window**: `[start, done + 300 ms]`, with `start` and `done` the app's own `BENCH_REPLAY` stamps (CLOCK_MONOTONIC, the shim's clock). Frame intervals are the gaps between consecutive presented toplevel frames inside the window, and `DISCARD_RATE` counts discards inside it. As for G4/G9, an iteration needs 5 intervals and the pooled row 30 (`CAPTURE_TOO_SHORT`). `over_interval_percent` is the same figure as for G4 (the share of intervals over 1.5 refresh periods), but for G8 it saturates at 100: the app presents about 2–3 frames per second during the replay, so every interval is far over 1.5 periods at any real refresh rate. Read it as "every frame was late", not as a ratio; use the percentiles and `frames` to compare runs.
- **Memory**: PSS and USS of the app's process tree (the launched process and its descendants) are read from `smaps_rollup` every 100 ms, and GPU memory every 1 s on a separate thread, so a slow GPU tool cannot stretch the PSS cadence. Every row carries its phase: `baseline`, `replay`, `settle` or `tail`; the phase and the row's `t_ns` are read together under one lock, so a row is tagged with the phase it was stamped in. A pid is identified by its first start time: a pid that another process reuses is dropped from the sums (and counted in `failed_pids`) and is never adopted, as are unreadable and foreign-UID pids. Samples stop at 20,000 (`MEMORY_SAMPLES_EXCEEDED`). A sampler thread that dies on an unexpected error stops the sampler and fails the iteration with `MEMORY_SAMPLER_FAILED`.
- **Growth**: `memory_growth_mb` is `median(tail PSS) - median(baseline PSS)` for the iteration; `gpu_growth_mb` is the same over the GPU samples (one value per distinct 1 s sample), using only the samples whose read began at or after the first row of the phase: a sample that began before the phase (the previous phase's last reading, still carried by the first rows) is left out, and a side with none left has no GPU growth. Each phase needs at least 3 PSS samples (`MEMORY_SAMPLES_INSUFFICIENT`, or `MEMORY_UNAVAILABLE` with none readable). This replaces the earlier figure, peak minus first sample over an 11 s window that started after the replay was already running; CSV-mode G8 still reports that one. `peak_pss_mb` is the highest PSS of any phase.
- **GPU sources**: DRM fdinfo first (`drm-total-*`, de-duplicated per DRM client), then `nvidia-smi pmon -s m -c 1` for the sampled pids (3 s timeout; more than 1 MiB of output kills the tool and counts as `tool_failed`). A sample with neither is `unavailable:<reason>` and its value stays blank, never 0. Reasons: `no_drm_keys` (no `nvidia-smi`, and fdinfo was readable but has no memory keys), `no_tool` (no `nvidia-smi` and no readable fdinfo), `no_matching_pid` (pmon lists none of the sampled pids), `no_numeric_fb` (pmon lists the sampled pids but every `fb` is `-`, so the driver gave no figure; this matches G3, whose `gpu_mb` is `unavailable` in the same case), `tool_failed` (`nvidia-smi` failed, timed out, exited non-zero, printed too much or returned a bad row) and `probe_error` (the GPU probe itself raised; the sampler records it and goes on). A numeric `fb` of `0` is a measured 0, and a pid with `-` next to one with a number is summed over the numeric ones. `gpu_source` for an iteration is the source that answered, `fdinfo` or `nvidia-smi` (joined with `+` if both did). Without GPU growth it is an `unavailable:<reason>`: the first one among the baseline and tail readings, or `unavailable:no_sample` when every reading had a source but one side has no sample of its own phase. It is never a numeric source with a reason.
- **Session binding**: each iteration is tagged with a session (run id, iteration, launch pid, launch time). The frames take the iteration from their present directory (`present/G8/replay_scroll/iter-N`) and their pid from the evidence: the `pid=` in the header of every shim log that presented a toplevel frame (`PRESENT_LOG_MALFORMED` if it is missing). Natively that pid must be the launched process. Under Flatpak the shim logs its sandbox pid, which is accepted when it is the innermost `NSpid` of a sampled process or the host pid of a sampled one. Any other pid is `SESSION_MISMATCH`, so a log from another launch cannot be passed off as this one. The memory samples take their pid from the sampler's root pid. The iteration fails with `SESSION_MISMATCH` unless the tags agree, no frame or memory sample precedes the launch, and the memory samples span the whole frame window. The collector needs the run id the runner assigns (`RUN_ID_MISSING`).
- **Outputs**: `G8.csv` has one row with the columns `scenario` (`replay_scroll`), `p50_ms`, `p95_ms`, `p99_ms`, `stddev_ms`, `over_interval_percent`, `frames`, `memory_growth_mb`, `peak_pss_mb`, `gpu_growth_mb`, `gpu_source`, `follow`, `status`. Two observation CSVs go in `raw/<run_id>/observations/`, rewritten after every iteration and sealed in `SHA256SUMS`. Times are CLOCK_MONOTONIC ns, and a missing reading is blank.

  | File                          | Columns                                                                    | Content                                                                                                                                                      |
  | ----------------------------- | -------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
  | `G8-replay_scroll-memory.csv` | `t_ns`, `phase`, `pss_mb`, `uss_mb`, `gpu_mb`, `gpu_source`, `failed_pids` | Every memory row of every iteration; `failed_pids` counts the pids of that sample that were unreadable, foreign or reused (0 when every pid was read).       |
  | `G8-replay_scroll-frames.csv` | `presented_ns`, `frame_ms`, `in_window`                                    | Every presented toplevel frame of every launch; `frame_ms` is the gap to the previous frame of the same launch (blank for the first); `in_window` is 1 or 0. |

- **Aggregation**: with several iterations the intervals are pooled, `memory_growth_mb` is the median of the per-iteration growths, `peak_pss_mb` the maximum, `gpu_growth_mb` the median (blank unless every iteration has GPU growth), `gpu_source` the sources joined with `+`, and `follow` is `mixed` when the iterations disagree.
- **Provenance**: `drive_stats.G8.replay_scroll` holds one entry per iteration: `session` (`run_id`, `pid`, `launch_ns`), `start_to_done_s`, `settle_s`, `notches`, `driven_s`, `follow`, `gpu_source`, `nvidia_smi_path` (the resolved path, or null when `nvidia-smi` was not needed or not found), `gpu_denied_max` (the most fdinfo reads skipped for permission in any one GPU sample of the iteration), `web_process_sampled` and `sampled_pids`. Each sampled process is recorded once, keyed on its pid and start time (a reused pid is a second entry), with its `comm`, its `start_time` (field 22 of `/proc/<pid>/stat`, null when unreadable) and, under Flatpak, its `nspid` (host pid first, innermost namespace last); `comm` and `cmdline` are read in at most 4,096 bytes. `web_process_sampled` says whether a `WebKitWebProcess` was in the sampled tree. The isolated `settings.toml` is deleted when the metric finishes, also after a failure.

Commands are in [Recipes](#recipes): quit CrossHook first, the build must include the G8 scenario and probe, and Flatpak needs the rebuilt local Flatpak installed. One iteration may give fewer than 30 intervals, because the app presents about 2–3 fps during the replay, so use at least 2 native or 4 Flatpak iterations.

Neither is in a metric's default list, so the canonical G4 and G5 baselines keep their scenario sets. Both need `--fixtures` with the 500-profile tree and the usual presentation prerequisites. Commands are in [Recipes](#recipes).

- **Cached versus live table.** While the health job runs, the page shows a "Cached — checking..." table labelled `Profile health status (cached)`, built from the last persisted snapshots. The live table, labelled exactly `Profile health status`, replaces it when the job's result arrives. Only the live table counts: the probes match `table[aria-label="Profile health status"]` exactly and count its `tr.crosshook-health-dashboard-row` rows in the first `tbody` (expanded detail rows do not carry that class). The 500-profile fixture gives every profile a health snapshot, and a `bench_fixtures` test asserts it.
- **G5 `health_table`.** After `bench_begin` the probe opens the health page, waits for the live table (up to 60 s), sends `health_ready` and returns to the library. Each trial is one library to health switch: an untimed reset returns to the library if the health page is active, the probe focuses the health tab without activating it, the runner sends Enter, and the probe waits for the route content to show 300+ live rows. ### First-content supplemental

`--collect presentation` G1 and G2 also record when the app first showed content. Each row adds `first_content_ms`, and the summary row adds `first_content_p50_ms` and `first_content_p95_ms`.

- **Definition.** `first_content_ms` runs from launch (like `first_present_ms`) to the first toplevel frame the compositor presented at or after `READY`. `READY` is printed after the summary fetch and a double `requestAnimationFrame`, so the first frame presented at or after it is a frame that can show the content.
- **Upper bound.** It is a conservative upper bound, not a paint marker: a frame presented before `READY` may already show content, and the value can only overstate first-content-painted. `first_present_ms` stays as it was, and `first_content_ms` is never below it (`INVALID_PRESENT_CLOCK` otherwise).
- **`NO_CONTENT_FRAME`.** After `READY` the runner waits up to 2 s for such a frame. With none presented in that time the run fails with `NO_CONTENT_FRAME` (exit 1).
- **CSV mode.** G1 and G2 without `--collect presentation` leave all three `first_content` columns blank.
- **Schema.** G1 and G2 share the columns `iteration`, `ready_ms`, `first_present_ms`, `first_content_ms`, `p50_ms`, `p95_ms`, `first_present_p50_ms`, `first_present_p95_ms`, `first_content_p50_ms`, `first_content_p95_ms` and `status`. The summary row carries the percentiles.

| Native, 10 iterations  | 1038.1 / 1100.5      | 245.8 / 316.3                | 1046.3 / 1107.2              |

`first_content_ms` is about 8–12 ms after `READY` in both runs (p50 minus p50: 8.2 ms native, 12.4 ms Flatpak), which is consistent with the frame presented right after `READY`. ## External capture CSV schemas

Real G4/G5/G6/G8/G9 ingest raw observations from `--capture-csv` (one CSV per run; select only metrics whose required columns that CSV carries). Header must match; values must be finite and non-negative. G4/G5/G8/G9 can instead be produced by `--collect presentation`, which refuses `--capture-csv`.

| Metric | Required columns | Notes                                                                                                                                                                                                                                                                                                                                                                                                |
| ------ | ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| G4     | `frame_ms`       | Adds `over_interval_percent`: share of intervals over 1.5 refresh periods (`1.5 × 1000/--refresh-hz`), i.e. a missed vblank. Presented intervals land on whole refresh periods, so a one-period threshold would count every frame at 119.88 Hz.                                                                                                                                                      |
| G5     | `latency_ms`     | One row, `scenario` `external`: p50/p95/p99 and `measured`; `ambiguous`, `timeout` and `early` stay empty. Any `scenario` column is ignored.                                                                                                                                                                                                                                                         |
| G6     | `stall_ms`       | Counts `> 16 ms` and `> 50 ms`; `duration_s` from `--duration` (300 when only G6 is selected).                                                                                                                                                                                                                                                                                                       |

## Raw provenance recipe

Real G4/G5/G6/G8/G9 captures must come from a runner-written raw run directory, `<output>/raw/<run_id>/`, holding `provenance.json` and `SHA256SUMS` (see [Presentation collector](#presentation-collector)). `--capture-csv` rejects every other CSV with `STALE_CAPTURE`: a hand-made directory, a CSV copied elsewhere, a different commit, variant, environment or boot, a dirty tree or a run that did not end `captured`. G4/G5/G8/G9 are produced directly by `--collect presentation`; G6 has no producer yet, so **G6 cannot be captured for real yet**; only its dry-run schema fixture and the ingest path exist (G8's ingest path still needs an external `frame_ms` CSV). Do not assemble `provenance.json` or `SHA256SUMS` by hand to get past the check.

Evidence that still belongs beside any real run, in the run's output location and recorded rather than assumed: exact command line, stdout/stderr, tool versions, display mode and refresh rate, and the SHA-256 of every raw artifact. External tools are prerequisites, not runner dependencies; their availability varies by host.

- Screen recordings: `gpu-screen-recorder` where supported, or a compositor-aware tool. If transcoding or inspection is needed, use `ffmpeg` on the preserved original and keep both files; encoded output is not the timing source.
- Input events: `ydotool` can inject keystrokes and pointer events, but an injection timestamp alone is not a photon timestamp. Record events and presentation timestamps from a monotonic clock in the same clock domain, and correlate each injected scenario to the measured first presentation change before emitting G5 observations (the runner's [G5 driver](#g5-input-to-photon-driver) does this).
- G6 scheduler evidence, with the UI-thread identity mapping retained:

```sh
perf sched record -o "$OUT/perf.data" -- <isolated-app-command>
perf sched timehist -i "$OUT/perf.data" > "$OUT/stalls.timehist"
```

Limitations (honest scope of these tools):

- The [presentation collector](#presentation-collector) observes true presentation timestamps, and drives G4/G5/G8/G9 itself (see [G8 single-session driver](#g8-single-session-driver) for the G8 recipe). Outside it, leave `frame_ms`/`latency_ms` unproduced rather than approximating. An encoded fixed-rate stream (gpu-screen-recorder/ffmpeg at `-f N`) duplicates or drops frames on a fixed cadence: duplication counts can indicate dropped frames, but per-frame `frame_ms` **cannot** be derived from such a stream.
- Keystroke-to-photon (G5) requires correlating the input event timestamp with the first presentation change; the runner does this with its own uinput stamp and the shim's presented timestamp. Outside the runner, ydotool gives injection time only and encoded video adds an unknown pipeline latency. Measure by pairing input-event monotonic timestamps with per-frame presentation timestamps; encoded recordings only bound the latency, they do not measure it.
- `perf sched timehist` attributes scheduling delays; map stalls to the UI thread explicitly and record the mapping with the artifact.

## Persistence

Runtime-only test data in temp/isolated directories. No change to TOML settings keys, no SQLite schema change, nothing written to user stores (`~/.config/crosshook`, `~/.local/share/crosshook`, `~/.cache/crosshook`, `~/.var/app/dev.crosshook.CrossHook`). G5 toggle scenarios change only the isolated profile copy (a favorite, an optimization) and restore it after every iteration. The health scenarios change no profile and write no settings file. G4 `health`, like `library` and `settings`, deletes any leftover isolated `settings.toml` first; G5 `health_table` does not, and relies on the collector's removal like the other G5 scenarios. `first_content_ms` writes nothing beyond the metric CSV. The G4 `console` scenario and G8 write an isolated `settings.toml` (drawer expanded) and delete it when the metric finishes. Fixture trees, `results/` CSVs and `meta.json` are disposable artifacts; nothing here is user-editable state.
