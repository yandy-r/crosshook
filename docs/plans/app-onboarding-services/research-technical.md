## 3. Error text preservation versus service sanitization

- Onboarding/offline raw `e.to_string()` is not a single stable literal: SettingsStoreError directly forwards IO/TOML Display (`core/settings/store.rs:21-28`); ProfileStoreError includes `invalid profile name: {name}`, `profile file not found: {path}` and IO/TOML detail (`core/profile/toml_store/error.rs:21-51`); MetadataStoreError includes `failed to {action}: {source}`, `failed to {action} '{path}': {source}`, `metadata validation error: {msg}`, corruption/read-only variants (`core/metadata/models.rs:55-105`). Record any accepted sanitizing delta explicitly; raw TOML/SQL/path detail must not be newly embedded in AppError.
- Cache errors: `failed to parse cached host readiness snapshot: {error}`; `invalid cached host readiness snapshot critical_failures value: {n}`; `invalid cached host readiness snapshot warnings value: {n}` (`cmd/onboarding.rs:73-86`).
- Per-tool disabled error: `readiness nag dismissals require the SQLite metadata store; dismiss_umu_install_nag and dismiss_steam_deck_caveats remain available via settings.toml`; unknown id: `unknown readiness tool_id: {tool_id}. Use a tool id from the host readiness catalog.` (`cmd/onboarding.rs:29-37,308-313`).
- Offline exact literals: `metadata store unavailable`; `profile id not found for {name}`; hash-only `trainer path is empty`, `trainer file missing or unreadable` (`cmd/offline.rs:15-16,25,39-40,89-107`). Join errors are raw Tokio Display in all four async wrappers.
- Existing app health blocks in `run_blocking` and uses AppError's home-redaction. Join errors become `background task was cancelled` / `background task failed` (`app/error.rs:88-96`); profile-health/cache string errors are wrapped with Unavailable (`app/services/health/mod.rs:50-75`). Batch summary builder returns a summary even on profile-list trouble; worker failure is its only service-level error path.
- Dual-write warnings currently say `failed to persist SQLite readiness nag dismissal for umu_run after settings save` / corresponding `steam_deck_caveats` (`cmd/onboarding.rs:269-297`). **No warning on disabled DB today**, contrary to requested fallback warning.

## 4. Already in crosshook-app; do not reimplement

- Health is already a directory service, not an unmoved monolithic Tauri body. `HealthService {profiles,metadata}` + `new`, four async facades run work in `run_blocking`; no JobRegistry/EventBus fields (`app/services/health/mod.rs:21-77`). Thus AC1 non-caller-thread batch is already satisfied; **batch-as-job** is not (startup wraps it in a job, direct command does not).
- Batch uses `batch_check_health_with_enrich`, one SQLite connection, offline enrichment map, fallbacks to `batch_check_health`, metadata prefetch retained across fallback; persists per-profile health snapshots best-effort (`app/services/health/batch.rs:12-127`). `prefetch.rs:26-132` batches failure trends, last success, total launches, favorites, ids, launcher drift, sources, snapshots; adds live Steam IDs and cached dependency states/required verbs/active prefixes.
- 30-day constant already centralized: `FAILURE_TREND_WINDOW_DAYS=30` (`health/mod.rs:21`), used by batch `query_failure_trends` (`prefetch.rs:36-41`) and single `query_failure_trend_for_profile` (`single.rs:47-49`). Enrichment builds metadata, adds version-change warnings and dependency issues (`enrich.rs:8-143`).
- Live Steam manifest build-ID exists for single and grouped batch: discover roots/libraries, parse `appmanifest_{id}.acf`, take first nonempty build id; batch groups discovery by configured Steam client path (`health/steam.rs:9-93`). Existing `SteamService` is metadata/settings based (`services/steam/mod.rs:13-23`), not the owner of this health helper today; avoid unnecessary duplicate discovery abstraction.
- Display paths already use `presenter::display_path_tilde` from `health/types.rs:183-198`; Tauri shared helper is just a forwarding shim (`cmd/shared.rs:6-8`). Keep legacy `~/` presentation distinct from `sanitize_display_path`'s `$HOME` variant (`app/presenter/mod.rs:5-23,42-75`).
- Startup scans already left src-tauri: `app/bootstrap/scans.rs:38-50` schedules a `startup-scans` registry job plus independent umu/background jobs. Sequential health → offline notice → version removes historical staggering, with cancellation/failed scheduling terminal states (`:79-172`). Health does actual offline preflight/snapshot work only when metadata permits; offline step itself **only computes total_profiles**, not a fresh scan (`:116-137,174-193`). Version scan is toolkit-free `bootstrap/version_scan.rs:23-146`; currently profiles without metadata ids are skipped (`:97-103`), so disabled DB means zero comparisons.
- Generic AppEvent is the only app-bus startup completion: `StartupJobFinished{job}`; `StartupJobKind` = `HealthBatch|OfflineReadiness|VersionScan|UmuRefresh|BackgroundPortal` (snake_case on serialization). No `HealthScanCompleted`, `OfflineReadinessScanCompleted` or `VersionScanCompleted` variants exist (`app/events.rs:13-27,57-85`). `finish` writes state then publishes (`bootstrap/scans.rs:57-61`).
- Tauri bridge alone maps those jobs to legacy success events `profile-health-batch-complete`, `offline-readiness-scan-complete`, `version-scan-complete`, then `startup-job-finished {job,state}`; failure/skipped only generic terminal notification; Resync republishes retained terminal slots (`src-tauri/src/startup_bridge.rs:62-130,159-181`). - Existing supervised scan pattern to reuse: StorageService `start_scan_inner`, keyed JobSpec, result slot, async `scan` waits Finished and takes result; handles cancellation/abandonment, bounded wait (`app/services/storage/scan.rs:48-146`). Do not copy only the happy-path slot and leak abandoned results.

## 5. Construction and management

- `App::bootstrap` creates runtime/stores, then `Services::new(&stores,events,runtime,jobs)` **before** StartupHandle, then calls `scans::schedule` (`app/bootstrap/app_bootstrap.rs:93-155`). `Services` owns settings/ui_settings/recent_files/diagnostics/health/profiles/background/launch/storage/mods/collections/launcher_export/version/steam (`bootstrap/stores.rs:50-79`). Extra process/install registries remain `:61-66`. No onboarding/host-tools/startup-scans service states exist. - Startup metadata reconciliation already syncs TOML nag timestamps to SQLite (`bootstrap/reconcile.rs:89-103`), but uses **36500** days versus commands' **3650**; keep/resolve this intentional existing distinction explicitly. Disabled/read-only store skips reconcile/nag writes (`bootstrap/app_bootstrap.rs:252-286`).

## 6. Fake host-probe seam

- Core `check_system_readiness()` is plain struct-returning: Steam roots/Proton discovery, umu resolution, Flatpak and Steam Deck detection (`core/onboarding/readiness/system.rs:27-54`). `evaluate_checks_inner(roots,proton_tools,umu_path,is_flatpak,is_steam_deck)` is a useful pure-input seam but `pub(super)` and still reads fixture compatdata directories (`:56`).
- `check_generalized_readiness(&ReadinessCatalog)` invokes live system readiness, distro detection, Flatpak and `evaluate_host_tool_checks`; the latter directly calls global `platform::host_command_exists` (`core/onboarding/readiness/host_tools.rs:9-26,71-84`). Catalog injection alone is **not** fake-host injection.
- `probe_host_tool_details` uses process-global OnceLock catalog (`core/onboarding/catalog.rs:216-225`), resolves via umu/host `which`, then gateway-backed process probing (`details.rs:57-100,158-202`). It returns unavailable details on unknown/missing/timeout/parse failure, never Result. Existing version probe has 1500 ms deadline/16 KiB output cap; its internal polling `thread::sleep` (`:173`) is not a startup scheduling sleep.
- No injectable command-runner trait exists. Gateway internal `host_command_with(program,flatpak)` / `host_std_command_with` accept explicit mode (`core/platform/gateway.rs:125,337`), and `is_flatpak_with` is internal (`platform/detect.rs:100`); preserve gateway execution, never replace with direct host-tool Command.
- Recommended smallest **service** test seam: injected readiness/details probe interface returning the existing core DTOs; production implementation delegates core APIs, fake returns deterministic checks, availability and paths. Run all calls inside the service job's blocking closure. If testing individual core tool decisions is required, add a narrow command-existence/input seam around `evaluate_host_tool_checks`, not global PATH mutation. No need to move all gateway code.
- Platform reuse: `platform::is_steam_deck` already has source-input evaluator (`platform/steam_deck.rs:34-41`); gamescope helper currently lives/reexports under **launch**, not platform (`launch/request/models.rs:13`). HostToolsService should reuse actual helper or deliberately relocate/reexport once, not duplicate env logic.
