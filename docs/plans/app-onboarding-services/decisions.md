# YAN-831 orchestrator decisions

These decisions bind the implementation of M1-33, which moves the health, startup scan, onboarding, readiness and host-tools services into `crosshook-app`. Where there is a choice, each one favours security, data integrity, UX and stability. Paths are relative to `src/crosshook-native/`. Research is in `research-technical.md`, `research-invariants.md` and `research-tests.md`.

| #   | Decision                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                | Why                                                                                                                                    |
| --- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| D1  | Two new service directories, `services/onboarding/` and `services/host_tools/`, plus `services/offline/` for the five offline commands. They follow the existing service shape: a `#[derive(Clone)]` struct, `async` public methods, blocking work on the blocking pool, `AppError` as the only error type, and files of about 500 lines or less. The existing `services/health/` service is extended rather than rewritten.                                                                                                                                                                                                                                                                                                                                            | Matches #533, #535 and #540, and avoids a second convention.                                                                           |
| D2  | **Jobs.** A single shared helper, `services::run_job(jobs, spec, work)`, runs `work` on the blocking pool inside a `JobRegistry` job, returns the closure's value, and reaps the job. If the job or the app is cancelled, the call returns `Cancelled`. `HealthService::batch_summary`, `OnboardingService::{check_readiness, check_generalized_readiness, capabilities}` and `HostToolsService::tool_details` all run through it. The job kinds are `health-batch`, `host-readiness` and `host-tool-details`. **Jobs have no exclusive key**: the startup health scan overlaps the UI's `batch_validate_profiles`, and `useHostReadiness` and `useOnboarding` both call `check_generalized_readiness`, so a key would surface as a user-visible `Conflict` regression. | AC1 ("as a job" / "as async jobs") puts the work off the caller thread and under app-shutdown cancellation, without new failure modes. |
| D3  | **Wiring.** `Services::new(&Stores, EventBus, Handle, JobRegistry)` gains `onboarding`, `host_tools` and `offline`, and `health` receives the job registry. `src-tauri/src/lib.rs` manages each one. The Tauri commands become thin `async` delegates.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  | The same wiring pattern as D2 of YAN-847.                                                                                              |
| D4  | **Host probe seam.** A `HostProbe` trait (`Send + Sync`) lives in `services/host_tools/probe.rs`. It has `system_readiness()`, `generalized_readiness()` and `tool_details(tool_id)`, all returning existing core DTOs. `CoreHostProbe` delegates to the existing core functions and so to the host gateway. No new host spawns are added. Services hold an `Arc<dyn HostProbe>`; `new(..)` uses `CoreHostProbe`, and `with_probe(..)` is the test constructor.                                                                                                                                                                                                                                                                                                         | AC2 calls for "readiness with a fake host probe", and the `flatpak-spawn` gateway stays the only host path.                            |
| D5  | **Dual write.** A single function, `OnboardingService::dismiss_legacy_nag(LegacyNag::{UmuInstall, SteamDeckCaveats})`, writes the TOML timestamp first, and a TOML error fails the call. It then calls the best-effort SQLite `dismiss_readiness_nag(<id>, 3650)`: a DB error only logs a warning and the call still succeeds. When the DB is disabled, it now logs a warning and writes TOML only. `dismiss_readiness_nag(tool_id, ttl)` stays SQLite-only. It checks DB availability before the catalog check, returns the exact legacy error text, and clamps `ttl_days` to at most 3650.                                                                                                                                                                            | AC2 test, issue persistence rules, and the existing UI contract.                                                                       |
| D6  | **Snapshot ordering.** One blocking closure runs the probe, writes the raw `host_readiness_snapshots` row (when the DB is available), then applies the settings and SQLite dismissals, then sanitizes. A snapshot write failure still fails the call. Cached snapshot decode and tool-guidance dismissals are applied on read.                                                                                                                                                                                                                                                                                                                                                                                                                                          | Keeps today's ordering and data.                                                                                                       |
| D7  | **Display paths.** The `checks[].path`, `resolved_path` and capability tool checks keep the exact current output of `sanitize_display_path` from `src-tauri/src/commands/shared.rs`. The service uses the equivalent `crate::presenter` function, and that equivalence is verified before the switch. If the outputs differ, the existing function moves into `presenter` unchanged.                                                                                                                                                                                                                                                                                                                                                                                    | IPC output stays byte-identical.                                                                                                       |
| D8  | **Error text.** Legacy user-visible strings are kept through `AppError::new(kind, "<legacy text>")`, and adapters map them with `error.message().to_string()`. These include `readiness nag dismissals require the SQLite metadata store; …`, the unknown tool id message, `metadata store unavailable`, `profile id not found for {name}`, `trainer path is empty` and `trainer file missing or unreadable`. Raw store `Display` errors become the sanitized fixed `AppError` texts.                                                                                                                                                                                                                                                                                   | Same policy as D8 of YAN-847.                                                                                                          |
| D9  | **Startup scans.** The health, offline-readiness and version scan sequence moves from `bootstrap/scans.rs` into `services/startup_scans.rs` (`StartupScansService`), and bootstrap only schedules it. Three named `AppEvent` variants are added: `HealthScanCompleted { summary counts }`, `OfflineReadinessScanCompleted { total_profiles }` and `VersionScanCompleted { summary }`. Each is published right after the matching `StartupJobFinished`, and only on success. The state-then-publish order is kept. `startup_bridge` keeps emitting the legacy Tauri events from `StartupJobFinished` and ignores the new variants, so nothing is emitted twice. Tests subscribe to the bus and use no sleeps.                                                            | AC3 and the issue's named events. The native UI consumes typed events, and Classic stays unchanged.                                    |
| D10 | **Offline.** The five offline commands move into `OfflineService` with their behaviour preserved, including `metadata store unavailable` when the DB is disabled. A connection-free offline preflight is out of scope and filed as a follow-up. `check_network_status` and `get_trainer_type_catalog` move as well.                                                                                                                                                                                                                                                                                                                                                                                                                                                     | The issue lists `offline.rs` as source to move, and changing the disabled-DB semantics is not in its AC.                               |
| D11 | **Host tools.** `check_gamescope_session` and `launch_platform_status` delegate to `HostToolsService`, which reuses `crosshook_core::launch::is_inside_gamescope_session`, `platform::is_steam_deck` and `launch_platform_capabilities`. Both run off the caller thread, because `unshare --net` is probed once. `check_game_running` stays in launch, since it is not in scope.                                                                                                                                                                                                                                                                                                                                                                                        | Issue scope; `unshare` spawns a host process.                                                                                          |
| D12 | **IPC frozen.** Command names, camelCase argument keys (`toolId`, `ttlDays`, `name`) and serde shapes stay byte-identical. `check-mock-coverage.sh` and the command-name pin tests must pass. React mocks are unchanged.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                | AC4 smoke tests.                                                                                                                       |
| D13 | **Tests are limited to the AC.** They cover: the enrichment window and trend, with launches inside and outside 30 days through the existing metadata API; auto-load resolution, which already exists and is cited; the dual write with the DB enabled and disabled plus a SQLite failure where feasible; readiness with a fake probe, covering snapshot ordering and dismissal overlay; a non-blocking gated test for readiness and batch; and the bus events.                                                                                                                                                                                                                                                                                                          | Critical tests only.                                                                                                                   |
| D14 | **Follow-ups, not fixed here:** offline readiness with the DB disabled; `verify_trainer_hash` reading the whole file into memory; the gaps in display-path aliasing; the manual Host Tools check inside Flatpak.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        | Keeps the refactor behaviour-preserving.                                                                                               |
