## 1. Prior art in `crosshook-app`

### 1.1 "Yields while blocking pool is gated" (AC1 evidence pattern)

Two verbatim copies exist; copy one:

- `app/src/services/steam/tests/proton.rs:67-108` (`proton_scan_yields_while_blocking_pool_is_gated`)
- `app/src/services/launcher_export/tests/export.rs:48-99` (`export_yields_while_blocking_pool_is_gated`)

Recipe (plain `#[test]`, no `#[tokio::test]`):

1. Build `Builder::new_current_thread().enable_all().max_blocking_threads(1)`.
2. `runtime.spawn_blocking` a gate closure that sends `entered_tx`, then blocks on `release_rx.recv()`. Wait on `entered_rx.recv()`, so the only blocking thread is now occupied.
3. Spawn a std watchdog thread: `done_rx.recv_timeout(5s)`; on timeout it releases the gate, so a regression fails instead of hanging. No sleeps and no runtime timers.
4. In `runtime.block_on`: `tokio::spawn(service.op())`, `tokio::task::yield_now().await`, then `let queued = !task.is_finished()`. The task can only be unfinished if its work was queued behind the gate on the blocking pool. Release the gate, `done_tx.send(())`, `gate.await`, await the task, then `assert!(queued, "... ran synchronously on the caller thread")`.
5. After `block_on`, `watchdog.join()`.

Each test is about 45 lines, and the gate boilerplate is duplicated, not shared. The app crate has no shared "gated" helper (`grep gated` finds only these two). **Recommendation:** add one `pub(crate)` `#[cfg(test)]` helper (for example `services::test_support::assert_yields_while_gated(|| async move { ... })`) used by the new tests, instead of a third and fourth pasted copy. Migrating the old two copies is optional.

The same gate technique covers `HealthService::batch_summary` (AC1), `check_readiness`, `check_generalized_readiness` and the host-tool probe. For the probe, the closure that blocks must be the real work. A fake probe that returns instantly still proves the call was queued on the pool.

### 1.3 Startup scan events (AC3)

- `app/tests/bootstrap_report.rs:229-312` (`jobs_finish_with_events_and_late_snapshot_keeps_results`): subscribes with `app.subscribe()` before the first await. This works because the current-thread runtime has not polled the spawned jobs yet. It awaits `startup.wait_finished(kind)` (`bootstrap/state.rs:126-129`, a watch channel, no sleeps) for all five kinds. It then reads exactly 4 `AppEvent::StartupJobFinished { job }` events (the umu skip fires inline in bootstrap before any subscriber). For each event it checks state-then-publish: `startup.snapshot()` already holds a terminal state. A late snapshot keeps the results. Also `:444 wait_finished_after_completion_returns_immediately`.
- `grep sleep` over `crosshook-app`: the only sleeps are in unrelated tests (`log_tail`, `launch/tests/cascade.rs` and `gamescope.rs`, `process/tests.rs`, `background/tests.rs:187`, `app/tests.rs:162`). None are in bootstrap or startup tests. The documented rule is "no startup sleeps" (AGENTS.md startup contract; README `StartupHandle::wait_finished`). `scripts/check-startup-path.sh` rejects `sleep`, `sleep_until` and `Duration::from_millis` in non-test startup code. It scans the whole of `crosshook-core`, `crosshook-app`, `crosshook-cli` and `src-tauri`, with `#[cfg(test)]` blocks and test paths exempted only for the BaseDirs rule (`:55-99`). **So a new `startup_scans.rs` must not contain `sleep` or `Duration::from_millis`, even in a test module outside `tests/`.** Use `start_paused` or channels instead.
- Current scan implementation: `bootstrap/scans.rs:79-175` runs health → offline-readiness notice → version scan in one `startup-scans` job. `AppEvent` (`app/src/events.rs:60-85`) has only `Resync`, `StartupJobFinished`, `ProfilesChanged` and `UiSettingsPersistFailed`. The issue names `HealthScanCompleted`, `OfflineReadinessScanCompleted` and `VersionScanCompleted`, which **do not exist as `AppEvent` variants**. The legacy Tauri event names are produced by `tauri/src/startup_bridge.rs:92-94` (`profile-health-batch-complete`, `version-scan-complete`, ...). Tests for the bridge are in `tauri/src/startup_bridge/tests.rs:21,102,148,161,183,191,202`. If the new events are added to `AppEvent`, the bridge tests, the `events.rs` doc/serde pins, and the React event listeners all need matching updates.
- `tauri/src/commands/startup/tests.rs` and `startup_bridge/tests.rs` pin JSON payload shapes. `app/src/bootstrap/report/tests.rs:13-77,269-291` pins the report JSON byte for byte.
- Auto-load profile resolution (AC2) already has unit tests: `app/src/bootstrap/reconcile/tests.rs:19-141` (disabled, valid, missing, blank, and store-variant parity) plus the live-recompute integration test `tests/bootstrap_report.rs:195-227`. If `resolve_auto_load_profile` moves or is re-exported into the new service, port or re-point these tests. They do not need rewriting.
