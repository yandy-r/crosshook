**`ProtonInstallRegistry`** (:30-63): `Mutex<HashMap<String, CancellationToken>>`, `register(op_id, token)`, `cancel(op_id) -> bool` (removes + cancels), `remove(op_id)`. **Install flow today (`protonup_install_version_async`)**:

1. `include_prereleases` from settings; `list_available_versions_by_id(meta, false, request.provider, include)`.
2. Find `v.version == request.version && v.provider == request.provider` in catalog → else `Err("requested version '..' for provider '..' was not found in the server catalog")` (**AC1**).
3. Compare caller-supplied `version: ProtonUpAvailableVersion` to the catalog entry: provider/version mismatch → `Err("install request/version mismatch with server catalog identity")`; `download_url`/`checksum_url`/`checksum_kind` mismatch → `Err("install metadata did not match server-resolved catalog entry")` (**AC2, AC3** — whole-string `Option<String>` equality, so host AND path differences are rejected). Note: the _catalog_ entry (`resolved_version`) is what gets installed, not the caller's.
4. `op_id = Uuid::new_v4()`; `(emitter, rx) = ProgressEmitter::new(&op_id)`; `CancellationToken::new()`; `registry.register`.
5. `tokio::spawn` pump: `while let Ok(p) = rx.recv().await { app.emit("protonup:install:progress", &p) }` (stops on Closed; a `Lagged` error ALSO ends the loop — latent bug: `while let Ok` exits on first lag).
6. `tokio::spawn` install: `install_version_with_progress(&request,&resolved,Some(emitter),Some(cancel)).await` → result ignored (`_result`); `registry.remove(op_id)`. So the terminal outcome reaches the UI **only** via the final `Phase::{Done,Failed,Cancelled}` progress event.
7. Returns `ProtonInstallHandle{op_id}` immediately.

Frontend contract: `src/hooks/useProtonInstallProgress.ts` listens for Tauri event **`protonup:install:progress`**, payload `ProtonInstallProgress{op_id, phase (kebab-case: resolving|downloading|verifying|extracting|finalizing|done|failed|cancelled), bytes_done, bytes_total?, message?}`, filters by `payload.op_id === opId`, drops unknown phases. `useProtonManager.ts:260` expects `protonup_cancel_install{opId}` → `boolean` and deliberately relies on the Rust task emitting `Phase::Cancelled` after cancel (does not remove opId itself). **Both wire shapes must be preserved** (no frontend change is required by the ticket).

### Owner / caller identity: NOT modeled

`JobId` is the only credential ("Only the caller that started a job (or one it handed the id to) can address it", types.rs:35-37; plan `docs/plans/job-registry/plan.md:21`: unguessable UUID = ownership check; `cancel` of an unknown/foreign/reaped id is `NotFound` and touches nothing else). There is no `owner`/`caller`/webview field anywhere in the registry; `grep -i owner` in `A/jobs/*.rs` finds only doc comments + test `cancel_is_scoped_to_the_owning_job` (tests.rs:311). Consequence for **AC4 ("cancel with an op_id the caller does not own is rejected")**:

- `JobRegistry::cancel(&JobId)` alone cannot tell _which_ caller started the job; any caller holding a valid id cancels it. Today's `ProtonInstallRegistry` has the same property (op_id = capability) but also masks absence as `false`.
- Recommended model (smallest correct): `ProtonUpService` keeps a **service-level ownership table** `Arc<Mutex<HashMap<JobId, InstallOwner>>>` where `InstallOwner` is an opaque caller token (see "Owner token" in (g)). `cancel_install(owner, op_id)` rejects with `AppErrorKind::NotFound` (same as unknown id — don't leak existence) or `Validation{field:"op_id"}` when `table[op_id] != owner`, only then calls `jobs.cancel(&id)`. Do NOT change `JobRegistry` semantics for other services. The owner token must come from the IPC layer: Tauri command has no session concept yet → cheapest real identity is the **webview label** (`tauri::Webview<R>`/`Window::label()`; `tauri.conf.json` window label `"main"`, one window). Caller-supplied strings are not trustworthy; derive it in the Tauri command (`webview.label().to_string()`), the command signature gains a Tauri-injected `webview: tauri::Webview` arg (injected param, **not** part of the JS invoke args, so frontend/mocks are unchanged). Alternative if main wants no Tauri-API in commands: owner = `ProtonUpInstallOwner(String)` created from a UUID stored in a managed `ProtonUpCallerId` at setup — but then every caller shares one id and the check is vacuous, so the webview label is better. **Decision for Main to confirm**: I recommend webview label + service-level table; document that single-window Classic makes AC4's positive path trivially true and test with two distinct owner tokens at service level.
- Existing semantic `cancel → bool`: keep IPC return `bool` (`Ok(true)` = cancelled; `Ok(false)` = op already finished/unknown to this owner **or** reject?). AC4 says "rejected": map foreign-owner to `Err(...)` (command returns `Err(String)`), unknown/finished to `Ok(false)` to keep UI behaviour (frontend calls `callCommand<boolean>`; a rejected promise on stale op_id would be a regression only for the foreign case, which UI never hits).

### Progress publication

- `JobContext::progress(JobProgress{current,total,message})` publishes `JobEventKind::Progress` on the per-job `broadcast` (cap 256, lag → `Dropped{n}`; `Finished` always delivered last). `AppEvent` / `EventBus` (`A/events.rs`) is a **separate app-wide** bus (`StartupJobFinished`, `ProfilesChanged`, `HealthScanCompleted`, …, `#[non_exhaustive]`); job events do NOT go through it; there is no generic job→Tauri bridge today (grep: only `startup_bridge.rs` bridges AppEvent; no src-tauri code touches `JobHandle/JobEvents`).
- Wire format needed: `protonup:install:progress` with `ProtonInstallProgress{op_id, phase, bytes_done, bytes_total, message}`. `JobProgress` only has `{current,total,message}` — **lossy** (no `phase`). Options:
  1. **Recommended**: service converts core `ProtonInstallProgress` → job events: `ctx.progress(JobProgress{current: bytes_done, total: bytes_total, message: Some(phase_tag)})` isn't lossless. Better: keep core `ProgressEmitter` as the producer and have the service return a typed stream. Concretely `ProtonUpService::start_install(...) -> Result<ProtonInstallStart, AppError>` where
     `pub struct ProtonInstallStart { pub op_id: String, pub progress: tokio::sync::broadcast::Receiver<ProtonInstallProgress> /* or a small ProtonInstallProgressStream */ }`.
     The job closure owns the `ProgressEmitter` (op_id = `ctx.id().to_string()`), runs `install_version_with_progress(&req,&ver,Some(emitter),Some(ctx.cancel_token().clone()))`, and ALSO mirrors a coarse `JobProgress{current: bytes_done, total: bytes_total, message: Some(phase.to_string())}` into `ctx.progress` for registry observers. Tauri command spawns the pump (`while let Ok|Lagged → continue` — fix the existing `while let Ok` lag bug; `app.emit("protonup:install:progress", &p)`). This keeps the exact wire payload and keeps `tauri` out of crosshook-app.
  2. Lossless via JobProgress: encode `phase` in `message` ("downloading") and parse back — brittle; rejected.
- Terminal state: job outcome. `install_version_with_progress` returns `Result<ProtonUpInstallResult, InstallError>`; map to `Outcome`: `Ok(result)` where `result.success` → `Succeeded`; `Err(InstallError::Cancelled)` → `Cancelled`; other `Err` → `Failed(AppError)`. Core already emits terminal `Phase::Done/Failed/Cancelled` through the emitter before returning (orchestrator.rs: `emit(em, Phase::Done)`, `fail_with_cleanup_message`, `cancel_with_cleanup`), so the UI terminal event is preserved without extra emits. Exception: failures _before_ the first `emit` of a terminal phase never occur (all `?`-early returns in `install_version_with_progress` happen after `emit(Resolving)` but **before** any terminal emit for: `resolve_checksum_kind`, `resolve_target_root`, `validate_install_destination`, missing `download_url`, `validate_release_url`, `validate_archive_filename`, `AlreadyInstalled` — these return `Err` with NO `Failed` phase!). Today's command swallows `_result`, so the UI would hang at "resolving" for those. The service SHOULD fix this by emitting a final `Phase::Failed` (via `emitter.emit(Phase::Failed,0,None,Some(msg))`) when the job returns `Err` and the last emitted phase wasn't terminal (track with a flag) — small behaviour improvement, flag to Main as optional.
- Results for non-job callers: the sync `protonup_install_version` command (no progress) maps to `install_blocking(...)` → `run_job`-style or plain `await` (see (g)).

### How YAN-835 community sync and others use the registry (shape to copy)

- `StorageService` (`A/services/storage/scan.rs`): exclusive `JobKey::new(STORAGE_SCAN_JOB_KEY)`, `ctx.progress(JobProgress{..})` inside `scan`, same take-once result slot pattern, 300 s timeout.
- `HealthService`/`HostToolsService`/`OnboardingService`: `run_job(&self.jobs, JobSpec::new("host-tool-details"), move || {blocking})` (`A/services/mod.rs:89`: runs blocking work in `spawn_blocking`, waits to `Finished`, reaps, returns value; no progress, no id exposed). `LaunchService` does NOT use JobRegistry (only `create_log_path_in`). So there is no existing "start job, return id to caller, later cancel by id" API shape except community `start_sync()` returning `JobHandle`; protonup install needs exactly that (return `op_id` immediately, job continues detached): **do not `reap` in a waiter** — a background task (or the job closure's own tail) must subscribe to events and `reap` after `Finished` to avoid retention pressure (retention cap 64 evicts oldest, so reaping is optional but `outcome()` queries would otherwise accumulate; storage/community comment says registry evicts).
- Dropping `JobHandle` does not cancel (cancel is explicit token). A `JobHandle` drop also drops its receiver; the job keeps running. Safe for fire-and-forget.
- Exclusivity: `JobKey` per install target would give Conflict on double-click: recommend `JobKey::new(format!("protonup-install:{provider}:{version}"))`? Current code has NO exclusion (two concurrent installs of same version race on `.tmp.<archive>` file). Adding a key is a behaviour change (returns `Conflict` error); memory note (YAN-831): "Don't give UI-triggered jobs exclusive JobKeys when several hooks call the same command". Install is a user-initiated single action → key by `(target_root,version)` is reasonable, but leave **optional**; recommend adding because the temp-file collision is a real bug. Decision for Main.

### Progress — `progress.rs`

`Phase` (kebab-case serde: Resolving, Downloading, Verifying, Extracting, Finalizing, Done, Failed, Cancelled); `ProtonInstallProgress{op_id: String, phase, bytes_done: u64, bytes_total: Option<u64>, message: Option<String>}` (Serialize+Deserialize+Clone+Debug); `ProgressEmitter{op_id, tx: broadcast::Sender}`: `new(op_id: impl Into<String>) -> (Self, broadcast::Receiver<ProtonInstallProgress>)` (buffer 64, lossy; lagged receivers get `RecvError::Lagged`), `subscribe()`, `op_id()`, `emit(phase, bytes_done, bytes_total, message)` (ignores no-receiver). Emitter is dropped when `install_version_with_progress` returns (it's moved in as `Option<ProgressEmitter>`; orchestrator holds `emitter.as_ref()`), which closes the channel after the terminal phase → receiver `Closed` ends the pump loop. Service must therefore give the **job the emitter** and the Tauri pump the receiver. `op_id` for emitter MUST equal `JobId` string (`ctx.id().as_str()`); since the emitter is built inside `jobs.start`'s closure (needs `ctx.id()`), but the receiver is needed by the caller → use a oneshot/`Arc<OnceLock>`… simpler: **create the emitter/receiver after `start` returns?** No (job already running). Use: pre-create `JobId`? `JobId::new_v4` is `pub(crate)` (accessible inside crosshook-app) but `start` generates its own id. **Cleanest**: create `ProgressEmitter::new("")`? op*id is fixed at construction. → Solution: inside job closure build `(emitter, rx)` with `ctx.id()` and send `rx` back through a `tokio::sync::oneshot` the service awaits right after `start` returns (the closure executes on the runtime; first action before any `.await` heavy work). `start` returns the handle synchronously, the closure runs async; awaiting the oneshot is a short wait. Alternative (no round trip): derive progress stream from the \_job's own event channel* — `handle.into_events()` and map `JobEventKind::Progress` → needs lossless phase → not possible with `JobProgress` (see (b)). → Use oneshot approach or extend `JobProgress`? (don't). Another alternative: service pre-generates `op_id = Uuid::new_v4().to_string()`, builds `(emitter, rx)` BEFORE `start`, stores `op_id → JobId` mapping in the owner table after `start` returns; the IPC-visible `op_id` is then the **emitter op_id**, not `JobId`. Cancel looks up `op_id → (owner, JobId)`. This is simplest, wire-compatible (op*id still a UUID string), avoids round-trip, but means two ids (op_id and JobId). **Recommended** unless Main prefers op_id ≡ JobId; the table is needed anyway for owner checks. Note `JobId::from_string(op_id)` for a foreign string then simply isn't in the table → rejected before touching the registry (strengthens AC4: even a \_valid JobId of another job kind* (e.g. a storage scan id) cannot be cancelled through `protonup_cancel_install`; with op_id ≡ JobId and no table check, `jobs.cancel` would happily cancel ANY job incl. storage scan — **must gate on the table**).

`start_install` algorithm: (1) load `include_prereleases` (`run_blocking(settings.load)`; Err→false); (2) `catalog = source.versions(&request.provider, false, include)`; (3) `verify_against_catalog`: if `catalog.versions.is_empty() && catalog.cache.offline` → `Unavailable` "catalog unavailable"; find entry by `(version, provider)` else `NotFound`/`Validation{field:"version"}` (**AC1**, kind to choose; existing message "requested version '{v}' for provider '{p}' was not found in the server catalog" — paths/versions are non-sensitive); compare provider+version (`Validation{field:"version"}`), then `download_url`, `checksum_url`, `checksum_kind` with `Option<String>` `==` → mismatch `Validation{field:"download_url" | "checksum_url" | "checksum_kind"}` with the existing fixed message "install metadata did not match server-resolved catalog entry" (**AC2/AC3**; tests must cover host swap, path swap, query/fragment tweak, scheme swap, and `None`↔`Some`, and checksum*url + checksum_kind each independently); (4) pre-generate `op_id` + `ProgressEmitter::new(&op_id)`; (5) `jobs.start(JobSpec::new(PROTONUP_INSTALL_JOB_KIND) [.with_key(...)], move |ctx| async move { …installer.install(&req,&server_version,Some(emitter),Some(ctx.cancel_token().clone())).await → Outcome; mirror progress via ctx.progress })`; (6) insert `op_id → (owner, job_id)`; spawn a tiny reaper that subscribes to the job's events, on `Finished` removes the entry and `jobs.reap`; (7) return `ProtonInstallStart`. The **server-resolved** entry is installed (not the caller's), preserving today's behaviour. Order matters: insert owner entry \_before* the job can finish (take the table lock around `start`+insert, or insert immediately after with the reaper handling a missing entry) to avoid the finished-before-registered leak.

### Risks / decisions to flag to Main

1. **Owner identity (AC4)** — registry has none; recommend service-level table + Tauri webview label (injected `tauri::Webview` param, not a JS arg). Foreign-owner → `Err` (NotFound-like to avoid existence oracle); unknown/finished → `Ok(false)`.
2. **Progress wire fidelity** — `JobProgress` lacks `phase`; keep core `ProgressEmitter` → broadcast receiver returned in `ProtonInstallStart`; Tauri pump stays in src-tauri (fix `while let Ok` lag-termination → continue on `Lagged`). Optionally mirror coarse progress to `ctx.progress`.
3. **Early-`Err` installs never emit a terminal `Phase`** (orchestrator returns `Err` before terminal emit for bad dest/url/etc. and for `AlreadyInstalled`) — today UI would hang because the command ignores `_result`; service should emit `Phase::Failed` when the job ends `Err` w/o terminal phase (small improvement; confirm acceptable).
4. **No HTTP seams in core** (client `OnceCell`, hard-coded GitHub URLs, `reqwest::Client::new()` in install, `cfg(test)`-only localhost allowance) → introduce `ProtonCatalogSource`/`ProtonInstaller`/`UmuRefresher` seams in the app (zero core change) and seed `proton_release_catalog` rows for cache-hit tests.
5. **`HOME`-dependent core path resolution** (`resolve_install_root_candidates`, `plan_uninstall` read `HOME`; `resolve_candidates_with` is `pub(crate)`) → security tests need an env lock/`EnvGuard`; alternative small additive core `pub` fns.
6. **Error leakage**: `ProtonUninstall*Response.error_message` and `refresh_umu_database` error currently carry raw paths/URLs; route through `presenter::sanitize_message` (IPC string change is intentional hardening; shape unchanged).
7. **Install exclusivity** (`JobKey`) — optional; protects `.tmp.<archive>` collision; changes behaviour (Conflict).
8. `check_umu_coverage` and `protonup_resolve_install_roots` currently block the invoke/async thread with fs IO; service wraps in `run_blocking` (behaviour-preserving).
9. `A/error.rs` is shared by sibling agents; add `From<InstallError>`/`UninstallError`/`umu_database::Error` mappers (or private `map_*` fns in service modules) with minimal footprint — coordinate with whoever owns error.rs edits.
10. Bootstrap change is small but crosses the Services/`scans.rs` boundary: `schedule_umu` needs `&Services`; `UmuRefreshSummary` unchanged; keep the `CROSSHOOK_BENCH=1` skip option.
