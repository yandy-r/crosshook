# YAN-822 security research

Source inspection only; no builds, tests, network requests, or source edits. Paths below are relative to `src/crosshook-native/`. Proposed tests and service APIs are recommendations, not exercised verification.

A focused read-only `code-reviewer` independently confirmed the catalog/owner/root findings below: no demonstrated critical issue; one HIGH root-authority concern and one MEDIUM, exposure-dependent ownership gap. The generic in-process JobRegistry is not itself an IPC vulnerability. No code changes were made; the migration plan must address these service-boundary findings before shipping.

## Required invariants

1. Resolve the requested `(provider, version)` from the backend catalog before starting a job or touching the install destination. Download only the resolved entry, never the caller's DTO.
2. Async caller metadata must match that entry's provider, version, download URL, checksum URL and checksum kind exactly. A legacy install with no DTO still resolves the same catalog identity.
3. A cancellation request must be authorized by caller ownership, not only knowledge of an operation ID.
4. Uninstall must target one tool immediately below a resolved trusted install root; reject raw `..`, escaping symlinks, root itself and system paths before deletion. Execute rechecks rather than trusting an earlier UI plan.
5. All error/result/progress text crossing the service boundary is path-free; structured installed-path fields remain deliberate DTO data, not error text.

## 1. Catalog identity and core download trust

### What the commands do today

- `src-tauri/src/commands/protonup.rs:224-264`, `protonup_install_version_async`: calls `list_available_versions_by_id(..., false, request.provider, include_prereleases)` and finds an entry satisfying **both** `v.version == request.version` and `v.provider == request.provider` (`:242-252`). Missing entry is rejected before UUID, registry or task creation.
- `:254-256`: supplied `version.provider` and `version.version` must equal the resolved entry.
- `:258-262`: `download_url`, `checksum_url`, `checksum_kind` are `Option<String>` exact equality comparisons. A host change, path change, query change, `None`/`Some` change, or merely different URL spelling fails. No URL normalization, hostname-only comparison, or prefix comparison is involved. Keep exact equality: accepting the same host with another path would violate AC2.
- Not compared: `release_url`, `asset_size`, `published_at` (`crates/crosshook-core/src/protonup/mod.rs:48-68`). They are not client-controlled install inputs in practice because the task passes **`resolved_version`**, not `version`, into core (`commands/protonup.rs:290-294`). `asset_size` therefore also comes from the backend. Do not grow identity equality to presentation-only fields unnecessarily.
- `protonup_install_version`, `commands/protonup.rs:129-159`, accepts only `ProtonUpInstallRequest` (`provider`, `version`, `target_root`, `force`; core `protonup/mod.rs:88-96`). It resolves provider+version and calls core with the cloned catalog entry. It does **not** validate a client-supplied metadata identity because its IPC has no such DTO; this is not a direct-URL bypass. Its missing-version failure is a structured `DependencyMissing` result rather than async's `Err(String)`.
- Catalog integrity means backend-resolved **cache or upstream** data, not necessarily a fresh network fetch. Local SQLite cache is part of the trusted application state; caller assertions must not overwrite it.

### Pure service validation proposal

Use a small internal helper, e.g. `resolve_install_identity<'a>(request, supplied: Option<&ProtonUpAvailableVersion>, catalog: &'a [ProtonUpAvailableVersion]) -> Result<&'a ProtonUpAvailableVersion, IdentityError>`. Find by request provider+version, then compare supplied fields exactly when `Some`. Return the borrowed backend entry. Keep a tiny typed error (`MissingVersion`, `IdentityMismatch`, `MetadataMismatch`) mapped to fixed service messages/appropriate existing IPC envelopes. No HTTP, filesystem, settings, UUID or job allocation belongs in this helper.

Both service install paths must call it; legacy uses `None`, async uses `Some(&version)`. Only clone the resolved entry once when moving into the job. Tests should mutate one field at a time, assert the precise category, and prove no job/destination was created. A fresh-cache service test complements pure tests and catches accidental bypass in either entry point.

### Existing core host/checksum checks

- `crates/crosshook-core/src/protonup/install/orchestrator.rs:48-74`: resolves checksum kind and destination, obtains the backend `download_url`, calls `validate_release_url`, validates the archive basename, then creates `reqwest::Client::new()`.
- `install/validation.rs:100-146`, `validate_release_url`: parses URL; production requires HTTPS with host exactly one of `github.com`, `api.github.com`, `objects.githubusercontent.com`, `github-releases.githubusercontent.com`. It is a host allowlist, **not** a provider/repository/path allowlist. Test builds of **core** additionally accept HTTP loopback/localhost (`:126-129`). Hostnames that merely suffix/prefix an allowed hostname fail.
- `install/orchestrator.rs:309-352`: checksum sidecar/manifest URLs are independently passed through the same URL validation. `:228-251` derives checksum strategy from a registered provider first; only unknown providers use entry `checksum_kind`. Known catalog-only providers reject install. A client `checksum_kind=None` cannot disable a known provider's checksum because both identity validation and registry strategy remain.
- `install/download.rs:118-167`: SHA-512 sidecar parses a 128-hex hash; SHA-256 manifest selects the requested archive basename's 64-hex row. Actual SHA digests are compared in `orchestrator.rs:317-366`. This is distinct from AC3's **metadata identity** check; test checksum URL/kind mutations even without downloading bytes.
- Providers use fixed GitHub Releases endpoints (`providers/ge_proton.rs:9-10`; registry in `providers/mod.rs:93-109`); shared asset conversion copies `browser_download_url` from release assets (`providers/mod.rs:292-307`), rather than independently enforcing repository/path identity.
- Caveat: the reviewed download calls do not install a custom redirect policy or revalidate each/final redirect URL (`orchestrator.rs:74`; `download.rs:27-31,175-182`). The initial URL allowlist is not proof that all redirect hops are allowlisted. Preserve the current policy in this move; do not silently label it a comprehensive redirect sandbox or expand this ticket into transport redesign.

## 2. Cancellation ownership

### Existing model and gap

- Current `ProtonInstallRegistry` stores only `HashMap<String, CancellationToken>` (`commands/protonup.rs:25-62`). `cancel(op_id)` removes and cancels any matching entry without caller identity (`:42-54`); the command forwards it directly (`:305-309`).
- `crates/crosshook-app/src/jobs/types.rs:9-30`: `JobId` is an unguessable UUID-v4 bearer address, and `from_string` can wrap any received string. This models **possession**, not a caller/owner/session identity.
- `jobs/registry.rs:39-44` stores key, cancellation token and event sender; no owner. `cancel(&JobId)` (`:224-235`) cancels any known running job, treats retained finished jobs as success, otherwise returns fixed `NotFound`. `subscribe`/`outcome`/`reap` are similarly ID-addressed. `JobKey` is exclusivity, not authorization.
- `JobHandle::cancel` (`registry.rs:441-465`) is an in-process capability scoped to its job, but IPC cannot preserve that capability by merely serializing `id`. Current `app.emit("protonup:install:progress", ...)` broadcasts the `op_id` (`commands/protonup.rs:282-286`), so an observed op ID cannot be called private proof of ownership.

### Minimal service owner model

Keep one `JobRegistry` for lifecycle/tokens. Use the `JobId` string as `op_id` (no second UUID), plus a service-private ephemeral authorization map `JobId -> InstallOwner`. No second registry of cancellation tokens. Service install accepts a backend-established owner; service cancel takes the same owner and op ID, checks membership+owner equality, then invokes `jobs.cancel`. Do not wrap arbitrary caller input in `JobId` and directly cancel: that would also expose unrelated job kinds.

For unchanged React IPC (`useProtonManager.ts:239-260` sends only request/version or opId), the thin Tauri adapter can derive owner from the injected invoking webview/window label; never trust a JSON `owner` argument. A typed opaque owner/session value keeps the app crate toolkit-independent. Define the boundary explicitly: webview-label ownership isolates windows, **not** two components or JS contexts inside one window; if page-reload isolation is required, a backend-issued session capability is needed and the IPC contract must deliberately carry it. Do not claim an op_id-only API can distinguish those callers. The default desktop capability currently targets `main` (`src-tauri/capabilities/default.json:1-5`).

Reject foreign and unknown IDs with the same fixed `NotFound`/validation message (e.g. `"install operation was not found"`) to avoid revealing another owner's job. Same-owner active cancel is accepted; same-owner completed/missing preserves the documented false/no-op adapter semantics. Ownership registration and completion removal must be coordinated even for instantly finishing jobs, so no stale authorization entries leak. Remove owner entry on completion/cancel lifecycle and reap finished jobs. Service clones share authorization state; constructing/cloning a service must not accidentally generate a fresh owner on each command.

## 3. Uninstall containment

### What is protected already

- `crates/crosshook-core/src/protonup/uninstall.rs:102-120`, `plan_uninstall`: resolves roots using supplied configured Steam path, HOME and platform, then scans mappings.
- `:165-176`: canonicalizes target first and normalizes a file named case-insensitive `proton` to its containing tool directory (`:264-281`). Missing/unresolvable targets return `NotFound`.
- `:179-223`: rejects canonical paths under explicit system Steam roots and `/usr`, `/opt`, `/snap`, `/var/lib/flatpak/runtime`, then requires the canonical tool's **parent equal a candidate root** (component-wise `Path` comparison). This rejects unrelated directories, sibling-prefix paths, nested tool subdirectories, root itself, and final/intermediate symlinks whose final canonical target is outside all candidates.
- `:127-140`: `execute_uninstall_for_path` replans immediately before recursive deletion. Preserve that, rather than deserialize a client-created `UninstallPlan`. Public `execute_uninstall(UninstallPlan)` does not revalidate and the plan has public fields; keep it internal to the trusted flow.
- Install roots enumerate home native roots, optional `<configured path>/compatibilitytools.d`, and Flatpak Steam (`install_root.rs:82-138`), deduping canonical paths (`:163-179`). They may legitimately themselves be trusted Steam-root symlinks.

### Gaps relevant to AC5

- Raw `..` is not rejected by uninstall; canonicalization erases it. A traversal ending outside fails, but `root/Tool/../OtherTool` ending as another direct in-root child is accepted. The root resolver marks candidates with raw `..` invalid/unwritable (`install_root.rs:184-205`), yet uninstall's matching loop ignores `writable`/`reason`, canonicalizing those candidates anyway (`uninstall.rs:205-218`). This does not bypass OS permissions, and in-root `..` alone is not a containment escape, but it defeats strict traversal rejection. Reject invalid-path candidates independently of ordinary writability.
- Final-target-only canonicalization can accept an intermediate link that leaves root and later returns inside. Reuse `crosshook_core::fs_util::ensure_within_workspace` (`fs_util.rs:256-280,281-384`): it rejects original `..`, compares `OsStr` components without normalization, walks/checks every symlink prefix, and returns the resolved existing path. It accepts root itself, so retain uninstall's direct-child rule and core system denylist. Do not replace those with the weaker generic prefix check.
- For the existing `tool/proton` input contract, containment should validate the **original input first**, then core normalization may choose the parent; checking only a normalized/canonical path loses traversal evidence. Execute must perform the same check again.
- **HIGH root-authority concern:** a caller-chosen `steam_client_install_path` is itself used to mint an accepted root today (`commands/protonup.rs:317-329,345-357`; `install_root.rs:109-120`). A test must hold allowed candidates fixed and vary only `tool_path`; do not pass the malicious target's parent as the configured Steam root. Services must resolve configured roots from trusted application configuration/discovery, not treat arbitrary target-derived roots as authorization. A malicious root symlink can otherwise authorize deletion outside genuine Steam installations. This is not unrestricted arbitrary deletion: direct-child relationship, system denylist and filesystem permissions still apply. Preserve legitimate configurable Steam locations, but the current DTO field alone is not trusted configuration.
- `ensure_within_workspace` is a point-in-time check, not race-free filesystem deletion (`fs_util.rs:278-280`). Rechecking execution closes stale-plan reuse but cannot promise immunity to hostile concurrent parent replacement. No `openat2`/FD-relative deletion redesign is required by this move.

## 4. Archive extraction: current state only

`install/archive.rs:7-44,46-132,146-207` implements a single top-level directory policy; rejects invalid first components/root-level file/link entries and cross-wrapper entries; validates symlink/hardlink targets lexically remain under that wrapper; calls `tar::Entry::unpack_in(dest_dir)` and treats its `false` traversal-skip result as an error, not success. Archive peek uses the same wrapper policy (`:238-266`); GE additionally requires wrapper==version (`orchestrator.rs:389-401`). Existing tests cover escaping link entries, safe in-root symlinks, and traversal skip handling (`install/tests/archive.rs:104-204`). Preserve these paths and tests. The synchronous extraction loop does not observe cancellation mid-extract (`install/mod.rs:10-15`); no extractor rewrite is proposed here.

## 5. Error privacy

- Current uninstall command serializes `UninstallError::to_string()` (`commands/protonup.rs:331-339,358-366`); all path variants include raw path (`uninstall.rs:65-77`). Install `InvalidPath`/I/O/AlreadyInstalled messages also contain paths (`install/validation.rs:43-79`; `install/errors.rs:32-35,67-72`); failure progress falls back to `error.to_string()` (`orchestrator.rs:437-445`). Sanitize **progress as well as return errors**.
- `AppError::new` uses presenter sanitization (`crates/crosshook-app/src/error.rs:27-41`), but presenter only redacts HOME and generic home users (`presenter/mod.rs:25-39`). `/tmp`, `/mnt`, `/run/media`, arbitrary configured paths and URL path components are not generally erased. Therefore `AppError::new(..., core_error.to_string())` is insufficient.
- Map typed errors to fixed messages (`Validation { field: "tool_path" }`, `NotFound`, `Io`, `Unavailable`, `Cancelled` as appropriate); log underlying details only on the backend. Use a fixed progress failure line and retain phase/op_id/byte counts. Missing-version messages should not echo arbitrary request strings if a strict path-free error requirement applies. Preserve the structured result fields/envelope the UI needs, but replace `error_message` text with fixed policy strings.

## 6. Offline fake-catalog approach

No catalog trait/injected HTTP fetcher is needed for AC1–3 service tests. Public `MetadataStore::open_in_memory()` (`metadata/store.rs:57-65`) applies migrations; public `ProtonCatalogRow` is exported (`metadata/mod.rs:151`) and `put_proton_catalog`/`replace_proton_catalog` are public (`metadata/catalog_ops.rs:57-88`). Follow the existing row fixture in `protonup/catalog/tests.rs:49-92`.

Seed a **nonempty**, fully deserializable `ProtonUpAvailableVersion` JSON payload under row `provider_id="ge-proton:stable"` (or `:prereleases` matching settings), with payload `provider="ge-proton"`, `fetched_at=Utc::now()`, and future `expires_at`. Copy optional columns consistently, but note that reads deserialize **payload_json**, not the separate URL/checksum columns (`catalog/cache.rs:87-108`). Set include-prereleases explicitly and call install with `force_refresh=false` (the current install paths already do).

`catalog/mod.rs:40-46` returns a fresh-cache response **before** calling `fetch_live_catalog_by_id`; this path does not create the HTTP client or contact upstream. For missing-version AC1, seed another valid version in the same scoped catalog: an empty cache, malformed payload, wrong scoped key, or all-expired rows causes live fetch (`:49-50`), so those are not offline negative fixtures. Fresh-row behavior is covered at `catalog/tests.rs:103-126`; no production endpoint override currently exists.

Use valid GitHub-looking fixture URLs for pure/service rejection tests; the invalid DTO should be rejected before core download. To demonstrate “no installer started” robustly, a narrow injected install executor seam can count calls; otherwise assert no new job/destination plus test the pure helper. Do not rely on loopback core test allowance from app tests: dependency `crosshook-core` is not compiled with its own `cfg(test)` just because `crosshook-app` is being tested.

Expired cache attempts live HTTP before stale fallback; to deterministically test offline/stale fallback or `Unavailable` without network, inject a narrow catalog-fetch/network-availability seam or use an unknown provider (which deterministically errors before sending a request, though it still constructs the client: `catalog/fetch.rs:9-25`). Do not call a timed-out real endpoint an offline fixture. Stale fallback sets `cache.offline=true, stale=true` (`catalog/cache.rs:210-236`); service install must enforce the issue's offline `Unavailable` policy rather than proceeding merely because cached versions exist. A fresh cache alone says nothing about current network reachability.

## Persistence/usability

No schema change. Existing catalog stays SQLite v22/v23; umu cache remains v24 (outside this focused review). Owner authorization map and JobRegistry are memory-only, discarded at shutdown; no ownership token in TOML/SQLite. User-editable Steam/provider/prerelease preferences remain existing settings. Catalog stays viewable from cache with freshness/offline indicators; install cannot weaken identity or offline denial on degraded backends. Existing React command names/DTOs and cancel boolean behavior can remain; backend owner derivation adds no React-controlled credential.
