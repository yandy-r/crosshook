# YAN-847 security research

## Scope and evidence

Read-only source review for M1-35. Paths below are relative to `src/crosshook-native/` unless prefixed with `repo:`. No builds, tests, linters, network requests, cleanup operations, or repository mutations were run. Threat descriptions intentionally omit exploit recipes. Recommendations are distinguished from current behavior.

Trust boundary: an IPC/native caller may supply stale or fabricated paths, identifiers, manifests and image inputs. A local process may change the filesystem between scan, validation and mutation. Filesystem access remains limited by the OS/Flatpak grants, but those grants are not a substitute for application-level deletion containment.

## Decision summary

1. **The fresh-scan allow-list already exists in Tauri.** Preserve it in `StorageService`, not just the raw core cleanup call. `commands/storage.rs:64-86` rebuilds profile references, scans again, matches the exact `(kind, resolved_prefix_path, target_path)` tuple, and deduplicates. Invalid requests are silently dropped today, so they appear in neither `skipped` nor audit rows.
2. **The core API is not itself an authorization boundary.** `storage/prefix_health/cleanup.rs:15-34` accepts caller-created targets. It has no trusted-root argument or fresh scan. The migrated service must be the single orchestrator, and tests must exercise that orchestrator.
3. **Post-scan symlink replacement is not rejected reliably.** Cleanup checks the staged root with `symlink_metadata`, but canonicalizes the requested target and deletes the resulting path without first rejecting a target symlink (`cleanup.rs:118-180`). A target redirected elsewhere inside the same staged root can satisfy the containment check. This directly intersects acceptance criterion 1.
4. **Launcher rename has inconsistent old-slug validation.** Delete-by-slug sanitizes its slug; rename interpolates the raw old slug into old paths. Neither path concatenation nor watermark checks prove parent-directory containment.
5. Preserve image magic-byte validation, 5 MiB limits, HTTPS redirect policy and explicit API-key tracing exclusion. The SteamGridDB response image URL is used as an initial request without the redirect allow-list being applied to that initial URL.
6. Mods add/remove are registry operations, not installers/uninstallers. Do not turn registered paths into filesystem mutation targets during migration. Collection import is parse/preview only and must remain non-mutating.

## Storage: present flow and mitigations

### Scan and roots

- `storage/prefix_health/references.rs:9-44`, `collect_profile_prefix_references(&ProfileStore) -> Result<ProfilePrefixReferences, String>` lists/loads profiles, uses the effective profile's `runtime.prefix_path`, resolves its Wine prefix and canonicalizes when possible. A failed profile load sets `profiles_load_failed`; list failure aborts. Canonicalization falls back to the original string on error in `utils.rs:40-45`.
- `scan.rs:16-32`, `scan_prefix_storage(references: &[PrefixReference], stale_days: u64, inventory_incomplete: bool) -> Result<PrefixStorageScanResult, String>` builds reference keys and discovers neighboring prefixes. There is **no configured global prefix-roots allow-list**. The effective search roots are the parent of each existing referenced prefix and, for a `pfx` prefix, its compatdata grandparent (`discovery.rs:31-48`). These roots come from trusted profile inventory, not the cleanup request.
- Ordinary directory discovery rejects symlink entries via `symlink_metadata` (`discovery.rs:59-69`). Compatdata discovery rejects the app directory symlink, but the nested `pfx` check follows links and then canonicalizes it (`discovery.rs:83-95`). Referenced prefixes are included directly; `scan.rs:40` uses link-following `is_dir` checks. Therefore “discovery rejects every symlink” would be inaccurate.
- An orphan must have no profile references, a complete inventory, and `drive_c/CrossHook` as a directory (`scan.rs:44-60`; marker helper `utils.rs:52-54`). This marker is a useful ownership heuristic, not an unforgeable authorization capability. `inventory_incomplete` suppresses orphan targets; preserve this fail-safe.
- Staged candidates are immediate children of `drive_c/CrossHook/StagedTrainers` (`constants.rs:1`). `staged_trainers.rs:13-25` rejects a symlink staged root. Its loop skips symlink entries, calculates bytes without following child symlinks, and requires a readable modification time older than the supplied threshold (`staged_trainers.rs:35-59`; `utils.rs:22-37`). Scan age uses `SystemTime::now` (`scan.rs:21-24`). Scan output is sorted and runtime-only.

### Cleanup validation today

- Tauri `cleanup_prefix_storage(targets: Vec<PrefixCleanupTarget>, ...)` runs the entire rescan/filter/delete/audit sequence in `spawn_blocking` (`commands/storage.rs:57-144`). Its signature function is at `177-183`. Matching includes the enum kind and both strings, not just a basename or path prefix.
- Orphan cleanup rechecks reference membership, existence/directory shape, `drive_c`, and the managed marker; canonicalizes the target; requires equality with normalized `resolved_prefix_path`; then measures/deletes the canonical directory (`cleanup.rs:36-103`). It does **not** verify the target is a non-symlink with `symlink_metadata`, or that the canonical prefix belongs under a separately trusted root. Importantly, `resolved_prefix_key` is re-canonicalized at cleanup time (`41`), not pinned to scan-time identity: both supplied strings can resolve to the same substituted referent and equality still holds. References are the same command-start snapshot reused by scan and cleanup, not a new profile inventory read immediately before each deletion.
- Staged cleanup verifies existence, rejects a symlink staged root, canonicalizes staged root and prefix, requires staged root under prefix, canonicalizes target and requires target under staged root, then deletes canonical target (`cleanup.rs:106-194`). This is component-aware `Path::starts_with`, not a string-prefix check. It does not require a strict descendant/immediate child, recheck stale age, or reject a symlink at the target itself. There is no stable filesystem identity carried from the fresh scan.
- `dir_size_bytes` ignores symlink children, reducing traversal during measurement (`utils.rs:7-37`). This does not eliminate ancestor replacement races before later path-based calls.

### Required migrated authorization contract

The service must establish trusted roots from profile inventory/discovery policy once per cleanup operation; **never derive them from requested `resolved_prefix_path`**. Preserve arbitrary user-configured prefix locations: a hard-coded home/Steam-only allow-list would break supported profiles. Make the discovered-root policy explicit (ordinary prefix siblings vs. compatdata app/pfx layout), and reject candidates that resolve outside it. For compatdata discovery, canonical containment must include the nested `pfx`, not only its app directory.

For each request:

1. Reload profile references and completeness state, then run a **fresh scan inside the cleanup worker**, not a previously displayed/cached scan. A DB snapshot or UI job result is informational, never authority.
2. Accept only an exact fresh-scan tuple `(kind, resolved_prefix_path, target_path)` and deduplicate it. Use the **fresh server-produced target** after matching, not the caller object. Keep strict string matching for the request envelope; canonical equivalence must not expand authorization to aliases that were not offered by the scan.
3. Canonicalize trusted roots, prefix and target with errors failing closed for deletion. Do not use `normalized_path_string`'s raw fallback as a safety proof. Compare component-wise, require orphan prefix strictly below an allowed root, and require staged target strictly below its staged root and within its allowed prefix. Reject the roots themselves. For current scan shape, require the staged target to be an immediate child of the staged root. Require orphan target identity to equal its resolved prefix.
4. Use `symlink_metadata`/no-follow checks on the requested target **before** canonicalizing it. Reject symlinks, dangling links, unexpected special files and wrong file kinds. Check the fixed intermediate components below the trusted root as well: checking only `StagedTrainers` does not protect a replaced `drive_c`/`CrossHook` ancestor. Canonicalization follows links and cannot substitute for a no-follow check.
5. Immediately before mutation, recheck kind, canonical identity/containment, orphan ownership/reference eligibility and staged age/eligibility. A candidate that disappeared, became a link or escaped its roots is skipped/rejected without touching its referent. Preserve the incomplete-inventory orphan prohibition.
6. Treat check-then-delete as a TOCTOU boundary, not atomic protection. Simple extra `symlink_metadata` calls satisfy the explicit before-cleanup symlink regression but leave a race if an attacker swaps an ancestor after validation. For a strong concurrent-mutation guarantee, resolve and delete relative to pinned directory handles with no-follow/beneath semantics (and verify stable device/inode identity), rather than recanonicalizing strings and deleting the resulting absolute path. Recursive deletion must not traverse substituted links. Reuse existing filesystem/dependency capabilities where suitable; do not claim a process-local lock protects against external processes.
7. Preserve deletion/audit results and surface rejected requests deliberately. Today invalid allow-list entries vanish silently. Prefer an explicit rejected/skipped outcome with a safe reason if the response contract permits; this should be an intentional compatibility decision, not an accidental migration change.

Canonical roots may intentionally originate from user-configured aliases. Resolve that trusted configuration boundary once; do not categorically ban all symlinked home/Steam configuration roots. The stricter no-follow rule concerns untrusted target traversal **below** the established root and later replacement of its identity.

### Audit schema and persistence

- Migration 15→16 is unchanged: `metadata/migrations/v11_v20.rs:194-231` creates `prefix_storage_snapshots` and `prefix_storage_cleanup_audit`. Audit columns: `id TEXT PRIMARY KEY`, non-null `target_kind`, `resolved_prefix_path`, `target_path`, `result`, nullable `reason`, non-null `reclaimed_bytes INTEGER`, `created_at TEXT`. Indices cover `created_at DESC` and `resolved_prefix_path`. No table-level enum/check constraint supplies authorization.
- `MetadataStore::insert_prefix_storage_cleanup_audit(&PrefixStorageCleanupAuditRow) -> Result<(), MetadataStoreError>` delegates via `with_conn_mut` (`metadata/prefix_ops.rs:133-140`); `prefix_storage_store.rs:74-98` uses parameterized SQL. Listing also binds its limit (`100-140`). Existing row round-trip tests are at `179-200`; these are not service authorization tests.
- Tauri writes one UUID row per deleted target (`commands/storage.rs:91-106`) and one per core-skipped target (`108-122`), then a `summary` row containing reclaimed total (`124-139`). Individual rows currently store zero reclaimed bytes. All audit writes are fail-soft warnings **after** deletion. An audit failure cannot roll back filesystem effects; preserve/document this explicitly rather than promise transactional filesystem+SQLite behavior.
- History is limited to 50 snapshots/100 audit rows and includes `available` (`commands/storage.rs:147-175`). Scans remain runtime-only; snapshots/history remain existing operational SQLite metadata. No migration or new TOML is needed. On DB failure, storage can still scan/clean under current behavior but history/audit availability must be honest; the issue's strict `Unavailable`/no partial writes rule applies separately to collections/mods.

### Testability and required regressions

Use `tempfile::TempDir` for two independent roots, prefixes with `drive_c/CrossHook`, staged children and out-of-root sentinels. Inject roots/prefix inventory and a scan clock or stale threshold; do not mutate global HOME/XDG or wait for wall time. `ProfileStore::with_base_path` plus `MetadataStore::open_in_memory` already support isolated integration fixtures (e.g. `profile/collection_exchange/mod.rs:70`, `game_images/client/tests.rs:234`). Add a private/package-scoped cleanup orchestration seam accepting a scanner and a deterministic before-delete hook/barrier, or factor pure selection from filesystem cleanup. Avoid making caller-supplied production roots an IPC argument.

Required tests:

- Requested tuple absent from the fresh scan: no deletion, no accidental acceptance from old UI output; test wrong kind, wrong prefix, wrong target and duplicates independently.
- Target changed to symlink after scan: reject whether its referent is inside **or outside** the staged root; referent survives. Also cover orphan symlink, dangling target, staged-root/intermediate-component replacement.
- Candidate canonicalizes outside injected root (including compatdata nested `pfx` link): reject; out-of-root sentinel survives. Cover sibling-prefix string confusion, root equality, staged-root equality and non-immediate-child requests.
- Referenced orphan and incomplete profile inventory cannot be deleted; staged child that no longer qualifies as stale is not authorized by stale UI state.
- Accepted target is removed exactly once and produces expected per-target audit row plus summary total; skipped target has a reason; DB-unavailable/fail-soft audit behavior is explicit.
- Deterministic ancestor-replacement race test if the implementation claims concurrent-mutation resistance; no sleep-based races. A pure preflight test is not evidence of atomic no-follow deletion.

No cleanup/scan tests were found in the reviewed `storage/` source modules; `prefix_health/mod.rs:1-20` has no test module, and the external tests directory inventory has no storage test. The existing metadata round-trip tests do not cover the required four acceptance cases.

## Other untrusted inputs and preservation requirements

### Custom-art import

Current `game_images/import.rs:33-72`, `import_custom_art(source_path: &str, art_type: GameImageType) -> Result<String, String>`:

- Enumerates only covers/portraits/backgrounds; destination directory is fixed under `$LOCALDATA/crosshook/media`. A source basename never becomes a destination basename; destination is the first 16 hex characters of a SHA-256 plus inferred extension (`44-65`). Thus source traversal does not directly choose a write destination. Reading a user-selected path outside media is intentional import functionality.
- Reads the entire source using `std::fs::read` **before** validating size (`46-53`). Source symlinks are followed; existence is the only source metadata gate. No regular-file or bounded-read check occurs before allocation, so special/very large inputs can block/consume resources even though later validation rejects the bytes.
- Reuses `validate_image_bytes` (`client/validation.rs:11-36`): maximum **5 MiB**, magic-byte allow-list JPEG/PNG/WebP; SVG/HTML/unknown formats rejected, regardless of extension. This is signature recognition, not complete decode/dimension validation.
- Destination `create_dir_all`/`exists`/`write` has no canonical parent containment/no-follow gate. `is_in_managed_media_dir` is only lexical `Path::starts_with` (`import.rs:17-23`), so it must not be used as a deletion or trust authorization primitive.

Preserve content-derived destination/allowed types/format checks and cache layout. Run sync import in a blocking worker in the service. Required preservation tests: valid image with misleading source extension gets inferred extension; SVG/HTML/unknown/oversize rejected; no output on failure; idempotent content; supported art-type subdirectory. Recommended hardening tests: bounded source read rejects oversize without unbounded allocation; regular-file policy and media destination symlink/ancestor escape; use an injectable media base so tests never write the developer's real media directory. Existing portrait test (`import.rs:113-152`) permits a validation error and can write the real base directory, so it is not a strong successful-import isolation test.

### Collections TOML import

- Command `commands/collections.rs:157-166` only rejects empty path and calls `preview_collection_preset_import(&ProfileStore, &Path)`.
- Core `profile/collection_exchange/import.rs:20-62` reads the selected file, parses/validates, builds a local profile-match index, and returns matched/ambiguous/unmatched descriptors. **It does not create collections, mutate profiles, execute hooks or fetch URLs.** Preserve preview-only semantics.
- TOML parser is typed (`import.rs:64-87`); `collection_schema.rs:23-49` requires schema version exactly `"1"` and nonblank name. Descriptors are identities, not filesystem paths (`10-19`). No explicit file-size/descriptor-count/string-size bound is applied before `read_to_string`/parse/classification, and schema validation does not sanitize every defaults field.
- IPC defaults sanitization is intentional: `commands/collections.rs:104-135` clears extras returned to callers and clears caller-supplied extras before preserving existing stored extras. Preserve this boundary and `apply_collection_defaults` merge-table behavior; moving code must not make imported defaults executable or directly save a profile outside `ProfileWriter`.

Required tests: malformed/unsupported-version/blank-name manifests produce errors without writes; valid import is preview-only; ambiguous matches require explicit choice; unknown/default extra handling does not let caller injection overwrite preserved extras; DB-disabled collection mutations report `Unavailable` before any partial operation. Keep existing parser/version/round-trip tests in `profile/collection_exchange/mod.rs:70-85,119-121`. Bounded reads/count limits would be hardening beyond the migration baseline and should be an explicit design decision.

### Launcher delete/rename and generated artifacts

- Ordinary delete derives a sanitized slug (`export/launcher_store/paths.rs:9-31`); delete-by-slug sanitizes as well (`34-53`). `sanitize_launcher_slug` emits alphanumeric characters/dashes (`export/launcher/names.rs:43-72`), preventing separators in that derived component.
- Mutations verify regular-file status with `symlink_metadata` and a CrossHook watermark (`launcher_store/fs_ops.rs:13-49`), then remove files (`53-63`). Non-CrossHook files and final-component symlinks are skipped. A watermark is ownership evidence, not path containment.
- **Gap:** `rename_launcher_files` sanitizes the new name but interpolates raw `old_launcher_slug` into old paths (`launcher_store/mutations.rs:121-157`). `combine_host_unix_path` normalizes slash spelling and concatenates strings; it does not remove/reject parent traversal (`launcher/paths.rs:8-32`). Normalize/reject the old slug consistently and prove both old/new parents are within the resolved launcher directories before read/write/delete.
- Parent-directory symlinks are not rejected/canonically contained. `resolve_target_home_path` accepts an absolute-looking preferred home with only a compatdata exclusion (`launcher/paths.rs:62-90,141-143`); caller-selected home must be treated as the explicit export root, not proof of a trusted global home.
- Rename destination checks protect existing normal symlinks/unwatermarked files, but `verify_destination_safe` treats nonexisting paths as safe using link-following `exists` (`mutations.rs:23-35`), including a dangling-link edge. Same-slug rewrite skips destination verification (`176-184`). Writer uses `fs::write` and changes permissions without no-follow (`launcher/paths.rs:34-59`). These checks remain check-then-use, not atomic replacement protection.
- No process executes on export: it writes script/desktop text. Preserve shell quoting (`paths.rs:145-155`), env-name validation (`launcher/types.rs:172-185`), ownership watermarks, modes and exact generated bytes. Do not reimplement generators in the service.

Required preservation tests: existing `launcher_store/tests/delete.rs:174,209,229` (symlink/watermark), `rename.rs:94,240,273,344,398` (env validation/ownership/destination), plus traversal old slug, parent-directory symlink, dangling destination and same-slug non-owned artifact cases. Byte-identical golden script/desktop tests must include whitespace, quotes, percent characters and display-name control characters. The reviewed request validation (`types.rs:138-211`) does not validate old slug or canonical launcher-root containment.

### Mods add/remove paths

- `commands/mods.rs:104-184` resolves a profile to metadata ID and checks DB availability before writes. Updates/removals are keyed by both profile ID and mod ID (`metadata/mods_store.rs:160-210`); SQL values use bound parameters. **Removal deletes a registry row only**, never files listed in `paths`.
- `metadata/mods_store.rs:10-94` trims input, requires name <=200 chars, <=32 paths, each <=1024 chars and no NUL, <=8 KiB encoded path JSON, and http(s) source URL <=2048 chars. Paths may intentionally be absolute/relative and are not canonicalized/contained because they are advisory metadata, not mutation authority.
- Detection is read-only and bounded to 2048 entries, skips link entries, and only visits the root plus fixed one-level markers (`mods/detection.rs:175-219`). Root itself is `read_dir`'d and may follow a configured alias; do not misstate entry no-follow as a complete no-symlink-root guarantee.

Required tests: register/remove with out-of-root/relative paths leaves filesystem untouched; cross-profile mod ID cannot update/delete another profile's row; input bounds/NUL/source scheme enforced; DB-disabled mutations return `Unavailable` with no row/file changes; detection symlink and budget tests remain (`mods/tests/detection.rs:180,200`). Do not add installer behavior or new path restrictions as accidental migration changes.

### Cover-art URLs, API key and offline behavior

- Public download validates nonempty numeric app ID before building URLs (`game_images/client/api.rs:47-60`), uses fixed Steam CDN URL templates (`download.rs:10-42`), validates downloaded bytes and writes via cache path validation (`api.rs:195-236`). Cache path construction canonicalizes base and parent and checks containment (`validation.rs:52-76`). Final-component write still is not no-follow/atomic.
- Image HTTP client uses a 15s timeout and only follows HTTPS redirects to four explicit Steam/SteamGridDB hosts (`client/http.rs:12-55`). Network image bodies enforce both announced and streaming **5 MiB** caps (`download.rs:73-90`).
- **Gap:** SteamGridDB JSON `first_url` is requested directly (`steamgriddb.rs:78-95`); redirect policy does not validate an initial URL. Treat remote URL as untrusted and apply HTTPS/approved-host validation before the first request as well. API JSON itself is read with `.json()` without the image streaming byte limit (`70`).
- Key is loaded from settings without printing it (`commands/game_metadata.rs:40-48`), sent only as bearer auth (`steamgriddb.rs:49-54`), explicitly excluded from tracing via `#[instrument(skip(api_key), ...)]` (`38`), and never included in generated endpoint/download URL. Authentication warnings include status and generic guidance, not key (`client/api.rs:110-113`). Preserve this in every new service span: use `skip`/`skip_all` rather than auto-recording request/settings objects. Do not log headers, full settings, the token, or a derived token prefix. Remote image URLs are logged (`steamgriddb.rs:87`); avoid logging credentials/query tokens if URL policy expands.
- Valid cached art is returned before network (`api.rs:67-94`); network failure falls back to existing stale file (`cache.rs:55-75`). No available image currently becomes `Ok(None)`, not typed `Unavailable`; service must adapt to issue-required offline status while retaining cached art. Cache remains `$LOCALDATA/crosshook/cache/images`, custom art remains `media`.
- Steam metadata separately uses a fixed app-details URL, numeric normalization, 6s timeout, stale cache and `Unavailable` (`steam_metadata/client.rs:80-121,126-162`). It does not share the image redirect policy or response-size limits; do not assume the two HTTP clients are identical.

Required tests: reject invalid app IDs before network; fixed initial URL + HTTPS/host redirect checks; rejected initial SteamGridDB URL never fetched; byte limits with and without Content-Length; SVG/HTML rejection; stale cached art survives offline failure; capturing tracing output across success/auth/network errors proves a sentinel API key never appears. Existing `game_images/client/tests.rs:30,75,86,186,196,206` covers several validation primitives; `oversized_content_is_rejected` at `95-106` actually passes a `MAX_IMAGE_BYTES + 1` JPEG-signature buffer to production `validate_image_bytes`. Preserve it, and add separate streaming-response cap coverage rather than treating byte validation as proof of bounded network reading.

## Host-tool gateway

- Policy: `repo:CLAUDE.md:30`; `repo:docs/architecture/adr-0001-platform-host-gateway.md:28-35,81-89`. Host tools must use `crosshook_core::platform` gateway. User-supplied executable paths/generated script text have a distinct policy boundary; generated text is not a Rust child process invocation.
- `repo:scripts/check-host-gateway.sh:7-21` includes core, Tauri, **app**, UI/widgets/view-model roots, and only excludes the exact gateway file. Moving service code to app does not escape enforcement. Denylist includes Proton/umu/gamescope/MangoHud/winetricks/protontricks/gamemoderun and URL openers/flatpak-spawn.
- The checker is lexical, not Rust parsing (`80-85`); aliases, multiline calls, raw strings, constants and macros require review. Symlink scan roots/Rust sources fail closed (`50-78,89-105`); tests directories exempt. Do not add suppressions simply to pass a migration.
- Reviewed storage/mods/collections/image/launcher mutation paths use Rust filesystem/HTTP/SQL operations rather than launching external cleanup/copy commands. Low-disk storage uses `statvfs`, not `df` (`storage/prefix_health/disk.rs:3,28`).
- Proton discovery **can spawn host filesystem probes indirectly** via gateway helpers: `steam/proton/discovery.rs:140-184,218-248` calls `host_path_is_dir`, `host_read_dir_names`, `host_path_is_file`, `host_read_file_bytes_if_system_path` for Flatpak system roots. ADR API contracts restrict those system probes under `/usr` or `/usr/local` with no `..` (`ADR:52-57`). Preserve gateway calls when moving `list_proton_installs` into its async scan; do not substitute shell calls or direct denylisted `Command::new`.

## Persistence and user-visible failure contract

No new persistence or migration: existing collections TOML wire format, SQLite collection/mod/storage/image metadata, media/cache directories remain unchanged. Fresh scan authorization sets and pinned filesystem identities are runtime-only and must not be reconstructed from persisted history. Imported source files remain user-selected; outputs must stay in their managed or explicitly selected roots. Collections/mods with disabled DB must report `Unavailable` before any write; storage audit remains current fail-soft behavior unless explicitly changed. Offline metadata/art fetch must make unavailability visible without hiding already cached art. Preserve actionable failure reasons without exposing secrets.
