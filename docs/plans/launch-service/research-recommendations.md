## 2. Decisions

### D1 — Target shape: one `LaunchService`, no `AppEvent` addition

`crates/crosshook-app/src/services/launch/{mod.rs,game.rs,trainer.rs,gamescope.rs,finalizer.rs,warnings.rs,streaming.rs,spawner.rs,types.rs,queries.rs}` plus `tests/` mirroring `services/profiles/tests/`. `services/mod.rs` gains `pub mod launch; pub use launch::LaunchService;`.

```rust
#[derive(Clone)]
pub struct LaunchService {
    profiles: ProfileStore, metadata: MetadataStore, settings: SettingsStore,
    sessions: Arc<LaunchSessionRegistry>,           // core type, unchanged
    spawner: Arc<dyn ProcessSpawner>,
    background: Option<Arc<BackgroundGrantHolder>>, // services::background, already in crosshook-app
}
impl LaunchService {
    pub fn new(profiles: ProfileStore, metadata: MetadataStore, settings: SettingsStore,
               sessions: Arc<LaunchSessionRegistry>, spawner: Arc<dyn ProcessSpawner>) -> Self;
    pub async fn start_game(&self, req: GameLaunchRequest) -> Result<LaunchSession, AppError>;
    pub async fn start_trainer(&self, req: TrainerLaunchRequest) -> Result<LaunchSession, AppError>;
    pub async fn cancel_session(&self, id: SessionId) -> Result<(), AppError>;      // own session only
    pub async fn reset_sessions(&self, profile_name: &str) -> usize;               // launch_reset_sessions
    // queries.rs: validate_launch, preview_launch, list_launch_history_for_profile,
    // build_steam_launch_options_command — async facades, blocking store I/O via services::run_blocking
}
```

Rationale: mirrors `ProfileWriter::new(profiles, metadata, settings, events)` (`services/profiles/mod.rs:43-63`); shells construct it from the stores they already manage. Do **not** hang it off `App` (`app.rs:55-90` owns only runtime/`EventBus`/`JobRegistry`, no stores) and do **not** add launch variants to `AppEvent` (`events.rs:55-72`, `#[non_exhaustive]`, capacity 256): high-frequency log batches would evict `ProfilesChanged`/`Resync` traffic and force every subscriber to filter every session's logs. Errors reuse `AppError`/`AppErrorKind` (profile-writer D11); Tauri maps `error.to_string()`.

Requests are built by callers with M1-01 (`LaunchRequest::from_profile`), helpers resolved with M1-29 (`runtime_helpers::resolve(RuntimeHelper::…)`), exactly as `execution.rs:125-145` and CLI `launch.rs:95-115` do today. `start_*` sets `launch_game_only`/`launch_trainer_only` itself (today: `execution.rs:79-80, 260-261`) so no caller can cross-wire them.

### D2 — `LaunchEvent` delivery: per-session bounded `broadcast`, subscribe-before-start

```rust
pub struct LaunchSession { pub id: SessionId, pub kind: SessionKind,
    pub warnings: Vec<LaunchValidationIssue>, pub helper_log_path: PathBuf,
    pub events: LaunchEventStream }
pub struct LaunchEventStream { /* broadcast::Receiver<LaunchEvent> + id */ }
#[derive(Debug, Clone, PartialEq)]
pub enum LaunchEvent {
    Log       { session_id: SessionId, batch: LogBatch },        // log_tail::LogBatch, incl. Dropped{n}
    Injection { session_id: SessionId, event: InjectionLogData },
    Diagnostic{ session_id: SessionId, report: Box<DiagnosticReport> },
    Exited    { session_id: SessionId, code: Option<i32>, signal: Option<i32> },
}
```

Decision: per-session `tokio::sync::broadcast` (capacity `DEFAULT_EVENT_CAPACITY = 256`, `events.rs:10`), channel and first receiver created **before** spawn and the receiver moved into `LaunchSession` — the exact subscribe-before-start invariant of `JobRegistry::start` (`jobs/registry.rs:136-190`), so an instantly-exiting child cannot outrun its caller. Every variant carries `session_id` explicitly (acceptance criterion), never only implicitly via stream identity.

Rejected: (a) global `EventBus` — see D1; (b) per-session unbounded `mpsc` — single-consumer only, and unbounded is the current pipe-mode defect (`streaming.rs:185`); a bounded `mpsc` is viable but loses late-subscribe/replay and diverges from the M1-04 precedent for zero gain; (c) running launches _as_ `JobRegistry` jobs — `Outcome` (`jobs/types.rs:96-110`) cannot express exit code+signal or carry a `DiagnosticReport`, and launch linking lives in `LaunchSessionRegistry`, not `JobKey`. Reuse the _pattern_, not the registry.

Lag semantics: `RecvError::Lagged(n)` on the adapter/CLI side surfaces as one synthetic `Log { batch: LogBatch::Dropped { n } }` then continues — never blocks the producer (finalizer must not stall on a dead UI). Exactly one `Exited` is published, last, by the finalizer; the sender is then dropped. No retained-replay store: the only legitimate consumer holds the pre-spawn receiver.

### D3 — Single gamescope predicate, env injected for testability

```rust
// services/launch/gamescope.rs
#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub struct GamescopeEnv { pub is_flatpak: bool, pub inside_gamescope_session: bool }
pub fn gamescope_env_now() -> GamescopeEnv; // is_flatpak() + is_inside_gamescope_session()
pub fn gamescope_required(req: &LaunchRequest, kind: SessionKind,
                          effective_method: &str, env: GamescopeEnv) -> bool;
pub fn gamescope_pid_capture_required(required: bool, env: GamescopeEnv) -> bool { required && env.is_flatpak }
```

Semantics, extracted verbatim: `effective_method == METHOD_PROTON_RUN && cfg.enabled && (cfg.allow_nested || !env.inside_gamescope_session)` where `cfg = if kind == Trainer { req.resolved_trainer_gamescope() } else { req.gamescope.clone() }` (`request/models.rs:203-215`). `effective_method` is the _execution_ method (`resolve_trainer_launch_method` output), never the raw request method — the Flatpak-Steam-trainer lesson already encoded in `portal.rs:8-12` and core `should_register_gamemode_portal_with`.

Rules: (1) the watchdog is spawned **iff** `gamescope_required` (`execution.rs:505-540` `consume_cancel_channel` collapses to: predicate true + `child.id()` → `gamescope_watchdog`; otherwise `drain_cancel_into_outcome`); (2) PID-capture file exists iff `gamescope_pid_capture_required` (today's divergent game/trainer formulations at `execution.rs:114-122` vs `306-315` become one call); (3) Flatpak is an input dimension precisely so the table test can prove it only affects capture, not requirement. The issue's `gamescope_required(req, settings)` second parameter is dropped: no settings field participates today (gamescope config rides on `LaunchRequest`); adding an unused `&AppSettingsData` would be a fake seam. If M1-01 later moves gamescope defaults into settings, extend `GamescopeEnv`, don't resurrect a settings bag.

### D4 — `ProcessSpawner`: minimal — spawn + wait-with-cancel; no shutdown method

```rust
// services/launch/spawner.rs
pub trait ProcessSpawner: Send + Sync {
    fn spawn(&self, command: tokio::process::Command) -> io::Result<Box<dyn SpawnedChild>>;
}
pub trait SpawnedChild: Send {
    fn id(&self) -> Option<u32>;
    fn take_stdout(&mut self) -> Option<Box<dyn AsyncRead + Send + Unpin>>;
    fn take_stderr(&mut self) -> Option<Box<dyn AsyncRead + Send + Unpin>>;
    fn wait_with_cancel<'a>(&'a mut self, cancel: &'a CancellationToken, grace: Duration)
        -> Pin<Box<dyn Future<Output = io::Result<ChildExit>> + Send + 'a>>;
}
pub struct TokioSpawner; // production impl
```

Shape rationale:

- **One spawner method.** The service builds the `tokio::process::Command` via the existing core builders (ADR-0001 gateway safety stays in core) and hands it over. The trait never sees program strings, env, or paths — a fake cannot accidentally bypass `build_proton_*_command`. No `#[async_trait]` (not in `crates/crosshook-app/Cargo.toml`); `spawn` is sync, matching `Command::spawn`.
- **`wait_with_cancel` is the wait.** Production impl delegates to `jobs::process::supervise_child` (`ChildExit::{Natural, Terminated, Killed}`), so SIGTERM→`DEFAULT_KILL_GRACE`→SIGKILL of the child's own process group is the _only_ non-gamescope kill path, and it is already tested. This forces one deliberate behaviour fix: the spawner sets `command.process_group(0)` before spawn (supervise_child rejects non-leaders, `jobs/process.rs:80-90`). Flag it in the PR; gamescope children are unaffected because their tree teardown stays with core `gamescope_watchdog` + per-session `ShutdownTarget` (core-private; the service holds only `(SessionId, gamescope_pid, exe_name, pid_capture_path)` per session — it never constructs or shares a target across sessions).
- **No `shutdown()` on the trait and no kill method on `LaunchService` beyond registry cancel.** Shutdown is expressed as: registry broadcast (`cancel_linked_children` / `cancel_session`) → the session's own watchdog _or_ its `wait_with_cancel` token fires. Two kill entry points is how a sibling's tree gets killed; one is the invariant behind "a session never kills another session's process tree".
- Fake for tests: `FakeSpawner { scripted stdout/stderr lines, exit status, spawn_error }` recording `wait_with_cancel` invocation; `ErrSpawner` for the spawn-failure deregister path (`execution.rs:160-165, 375-393`).

### D6 — Finalizer as a pure-ish, once-only sink

`finalizer.rs` exposes `async fn finalize(input: FinalizeInput, deps: &FinalizerDeps) -> FinalizeOutcome` where `FinalizeInput` is everything `LaunchStreamContext` carries today (`shared.rs:160-190`) minus `AppHandle`, and `FinalizeOutcome { exit: (Option<i32>, Option<i32>), report: Option<DiagnosticReport> /* already gated by should_surface_report */, injection: Vec<InjectionLogData> }`. The adapter/CLI render the outcome; the finalizer itself emits on the session channel.

Non-negotiable ordering, copied from `streaming.rs:240-460`: analyze+sanitize → watchdog-outcome rewrite → `record_launch_finished` (exactly once, only if `operation_id` present) → snapshot+known-good **only** on `CleanExit | Indeterminate` → post-exit hooks → `cancel_linked_children(LinkedSessionExit)` for games → `deregister` → publish `Diagnostic` then `Exited`. Side effects run via `run_blocking`; each is fail-soft with `tracing::warn!` exactly as today — a metadata failure must never suppress `Exited` or the cascade (data integrity: history row is best-effort, session teardown is not). `sanitize_diagnostic_report` / `diagnostic_method_for_log` / relay suppression (`shared.rs:23-60`) move into the service _with their tests_ (`tests/{log_relay,diagnostics}.rs` relocate, not rewrite).

### D7 — Streaming unification on M1-04

One `streaming.rs` path replaces both modes: if the spawned child has piped stdout/stderr, drain pipes → append to log file → publish lines (preserving today's file-as-source-of-truth, `streaming.rs:177-237`); concurrently `log_tail::follow(log_path, TailConfig::default(), session_cancel, sink)` publishes `LogBatch::Lines` after the existing `transform_launch_log_line_for_ui` suppression transform. File-only children just use `follow`. The 500 ms whole-file re-read (`streaming.rs:104-160`) and CLI `drain_log` polling are deleted. Diagnostics tail uses a bounded seek-read in the service (replacing both `safe_read_tail` copies: `diagnostics.rs:9-35`, CLI `launch.rs:340-354`) capped at `MAX_LOG_TAIL_BYTES` — do not tail-follow for the tail; one offset read, lossy UTF-8, same as today.

## 6. Persistence & usability classification

Runtime-only: `LaunchSession`, event channels, relay suppression state, watchdog handles — memory, lost on exit, exactly as today's registry. SQLite (unchanged schema/format): `launch_operations` start/finish rows, `version_snapshots`, known-good `config_revisions` tagging. TOML: untouched. Log files: same `/tmp/crosshook-logs` location via `create_log_path`. No migration, offline behaviour unchanged (warnings already degrade to empty when metadata is unavailable, `warnings.rs:22-25`), degraded fallback = today's fail-soft finalizer. User-visible change: none, except log lines becoming attributable per session in future UI.

## 7. Explicitly rejected

Dual-emitting old+new `launch-log` payloads; a `shutdown()`/`kill()` method on `ProcessSpawner` or `LaunchService`; launches as `JobRegistry` jobs; launch events on the global `EventBus`; an unused `settings` parameter on the predicate; retaining either `safe_read_tail` copy or the CLI streaming loop "for safety"; schema or `DiagnosticReport` field changes in core (the `session_id` lives in the adapter payload and the service event, not in the persisted report).
