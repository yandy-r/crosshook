# Practices Research: launch-service (M1-05 / YAN-798 / #534)

> Target file: `docs/plans/launch-service/research-practices.md` (worktree `crosshook-yan-798`).
> Read-only research. Paths are relative to `src/crosshook-native/` unless absolute. Line numbers are from the researched checkout.
> Sibling doc: [research-recommendations.md](research-recommendations.md) (decisions D1–D7). This doc covers what to **reuse**, the **conventions** to copy, and what **not** to abstract. Where it disagrees with the recommendations doc, it says so and gives the reason (§3.3, §3.4).

## 0. Executive summary

- `crosshook-app` already has every primitive the launch service needs: the service shape (`ProfileWriter::new(stores…, EventBus)`), `Services::new(&Stores, EventBus)`, `run_blocking`, `AppError`, `BackgroundGrantHolder`, `log_tail::follow`, `jobs::create_log_path`, and the subscribe-before-start broadcast pattern. **Nothing new needs inventing except `gamescope_required`, `ProcessSpawner` and the `LaunchEvent` type.**
- Reuse core as-is: `LaunchSessionRegistry`, `drain_cancel_into_outcome`, `gamescope_watchdog`, the six `script_runner` builders, `analyze`, `run_*_hooks`, `should_register_gamemode_portal`. Do not wrap them.
- Two behavioural traps in the recommendations doc's spawner design: `supervise_child` needs `process_group(0)` and only signals the `flatpak-spawn` proxy under Flatpak, and today's non-gamescope sessions are **never killed** on cascade (they only record a reason). Keep `wait()`-only semantics in M1-05; details in §3.3.
- Six tests in `src-tauri/src/commands/launch/tests/` move with their code (§6). Thin IPC contract tests stay in the adapter.

## 2. Conventions to copy

### 2.1 Module layout and file size

- CLAUDE.md "File size (~500 lines)" is a soft cap that **must** be refactored when exceeded. "Single responsibility" and "No copy-paste duplication" are MUSTs. Rust modules are directories with `mod.rs`.
- Precedent: `services/profiles/` uses `mod.rs` for the struct, constructor and re-exports, then one file per concern (`writer.rs`, `lifecycle.rs`, `sections.rs`…), plus `tests/{mod.rs, helpers.rs, <slice>.rs}` (`services/profiles/tests/mod.rs`). Core splits tests out to stay under the cap (`launch/session/registry_tests.rs:1-2`).
- Inputs being split: `execution.rs` 641 lines, `streaming.rs` 542, `shared.rs` 208, `warnings.rs` 182, `queries.rs` 140, `diagnostics.rs` ≈75, `portal.rs` ≈40, `mod.rs` 52, about 1,880 in total. Plus CLI `launch.rs` ≈360.

### 2.2 Service conventions

- Every public method is `async`. Blocking work goes through `run_blocking` (`services/mod.rs` header doc, lines 1-5).
- The service is `#[derive(Clone)]` and cheap to clone (stores + `Arc`s). It must be `Send + Sync`; add `static_assertions::assert_impl_all!(LaunchService: Send, Sync)`, the way `app.rs` does for `App`.
- No Tauri, GTK or other UI crate. `scripts/check-app-deps.sh` (`BANNED_RE`, line ~17) fails the build otherwise. `scripts/check-host-gateway.sh` scans `crates/crosshook-app/src` (lines 11-18), so nothing in the service may `Command::new("<host tool>")`. Commands come from core builders only.
- `#![deny(missing_docs)]` is on in `lib.rs:8`. Every `pub` item in the service needs a doc comment.
- Wire DTOs (`LaunchResult`, `InjectionLogEvent` serde shape) stay in the **adapter**. `LaunchResult` has `#[serde(skip_serializing_if = "Vec::is_empty")] warnings` at `shared.rs:63-70`. The service returns domain types. Precedent: `src-tauri/src/startup_bridge.rs` owns `ProfilesChangedPayload` / `FinishedPayload`, and the app owns the enums.
- Spawning background tasks: the service runs inside the caller's runtime (Tauri's borrowed handle is the same runtime `App::bootstrap` uses, `src-tauri/src/lib.rs:19-20`; the CLI uses `#[tokio::main]`). Use `tokio::spawn` from inside the `async fn`, as `JobRegistry::default` falls back to `Handle::try_current` (`jobs/registry.rs:140-145`). Do **not** require an `App` clone. The service must also work in the CLI without bootstrap.
- Tauri wiring precedent: `.manage(services.<x>.clone())` (`src-tauri/src/lib.rs:41-46`). Add `.manage(services.launch.clone())`. Remove the separate `.manage(Arc::new(LaunchSessionRegistry::new()))` (`:58-60`) once `list_running_profiles` / `launch_reset_sessions` delegate. Two registries would split the session world.
- The CLI must gain `crosshook-app = { path = "../crosshook-app" }` (absent today, `crates/crosshook-cli/Cargo.toml`). The CLI builds `LaunchService::new(...)` directly from its stores. It does not need `App::bootstrap` (no startup jobs, no logging policy change).

## 3. KISS assessment: what to build, and what not to abstract

### 3.1 Build only these three new things

1. `gamescope_required`, a pure function: `effective_method == METHOD_PROTON_RUN && cfg.enabled && (cfg.allow_nested || !env.inside_gamescope_session)`. Here `cfg` is `req.gamescope` for a game and `req.resolved_trainer_gamescope()` for a trainer. Pid capture is `required && env.is_flatpak`. This keeps today's game semantics (`execution.rs:109-113` checks `request.resolved_method()`, which equals `method` for games) and trainer semantics (`:294-299`). I agree with D3 that the predicate takes no settings parameter, because nothing in settings participates today. It is the issue's `(req, settings)` signature minus a fake input.
2. `LaunchEvent` and the per-session receiver. Copy the `JobEvents` lag mapping. Deliver exactly one terminal `Exited`.
3. `ProcessSpawner`, kept minimal (§3.3).

### 3.2 Do NOT abstract (each rejected with its cost)

| Temptation                                                            | Why not                                                                                                                                                                                                                                                                                                                                                                                                                       |
| --------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `LaunchError` / per-module error enums                                | `AppError` already sanitizes and has a launch validation mapping (`error.rs:242`). A second type means a second Tauri mapping. Profile-writer D11 sets the precedent.                                                                                                                                                                                                                                                         |
| `EventSink` / `Emitter` trait injected into the service               | The service returns a receiver and the adapter maps it, the way `startup_bridge.rs` maps `AppEvent`. A sink trait duplicates the channel and makes "subscribe-before-spawn" unprovable.                                                                                                                                                                                                                                       |
| `MetadataPort` / store traits for finalizer tests                     | `MetadataStore::open_in_memory()` and `::disabled()` exist and already serve as the profile-writer test double. A trait adds about 15 forwarding methods for no coverage gain.                                                                                                                                                                                                                                                |
| Filesystem or clock traits                                            | Tests use tempdir files (`log_tail` tests do). The injection `timestamp` is a display string. Stamp it in the service and assert only shape. Note that `chrono` is a dependency of `crosshook-core` and `src-tauri` but not of `crosshook-app`. ### 3.3 `ProcessSpawner`: simpler than D4, and behaviour-preserving

D4 proposes a `SpawnedChild` trait object with boxed `take_stdout`/`take_stderr` and a `wait_with_cancel` that delegates to `supervise_child` with `process_group(0)`. Recommended instead:

```rust
// services/launch/spawner.rs
pub trait ProcessSpawner: Send + Sync {
    /// Spawns a fully built command. Production: `command.spawn()`.
    fn spawn(&self, command: tokio::process::Command) -> std::io::Result<tokio::process::Child>;
}
#[derive(Debug, Default)] pub struct TokioSpawner;
```

Why:

- **Concrete `tokio::process::Child` keeps every downstream user unchanged.** That covers pipe capture (`child.stdout.take()`), `child.id()` for the watchdog PID, and `wait()`. No `Pin<Box<dyn Future>>`, no `dyn AsyncRead`, no `async_trait`. The fake is about 20 lines: it records `command.as_std().get_program()/get_args()/get_envs()/get_current_dir()` and spawns `sh -c "<scripted output>; exit N"`. Real processes are already the house style for process tests (`jobs/process/tests.rs`). This also gives the trainer-parity test its captured `Command`s for free.
- **`supervise_child` + `process_group(0)` changes behaviour in three ways the issue does not ask for:**
  1. Today a session **without** gamescope is **not** killed on cascade or user reset. `drain_cancel_into_outcome` only records the reason, by design (`session/drain.rs:14-29`: "without flagging `was_killed`, because this path has no gamescope tree to tear down"). Wiring the registry cancel to a `killpg` would start killing `proton_run` trainers on game exit.
  2. Under Flatpak the launch builders use `host_command_with_env_and_directory` (`runtime_helpers/proton_command.rs:100,112`) and `host_command_with_env` (`script_runner/steam_helpers.rs:55`). These are the non-`--watch-bus` variants, so the README says `killpg` reaches only the proxy (`crates/crosshook-app/README.md` § Jobs). Native and Flatpak would then diverge.
  3. `process_group(0)` detaches the game from the CLI's terminal process group, so Ctrl-C in `crosshook launch` would no longer reach the game.

  Keep `child.wait()` as today. Kill semantics stay exactly where they are: core watchdog plus a per-session `ShutdownTarget`. "A session never kills another session's process tree" then holds by construction, because the service has no kill path at all.

- Hold it as `Arc<dyn ProcessSpawner>` (object-safe, since `spawn` is sync), so `Services` and Tauri `State<LaunchService>` stay non-generic.

### 3.4 Cascade test given today's semantics

"Linked-child cascade, sibling survives" is assertable without kills: start game A (fake: exit 0), trainer A (fake: `read` on a FIFO or `sleep` until signalled by the test) and trainer B for another profile. After A's `Exited`, assert the following:

- Trainer A's `WatchdogOutcome::reason() == Some(LinkedSessionExit)`, observed via its eventual report's `teardown_reason`.
- Trainer A's process is still alive, matching current non-gamescope behaviour.
- Trainer B's outcome is `None`, B is still in `sessions.sessions_for_profile`, and B's receiver has seen no events.

The test then releases both trainers and asserts each gets exactly one `Exited`. If the plan instead decides that non-gamescope trainers **should** die on cascade, that is a separate, explicit behaviour change and needs its own Flatpak story (lifecycle builders). It is not a side effect of the spawner seam.

### 3.5 Scope fences (leave as-is)

- The core builders' `should_skip_gamescope` (`script_runner/common.rs:52`, used at `proton_game.rs:39`, `proton_trainer.rs:74`, `steam_helpers.rs:76,276,340`) decides **command arguments**. That is a different responsibility from watchdog gating, and it has no method check. `preview/builder.rs:31-33` and `validation.rs:233` are preview/validation reads. Unifying them is a core refactor outside M1-05. Note it in the PR, but do not do it.
- Do not move `check_gamescope_session`, `launch_platform_status` or `check_game_running` (`queries.rs:95-112`). They are stateless one-line core passthroughs with nothing to orchestrate. `list_running_profiles` and `launch_reset_sessions` **do** move to the service, because the registry moves there.
- Do not change `DiagnosticReport`, schema or snapshot semantics. `session_id` lives on `LaunchEvent` and the adapter payload, not on the persisted report (issue storage boundary).

## 4. Interface design notes

- `start_game(&self, request: LaunchRequest) -> Result<LaunchSession, AppError>`. Same for `start_trainer`. Take the M1-01 `LaunchRequest` directly. Avoid new `GameLaunchRequest`/`TrainerLaunchRequest` wrappers unless they carry a field `LaunchRequest` lacks. Today both commands take the same `LaunchRequest` (`execution.rs:64`, `:241`), and a wrapper would only rename it.
- `LaunchSession { id: SessionId, kind: SessionKind, warnings: Vec<LaunchValidationIssue>, log_path: PathBuf, events: LaunchEvents }`. `log_path` is required, because the adapter's `LaunchResult.helper_log_path` (`shared.rs:66`) and the CLI need it.
- Every `LaunchEvent` variant carries `session_id: SessionId` explicitly (acceptance criterion). Injection data carries `session_kind` and `profile_name`, as `build_injection_log_event` does today (`shared.rs:127-150`, including the trim and `"Unknown profile"` fallback).
- Do not return the `Child` or any kill handle to callers. Cancellation goes through `reset_sessions(profile_name) -> usize` (today's semantics, `execution.rs:503-509`) and the registry only.
- The GameMode portal guard is held by the session task until after finalize, as `streaming.rs:44-51` does today. It is service-internal and not exposed.
