# Profile writer refactor — implementation recommendations

## Executive Summary

Land YAN-811 / [GitHub #532](https://github.com/yandy-r/crosshook/issues/532) as **one complete cutover PR**, implemented in dependency-ordered batches rather than separate partial releases. First freeze the current TOML and IPC behavior, then introduce the async application service and typed event contract, migrate independent operation families in parallel, and finally remove the command-layer orchestration and run the acceptance gates. The governing scope and acceptance criteria are [issue.md](issue.md); the eight-point estimate is not grounds to omit an operation family.

The safest design reuses `ProfileStore`, core diff/security helpers, `MetadataStore`, and the existing app `run_blocking` convention. `ProfileWriter::commit(name, mutation, reason)` should centralize successful mutation finalization without pretending favorites, deletes, renames, and ordinary TOML saves are identical operations. **Do not replace storage serialization or change revision hashing to achieve architectural uniformity.** Change all five frontend listeners and all mock event producers together; there must be no string/object compatibility shim.

This report is read-only code research and implementation guidance. No builds, tests, or smoke checks were run. Paths below are relative to `src/crosshook-native/` unless explicitly rooted at the repository.

## Implementation Recommendations

Recommended phasing — one PR, no deferred acceptance criteria.

### Phase 0 — characterize the pre-refactor behavior

1. Record a command inventory against every scope bullet in `issue.md`, including non-writing reads/exports, ProtonDB accept and both migration commands. Do not use “23 commands” as a stopping count if helper dependencies reveal more necessary edits.
2. Capture committed, fixed pre-refactor TOML fixtures for **save, rename, duplicate and rollback**, using deterministic profile names/paths. Include unknown disk keys, local overrides, active presets and representative hooks. Expected bytes must come from the pre-refactor behavior, not be regenerated by the new writer under test.
3. Characterize JSON return values and side effects separately from TOML: duplicate result name/profile, rename's boolean, rollback's optional revision ID, MangoHud companion operations, revision provenance, and disabled metadata behavior.
4. Agree the event wire representation and result/warning surface before the frontend and Rust agents start.

**Exit:** a reviewed compatibility matrix and fixed fixtures; acceptance tests can be added alongside each new service slice without inventing expected behavior from the implementation.

### Phase 1 — shared contracts and reusable writer pipeline

1. Establish `services/profiles/` with async operation entry points and one private commit/finalization path. Move response/request DTOs out of the shell where required, retaining their existing Serde casing and command parameter names.
2. Build over cloned `ProfileStore`, `SettingsStore`, `MetadataStore` and `EventBus`; use `run_blocking` inside the service. Keep blocking load–mutate–persist–observe–capture–invalidate work together rather than offloading only the final `save`.
3. Define operation-specific mutation outcomes: affected names, current profile when relevant, revision source/rollback lineage, metadata synchronization kind/duplicate ancestry, and whether health is affected. A favorite is SQLite-only, not a dummy TOML write; delete must not attempt to reload a deleted profile.
4. Add `ProfileChangeReason` and `AppEvent::ProfilesChanged { reason, names }`. Define typed serializable Tauri payloads and a matching frontend type. Establish state-before-publish ordering, and no publication for failed validation or failed primary persistence.
5. Add a schema-neutral health invalidation store operation if necessary. `metadata/health_ops.rs:1–32` currently exposes upsert/load/lookup only; migration currently recomputes/upserts rather than actually removing a stale snapshot.
6. Register the service in bootstrap and Tauri state; bridge app profile events. This is shared-file work owned by one integration agent, not edits every slice repeats.

**Exit:** stable internal interfaces, payload examples and test helpers unblock independent implementation. No command may depend on a shim as the final PR state.

### Phase 2 — independent operation-family migrations

Run the ownership slices below in parallel after Phase 1's interfaces are stable:

- Lifecycle, defaults, art, summaries/export/import and favorites.
- Launch section updates, command arguments, bundled/manual presets.
- History, diff, rollback and known-good.
- ProtonDB acceptance and Proton migration application.
- Frontend listener filtering and browser mock contract updates (independent owners).

Each owner adds tests in its own app-service test module and removes the corresponding shell orchestration. Reuse core persistence/validation algorithms; extract a narrowly reusable core mutation helper only where an existing “validate + persist” function otherwise forces a second write or a bypass around the common finalization path.

### Phase 3 — integrated clean cutover

1. Migrate every remaining caller of removed shell helpers, notably Lutris, and remove old `capture_config_revision`, generic string `emit_profiles_changed`, and section-save implementations/re-exports. Retain `apply_collection_defaults` and its existing collection tests in their current boundary: collections are explicitly M1-35, not this issue.
2. Resolve the summary/load collection-context boundary without moving collection defaults into the writer: service owns profile reading/projection; any temporary shell collection composition remains explicit and intentionally unchanged, not a second mutation pipeline.
3. Check the operation matrix: correct reason, concrete names, primary persistence, metadata source/identity, revision source, health policy, and result for every entry. No double event publication from wrapper + service, no duplicate persistence from core convenience method + writer.
4. Preserve frontend rename selection and launcher re-export behavior. A new rename event can arrive before the command resolves; list refresh must not auto-select an unrelated profile and overwrite the renamed selection/draft.
5. Update the existing architectural documentation to describe the writer, event object and degraded save semantics; update mock documentation if a shared emission helper is added. No user-facing TOML or SQLite migration documentation is needed because no format/schema migration is allowed.

### Phase 4 — final PR acceptance gates

The main implementation agent runs verification once after all slices are integrated, not concurrently against partially edited files:

- `cargo test --manifest-path src/crosshook-native/Cargo.toml -p crosshook-app`: all operation families, real tempdir stores, metadata enabled and disabled, fixed TOML goldens, dedupe/lineage/diff/launcher tests.
- `cargo test --manifest-path src/crosshook-native/Cargo.toml -p crosshook-core`: required if core mutation extraction or health invalidation changes are substantive; retain lower-level storage/diff/security coverage.
- Tauri crate checks/tests using the package declared in its manifest: async command registration, moved imports and bridge payload tests. Do not assume passing app tests compiles the shell.
- From `src/crosshook-native/`: `npm test`, `npm run test:smoke`; also type checking/build according to repository checks. `package.json:16–25` confirms Vitest, Playwright and strict typecheck scripts already exist; no frontend test framework bootstrap is needed.
- Browser smoke is necessary but synthetic: reverify actual Tauri behavior, especially the Rust-to-JS payload and launcher cleanup/re-export, before merge.
- Run applicable existing dependency/startup/host-gateway checks when those boundaries are touched, and conduct full integrated review before committing. Record only checks actually exercised.

## Event and listener recommendation

### Proposed exact wire shape

The issue mandates an object and the Rust reason enum, but does not prescribe Serde tagging. Use an internally tagged reason (aligned with the technical-design recommendation):

```json
{"reason":{"kind":"favorite_toggled"},"names":["A"]}
```

```json
{"reason":{"kind":"renamed","from":"Old"},"names":["New"]}
```

The reason union is `saved | deleted | renamed { from } | duplicated | favorite_toggled | rolled_back | preset_applied | imported | migrated`, represented by `reason.kind` in TypeScript. Normal writes carry concrete canonical affected names; duplicate names the new copy, delete names the removed profile, and rename names the new profile with the old identity in `from`. A successful batch migration should publish one event with de-duplicated names of applied profiles only; failed/already-valid entries do not appear. `ProtonDB` acceptance fits `Saved` while retaining `ProtonDbSuggestionApply` as its revision source.

For bounded bus lag, reserve `names: []` as a **documented full-resync notification**, emitted conservatively as `Saved` by the bridge on `AppEvent::Resync`. The present startup bridge only replays startup completions (`startup_bridge.rs:135–146`); silently ignoring profile lag would leave stale UI. This sentinel is a proposed runtime contract, not a new persisted datum or a legacy-payload fallback. Do not interpret ordinary empty successful batches as resyncs.

### Five listeners that must change together

| Listener | Location | Recommended behavior |
| --- | --- | --- |
| Health | `src/hooks/useProfileHealth.ts:238–259` | Decode typed payload; return before `batchValidate()` for `favorite_toggled`. Preserve existing startup/launch/version behavior. Other reasons may retain batch refresh for this refactor; targeted validation is not required to satisfy the issue. |
| Main profile/favorites state | `src/hooks/useProfile.ts:232–252` | Favorite event reloads favorites, not the entire profile list. Other events refresh names and favorites as needed without blindly reloading dirty editor state. |
| Profile summaries | `src/hooks/useProfileSummaries.ts:38–53` | Favorite event requires no summary fetch; the DTO has no favorite field. Retain normal refresh for content/identity changes. |
| Library summaries | `src/hooks/useLibrarySummaries.ts:63–80,82–86` | Skip favorite-triggered summary fetch; existing favorite-state effect already updates card flags without IPC. |
| Community imported names | `src/hooks/useCommunityProfiles.ts:432–455` | Skip favorite-triggered membership rescan; continue refreshing when profile existence/import identity can change. |

All five currently subscribe with `subscribeEvent<string>` and ignore the payload. Merely changing the generic type does not implement the performance acceptance criterion. `src/lib/events.ts:7–25` forwards `unknown` mock payloads without validation, so typed producers plus direct wire-shape assertions are needed to catch mock drift.

## Alternatives and recommendation

| Alternative | Assessment |
| --- | --- |
| Keep the string reason and add affected names elsewhere | **Reject:** fails the mandated object payload and creates two notifications that can race. |
| Accept both strings and objects during migration | **Reject for the final PR:** one repo, one PR can migrate all consumers; compatibility parsing hides missed callers and mock divergence. |
| Flat `{reason: 'renamed', from, names}` versus nested tagged reason | Either can express the domain, but nested `{reason: {kind, from?}, names}` maps the Rust enum directly and makes rename-only data a discriminated union. Recommend nested; require explicit Serde tags and matching TS shape. |
| Leave writes in Tauri and move only revision capture | **Reject:** recreates repeated load/mutate/save/finalize orchestration and fails thin-command acceptance. |
| Move raw TOML/SQL into `crosshook-app` | **Reject:** orchestration belongs in app; durable serialization/atomic writes, revision rows/security and health storage stay in core. No schema redesign. |
| One generic arbitrary public closure API | Avoid exposing it as the service's shell contract: it makes invariants/provenance caller-defined. Prefer typed async operations over a private cohesive `commit` pipeline; use closures internally only when they preserve existing core validation reuse. |
| Force every operation through “load, save TOML, revision” | **Reject:** favorites are metadata-only, delete removes files, rename preserves identity and lineage. Share finalization policy, not fictitious writes. |
| Reuse a core convenience method that already saves, then call writer save again | **Reject:** duplicate IO, companion side effects and possible revision snapshot mismatch. Extract/reuse mutation-only behavior where necessary, preserving one authoritative write. |
| Split into backend-first and frontend-later PRs | **Reject:** violates requested one-PR delivery and ships a broken event contract. Internal batches may be incomplete temporarily; final branch must be fully cut over. |
| Add targeted per-name health batching/coalescing now | Not necessary for the acceptance criterion. Safely skip favorite health work first; names carry future/in-scope consumer context without silently expanding this refactor into a new health scheduling feature. |

## Key decisions to settle before implementation

1. **Exact event representation and names semantics — recommended above.** Serde internal tag `kind`, snake_case values, new name in rename `names`, old name in `reason.from`, concrete names for normal commits, empty names only for conservative lag resync. Freeze examples for Rust/F/G simultaneously.
2. **Writer mutation API and persistence policies.** Keep typed async public methods; use private operation-aware commit dispatch. Decide the smallest core mutation extraction needed so launch section and migration paths write once without changing persistence side effects. Do not add a general plugin/callback framework.
3. **Health invalidation versus recomputation.** Recommend a small core deletion/invalidation operation, not invoking full health validation inside every commit. Favorite bypasses both. Decide treatment of rename/delete snapshots while retaining stable profile IDs; all policies remain within the existing table/schema.
4. **How successful-but-degraded saves surface warnings.** Current capture simply skips unavailable metadata (`shared.rs:121–123`), which does not meet “logged and surfaced.” Choose a runtime-only warning delivery/read surface that retains current command success contracts and can be asserted from frontend tests. The issue does not prescribe it; do not silently change `Result<(), String>` into an uncoordinated new envelope or merely log and claim completion. Startup's frozen degraded report alone does not prove a per-save failure was surfaced.
5. **Collection-aware reads boundary.** `profile_load` and summaries currently call `apply_collection_defaults`; collections and that helper are explicitly excluded. Recommend preserving shell composition and existing corrupt/fail-open behavior, with app-owned raw reading/projection, rather than moving collection logic under the profile writer. Document the intentional temporary boundary.
6. **Legacy helper-dependent imports.** Minimum Lutris integration is required to delete obsolete shell helpers and emit the new payload. Broader import/discovery rewrites and community/collection exchange redesigns are not implied. Inventory actual helper consumers before removal and assign each to E or A.
7. **Concurrency/no-op semantics.** Existing store documents unsynchronized last-completed-write-wins. Preserve that unless an explicit requirement changes it; do not add a global write queue by assumption. Decide event policy for no-op same-name rename/already-valid migration/repeated favorite requests; failed/no-change operations must not falsely report unrelated profile changes.

## Storage boundary and persistence/usability

- **TOML:** game profiles retain existing bytes for equivalent save/rename/duplicate/rollback operations and the same editable format. Settings-driven creation defaults and rename's last-used preference continue using existing `settings.toml`; no new setting is necessary.
- **SQLite:** profile identity/favorites, preset provenance, config revision rows/hash/signature/lineage and health snapshots stay in the existing metadata DB. Schema version and table definitions remain unchanged. An invalidation query is behavior over the existing health table, not a migration.
- **Runtime only:** typed change events, affected names, warning delivery and any counters/test instrumentation. No persisted event log, task table, telemetry or cache is introduced.
- **Compatibility/offline:** no migration; offline behavior remains unchanged. Users keep editing profiles via UI or TOML and use the same history/diff/rollback/known-good controls. No new UI layout or scroll-container work is required by this refactor.
- **Degraded persistence:** unavailable metadata cannot undo a successful TOML save; revisions are skipped and a warning is logged and surfaced. Metadata-dependent reads/actions remain explicitly unavailable where no real result can be produced. Tests must distinguish primary-store failure from advisory metadata failure, and verify existing user-visible actions still work without fabricated history or silent fallback data.
