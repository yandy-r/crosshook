# Profile writer refactor — UX behavior and refresh research

## Executive Summary

YAN-811 / [GitHub #532](https://github.com/yandy-r/crosshook/issues/532) is an application-layer refactor, not a UI redesign. Preserve profile editing, selection, rename/undo, launcher re-export, history, favorites, and offline behavior; the intentional visible improvement is fewer redundant rescans/loading transitions. The acceptance criteria in [issue.md](issue.md) govern this report.

**Key decisions:**

- `FavoriteToggled` must not call `batch_validate_profiles` or otherwise recheck filesystem health. It must still reload authoritative favorites and update **every favorite presentation**, including Health Dashboard stars and favorite-first ordering, which currently depend on metadata embedded in the health summary.
- For the initial cutover, skip health revalidation for **only `FavoriteToggled`** among the nine specified mutation reasons. Keep health refresh for save, delete, rename, duplicate, rollback, preset, import, and migration. Rename/delete do not necessarily change file health, but they change the identity/membership of the name-keyed health summary; silently skipping them leaves stale rows unless an explicit remap/removal path exists.
- Keep list/summary refresh for all non-favorite mutation reasons. Favorite changes require a favorites refresh, not a TOML/name/summary rescan. `useLibrarySummaries` already applies favorites separately without a summary fetch.
- Reuse the app-level, session-dismissible `MetadataStatusBanner` for a disabled metadata store; make the consequence explicit: **profile files still save, but configuration snapshots are not recorded**. Do not convert successful TOML persistence into a failed save, and do not show a new toast on every autosave.
- Existing Library favorite UI is already optimistic. Preserve it; **do not introduce, expand, or redesign optimistic UI** in this issue.

**Confidence: High** for current behavior and the favorite-health consistency risk: directly read the five listeners, their consumers, mutation commands, history UI, and metadata operations. **Confidence: Medium** for the proposed payload spelling and warning transport: the issue defines semantic reasons and an object payload, but not Serde tagging or a new partial-success result contract. Those are implementation decisions, not current APIs.

## Current event contract and listener map

Native `src-tauri/src/commands/profile/shared.rs:68–72` emits a **string**, e.g. `"favorite-updated"`, with no affected name. All five React listeners subscribe as `subscribeEvent<string>` and ignore the payload. Browser mocks already send objects, but the objects are a different contract: `{ name, action }`, e.g. `{ name: trimmed, action: 'favorite' }` in `src/lib/mocks/handlers/profile-mutations.ts:257–269`. Ignoring payloads currently masks that mismatch.

`src/lib/events.ts:7–24` is the shared event adapter: Tauri listeners receive the backend event; browser listeners receive an event wrapper with `payload` cast to the requested generic. The generic is not runtime validation. Migrate all listeners, mocks, and tests together to a shared object contract; do not retain string/object compatibility shims.

## User Workflows

### Workflows to preserve

### 1. Save and section autosaves

1. The UI persists a draft and explicitly refreshes names/reloads the saved profile (`src/hooks/profile/useProfileCrud.ts:327–330`). Native full save emits `"saved"` (`src-tauri/src/commands/profile/lifecycle.rs:203–225`).
2. Five listeners then perform the work above. The shared action handler also invokes `revalidateSingle` after save (`src/hooks/profile/useProfileActions.ts:182–187`), so save currently has overlapping health paths.
3. Section saves are not all equivalent today. `save_profile_section` (`src-tauri/src/commands/profile/shared.rs:242–277`) saves, observes, and captures a revision but does not emit. The issue's unified pipeline intentionally adds consistent notifications across these paths.

**UX risk:** adding events for every autosave without coordinated listener filtering can increase summary reloads and health checking. Conversely, treating all `Saved` events as harmless would stale changed paths, launch method, hooks, art, or network-isolation display. The reason is intentionally broad, so do not infer which fields changed from it.

**Preserve:** existing saved/error statuses, dirty-state clearing, selected profile reload, and local editor values. A list notification is an invalidation signal, not permission to blindly reload the active editor and overwrite unsaved edits.

### 2. Favorite toggle and Favorites filter

- `useProfileCrud.toggleFavorite` (`src/hooks/profile/useProfileCrud.ts:96–115`) waits for `profile_set_favorite`, then awaits `loadFavorites`. The event listener also calls `loadFavorites`, creating redundant reads.
- Library already immediately updates the card's `isFavorite` and reverts on rejected mutation (`src/components/pages/LibraryPage.tsx:291–303`). This existing optimistic path is outside redesign scope.
- Native favorite mutation only updates SQLite (`src-tauri/src/commands/profile/favorites.rs:7–27`; core `metadata/collections.rs:167–205`). It does not change a TOML field checked by profile health.
- `useLibrarySummaries.ts:78–86` propagates authoritative `favoriteProfiles` into cards. Preserve that effect so the Favorites filter and collection-modal cards agree after persistence.

**Critical hidden consumer:** `crates/crosshook-app/src/services/health/enrich.rs:59,122–136` embeds `metadata.is_favorite` in health reports. Health Dashboard displays it (`src/components/pages/HealthDashboardPage.tsx:424–426`), uses it to pin favorites before other sort fields and for favorite sorting (`health-dashboard/useHealthDashboardState.ts:94–97,123–127`), and labels expanded rows (`health-dashboard/IssueBreakdownPanel.tsx:124`). Simply returning early in the health listener makes these stale across route changes.

**Recommendation:** after the existing authoritative favorites reload succeeds, derive/overlay favorite presentation for the shared health summary or its consumers from that same favorite set. Do not call `get_profile_health` as a substitute: this is still an avoidable health recheck. A post-persistence projection is not new optimistic UI. Do not reset health status, `checked_at`, issues, trends, totals, or metadata availability while applying a favorite projection.

**Latency inference:** the desired improvement is removing competing whole-list and filesystem work around an unchanged toggle interaction. Do not add new spinners, delays, or a new favorite mutation protocol.

### 3. Rename, undo, and launcher re-export

- Native rename (`src-tauri/src/commands/profile/lifecycle.rs:293–347`) renames the file/metadata identity, cleans old launchers, updates launcher display name and last-used setting, and returns `had_launcher`. It currently **does not emit**. Native duplicate (`:268–290`) likewise returns the new name/profile without emitting.
- The initiating UI explicitly refreshes names, loads the new name, and reloads favorites (`src/hooks/profile/useProfileCrud.ts:375–400`). Duplicate explicitly refreshes and selects the returned copy (`:355–372`).
- `useProfileNotifications.ts:138–180` shows rename success/Undo and sets pending launcher re-export only after a successful command result with `hadLauncher`. Undo calls the same rename API in reverse. `ProfilesOverlays.tsx:196–207` uses a polite status toast with Undo/dismiss controls. Preserve this result contract and behavior; the new event must not replace the command result or generate a second success toast.

**Race inference:** the new service event can arrive before the initiating command promise resolves. `refreshProfiles` can see the old selection absent and auto-select a different first profile before `renameProfile` explicitly loads the new name. This can cause transient selection/badge changes or clobber the intended selection. Handle `Renamed { from }` with the explicit identity mapping and protect in-flight rename selection; never infer rename as delete-plus-random-auto-selection.

**Stale detail risk:** `LibraryPage.tsx:309–324` finds inspector selection by its old name; `:372–373` resolves `detailName` with a stale `detailSummarySnapshot` fallback if no matching row exists. A name-list refresh alone cannot repair these identities. Test open Hero Detail/inspector rename and Undo; consume `from`/new name where necessary to preserve the current logical selection, not merely the list contents. Avoid scope expansion into a general selection-state redesign.

**Health policy:** rename must refresh/reconcile name-keyed reports and preserve trend/cache identity expectations. For this issue, continuing batch validation is the boring safe behavior; skipping it requires an explicit, tested remap of report names, cached snapshots, counts, and display keys. Delete similarly requires removal/count reconciliation, not just a no-op health listener.

### 4. Delete and duplicate

- Delete displays existing launcher-aware confirmation (`src/hooks/profile/useProfileCrud.ts:403–430`), then calls the backend and finalizes deletion (`:433–450`). `finalizeProfileDeletion`, `:228–258`, clears last-used state, refreshes names/favorites, selects the next profile, or resets to an empty editor.
- Native cleanup is best effort; primary profile deletion still succeeds (`src-tauri/src/commands/profile/lifecycle.rs:229–250`). Preserve this distinction.
- Delete/duplicate events must refresh summaries, imported-name markers, and health membership. Duplicate names the new copy, not only the source. Do not globally auto-select a duplicate just because any listener observes the event: the initiating command owns selecting its returned result.

### 5. History, diff, rollback, and known-good

- `useProfileHistory.ts:33–124` owns request counts/errors. Rollback awaits persistence, reloads the named profile with the specific error context “Rollback applied, but reloading the profile failed,” then calls its completion callback.
- Backend rollback checks metadata availability, ownership/integrity, restores TOML, captures lineage, then emits (`src-tauri/src/commands/profile/config_history.rs:260–341`). Keep error/result casing and semantics.
- `ConfigHistoryPanel.tsx:150–182` separates “Snapshot restored” success from **history refresh failure after successful restore**. It retains success and shows `historyRefreshWarning`; do not regress this to “No changes were applied.” Its status/alert live regions and contextual warning are at `:250–311`.
- Known-good marking updates/reloads the history list locally (`ConfigHistoryPanel.tsx:186–205`). It does not mutate profile TOML and currently emits no `profiles-changed` (`config_history.rs:347–378`). History read, diff, TOML export/preview, and known-good marking should not become `Saved` events merely because their APIs move into the same service.

### 6. Preset, import, ProtonDB accept, and migration

These can change effective launch fields or add profiles and must refresh summaries and health. Core health checks paths, method, enabled injection/hooks, optional icon/working directory, and prefixes (`crates/crosshook-core/src/profile/health/profile.rs:18–151`); enrichment additionally uses dependencies, launch/version metadata, and offline readiness (`services/health/batch.rs:12–139`, `enrich.rs:35–144`). A “preset does not change paths” shortcut is not a valid reason-level guarantee.

Migration already has explicit UI revalidation (`src/hooks/useProtonMigration.ts:44–83`): single apply uses `revalidateSingle`, batch apply uses `batchValidate` when at least one entry applied. Adding service events must not produce a second scan for the same successful action. Batch events should contain only actually applied names; already-valid/failed entries are not successful mutations.

## Recommended object contract and refresh matrix

The issue mandates `AppEvent::ProfilesChanged { reason: ProfileChangeReason, names }` and an object payload, but leaves enum tagging unspecified. A concrete proposal aligned with a discriminated TypeScript union:

```json
{ "reason": { "kind": "favorite_toggled" }, "names": ["Game A"] }
```

```json
{ "reason": { "kind": "renamed", "from": "Old name" }, "names": ["New name"] }
```

This is **proposed**, not the current wire contract. Carry canonical affected names after primary persistence: new name for duplicate, deleted name for delete, new name plus `from` for rename, all applied names for batch migration. A successful failed/no-op validation path must not produce a misleading mutation notification. Agree any bus-lag/full-resync sentinel explicitly; a lag resync must conservatively refresh health and lists, never masquerade as a favorite-only event.

**Must/should boundary:** the favorite skip and all non-favorite summary/name invalidations are required behavior for the cutover. Community membership skips for preset/migration/rollback are safe secondary reductions once their exact invariants are kept; preserving current conservative community refresh is acceptable. Do not add new changed-field detection, partial health caches, or identity-remap machinery just to skip additional scans. `names` enables correct identity and future targeting, not a requirement for a new incremental data layer.

### Warning surface recommendation

**Use a banner for ongoing degraded capability, not a repeated toast.** `MetadataStatusBanner.tsx:28–49` is app-level, session-dismissible, `role="status"`, and has an accessible dismiss label. It is already mounted in `AppShell.tsx:618`, alongside status toasts. Its reason is clamped to 200 characters, while backend startup degradation sanitizes the reason (`crates/crosshook-app/src/bootstrap/stores.rs:145–160`). Reuse these privacy and brevity constraints.

A one-off contextual partial-success message can follow the existing `ConfigHistoryPanel` restore/history-refresh warning pattern. Rename toast (`ProfilesOverlays.tsx:196–207`) and shell toasts (`AppShell.tsx:603–617`) establish polite `role="status"`/`aria-live="polite"` notification conventions, but their transient nature is a poor sole warning for revisions being disabled for the entire session. No global notification framework or blocking dialog is necessary.

**Accessibility constraint:** the history panel uses a modal focus trap and modal semantics (`ConfigHistoryPanel.tsx:69–83,244–255`). Existing accessibility test `src/__tests__/a11y/modals.a11y.test.tsx:79–115` explicitly notes shell siblings are hidden/inert while the modal is open. Therefore a shell banner alone is not sufficient contextual explanation inside an already-open History modal. Preserve its existing local error/warning route; do not move focus or open another modal just to announce metadata degradation.

## Prioritized recommendations

### Must

1. Migrate all five listeners, all mock emitters, and event tests to one typed object payload; carry names and rename `from`; publish after primary persistence.
2. Guarantee `FavoriteToggled` causes **zero** `batch_validate_profiles` calls and no substitute filesystem health check. Keep favorite state current in Library, Favorites filters, collection cards, Health Dashboard stars, expanded labels, and favorite-first ordering using authoritative favorites after persistence.
3. Keep list/summary invalidation for rename/delete/create/save/duplicate/import/rollback/preset/migration; preserve existing selection, draft ownership, rename Undo, launcher cleanup and re-export result behavior. Protect rename against its new event arriving before its command resolves.
4. Preserve successful TOML writes with disabled metadata and visibly explain skipped snapshots. Log the warning, reuse the metadata banner, retain metadata-dependent history/rollback unavailable errors, and never warn for SHA-256 dedupe.
5. Preserve error distinctions: before-write failure vs applied-but-reload/history-refresh failure. No fake fallback history or silently fabricated favorite persistence.
6. Preserve existing Library optimistic toggle unchanged; new optimistic UI is out of scope. No TOML/schema changes or new persisted warning preferences.

### Should

1. Make the event-driven health refresh the single owner for successful save/rollback/migration invalidation, coordinating/removing redundant explicit post-mutation scans without removing manual Refresh/Recheck, startup handling, launch-complete, or version-scan triggers. Avoid double batch + single checks from existing action callbacks.
2. On `FavoriteToggled`, have `useProfile` reload only favorites; both summary hooks and the community imported-name listener return without list IPC. Retain the existing `favoriteProfiles` enrichment effect.
3. Keep previous health reports visible while legitimate checks run. The reducer currently retains summary; Inspector only shows loading without a report (`GameInspector.tsx:150–165`), and Dashboard skeletons are initial-only (`HealthDashboardPage.tsx:150`). Do not replace these with blank badges. Existing “Checking profile health…” status (`:227`) should no longer appear on favorite-only updates.
4. Use precise degraded banner copy and contextual history errors; avoid per-autosave toast storms. Distinguish a persistent disabled-store condition from an individual revision-capture failure.
5. Keep one event for a successful migration batch with applied names; define conservative bus-lag refresh behavior so dropped events cannot strand stale lists.

### Nice (only if no additional architecture or scope)

1. Skip community name rescans for `PresetApplied`, `Migrated`, and `RolledBack` once existing-profile identity invariants are explicit; this is lower priority than the required favorite skip.
2. Reuse a small table-driven pure reason policy shared by tests rather than duplicating reason-string comparisons in five hooks. Avoid a generic event/cache framework.
3. Add assertions that favorite-only changes leave health `checked_at`, issue counts, trend, and validated time unchanged, making the performance improvement user-observable without new telemetry.

## Alternatives, uncertainties, and gaps

- **Alternative: skip rename/delete health checks too.** Technically possible with complete name remap/removal and count/cache reconciliation, but not a drop-in listener filter. Current state is name-keyed and `revalidateSingle` adds/replaces one row without removing an old name (`useProfileHealth.ts:79–101`). Prefer conservative batch behavior rather than expanding this refactor into incremental health state management. **Confidence: High.**
- **Alternative: use a warning toast for every successful degraded save.** Reject: section autosaves can repeatedly emit; the degradation is persistent and already has a dismissible app-level banner. A contextual one-off partial-success warning is suitable only for a distinct per-operation failure. **Confidence: Medium**, a design recommendation grounded in existing surfaces, not a usability study.
- **Payload spelling is not yet established.** The proposed `reason.kind` shape needs Rust bridge/Serde and TypeScript agreement. The issue requires semantics, not this exact tagging. **Confidence: Medium.**
- **Dynamic metadata failure transport is unspecified.** `useMetadataStoreStatus` fetches once, and `capture_config_revision` currently collapses dedupe/skip/error into `None`. A runtime revision warning cannot reliably derive from `new_revision_id === null` or from the mount-only banner if store status is otherwise OK. Decide a concrete existing-compatible status/result path in implementation; do not invent a production event here. **Confidence: High** about the gap; no API implementation is claimed.
- **Actual flicker and latency are unmeasured.** Batch loading preserves summary, so it is inaccurate to claim badges always disappear. The definite unnecessary changes are loading status, recheck work, and validated time; Inspector protects existing reports while Dashboard shows a checking pill. Browser/native measurements would establish visible timing. **Confidence: High** in control flow, **Low** in any unmeasured duration claim (none asserted).
