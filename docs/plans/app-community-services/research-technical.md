### Shared exact error surfaces to preserve where safe

- Community containment (`$T/commands/community.rs:140-217`): `cannot resolve community profile path '{path}': {error}`; `community profile path '{path}' is not a file`; `community profile path '{path}' must point to a .json file`; `community profile path '{path}' is not inside a known tap workspace`. New service `AppError` construction sanitizes/home-redacts these; the containment predicate, not exposure of host paths, is the security contract.
- Tap errors (`$C/community/taps/types.rs:81-126`): `tap url cannot be empty`; `invalid tap url: {url}`; `invalid branch name (allowed: a-z A-Z 0-9 / . _ -, max 200 chars, must not start with '-'): {branch}`; `invalid pinned commit (must be 7-64 hex characters): {commit}`; `failed to {action} '{path}': {source}`; `failed to {action} with `{command}`: {stderr}`; index errors `failed to {action} '{path}': {source}` / `failed to parse community profile '{path}': {source}` (`$C/community/index.rs:31-61`). Prefer fixed sanitized app messages for I/O/git/index failures rather than re-exposing commands, stderr, SQL, or absolute paths.
- Community exchange (`$C/profile/exchange/error.rs:30-53`): `failed to {action} '{path}': {message}`; `failed to parse community profile '{path}': {message}`; `invalid community profile: {message}`; `unsupported community profile schema version {version}; supported version is {supported}`; profile-store message. Existing `From<CommunityExchangeError> for AppError` already removes caller paths and maps validation (`$A/error.rs:144-167`).
- Lutris (`$C/profile/lutris_import/error.rs:8-53`): `failed to {action} '{path}': {message}`; `failed to parse Lutris config '{path}': {message}`; `failed to read Lutris pga.db: {message}`; profile-store message. No `AppError` conversion exists yet.
- External source validation (`$C/discovery/models.rs:155-190`): `source_id is required`; `source_id must be 64 characters or fewer`; `source_id must contain only alphanumeric characters, underscores, or hyphens`; `display_name is required`; `display_name must be 128 characters or fewer`; `base_url must be a valid HTTPS URL with a host`; `unknown source_type {type:?}; known types: {types:?}`. These contain user input but no host paths; retain via `AppError::validation("external_source", text)`.

## 3. Existing app/core building blocks

- There is no `AppContext` type. `BootstrappedApp` owns `Stores`, `Services`, startup state and derefs to `App`; accessors are `stores()` and `services()` (`$A/bootstrap/app_bootstrap.rs:27-79`). `Stores` already has settings, profiles, community taps and metadata (`$A/bootstrap/stores.rs:36-47`). `App::jobs()` supplies the shared shutdown-linked `JobRegistry`.
- `Services::new(&Stores, EventBus, Handle, JobRegistry)` is the single construction point (`stores.rs:88-147`). Services are cheap `Clone` structs with positional `new`, async public methods and `run_blocking` for store/filesystem work (`$A/services/mod.rs:1-8,59-67`). Tauri obtains them with `State<'_, SomeService>` after `.manage(services.foo.clone())` (`$T/lib.rs:36-59`), then awaits and maps `error.message().to_string()` (example `$T/commands/collections.rs:12-25`).
- `SettingsService::load/update` exists but its generic infallible update cannot directly express duplicate/missing-source errors (`$A/services/settings.rs:233-289`). Keep the raw `SettingsStore` inside community/discovery for their atomic fallible updates; do not route through the UI-wide settings save request.
- `ProfileWriter::{import_community, import_lutris, accept_protondb_suggestion}` already supplies locking, single persistence, metadata observe/revisions, warnings and events (`$A/services/profiles/imports.rs:1-6`; `suggestions.rs:1-5`). Services should compose the same writer clone used in `Services`, not construct another writer.
- `run_job` gives a non-exclusive supervised job and `Cancelled` on registry/job cancellation (`$A/services/mod.rs:69-113`). **It does not interrupt the blocking closure**; after returning `Cancelled`, `sync_many` and its git child can continue. `JobRegistry::cancel(&JobId)` and `JobHandle::cancel()` exist (`$A/jobs/registry.rs:219-234,462-465`), but no generic cancel IPC/UI exists.
- `jobs::supervise_child` really kills a process group on cancellation, but requires `process_group(0)` and lifecycle host commands (`$A/jobs/process.rs:51-87`). Current git uses synchronous `host_std_command_with_env(...).output()` (`$C/community/taps/git.rs:24-35,148-177`), which cannot satisfy the cancellation AC merely by moving into `run_job`.
- Core APIs to reuse unchanged where possible: `CommunityTapStore::{resolve_workspace,sync_many,index_workspaces}` (`$C/community/taps/store.rs:44-91`); exchange preview/export; Lutris preview; metadata catalog/list/index/offline methods (`$C/metadata/community_ops.rs:9-90`); `degraded_catalog_from_taps`; external search and version matching; ProtonDB lookup/cache and suggestion derivation.
- `AppErrorKind` already includes `Validation`, `NotFound`, `Conflict`, `Unavailable`, `Io`, `Cancelled`, `Internal` (`$A/error.rs:5-25`). Existing conversions cover settings, profile, community exchange and metadata (`error.rs:99-260`). Add explicit conversions/mappers for `CommunityTapError` and `LutrisImportError`; never use raw `Display` indiscriminately for path-bearing errors.

## 4. Recommended service contracts and wiring

All methods below are `async -> Result<T, AppError>`; filesystem/SQLite/settings portions run in one `run_blocking` closure per operation. Return existing core DTOs so serde remains unchanged. `force_refresh` is a `bool` internally; adapters retain `Option<bool>` and apply `unwrap_or(false)`.

CommunityService::new(settings, taps, profiles, metadata, writer, jobs)
  add_tap(tap) -> Vec<CommunityTapSubscription>
  remove_tap(tap) -> Vec<CommunityTapSubscription>       // service-only; no new Classic command
  list_profiles() -> CommunityProfileIndex
  export_profile(profile_name: String, output_path: String) -> CommunityExportResult
  prepare_import(path: PathBuf) -> CommunityImportPreview
  import_profile(path: PathBuf) -> CommunityImportResult
  sync() -> Vec<CommunityTapSyncResult>
  list_indexed_profiles() -> Vec<CommunityProfileRow>

LutrisService::new(profiles, writer)
  prepare_import(directory: Option<PathBuf>) -> LutrisImportPreview
  import_profiles(entries: Vec<LutrisImportEntry>) -> LutrisImportResult

DiscoveryService::new(settings, metadata, taps)
  catalog(query: CatalogQuery) -> CatalogPage
  search_external(query: ExternalTrainerSearchQuery) -> ExternalTrainerSearchResponse
  check_version_compatibility(profile_name: String, trainer_game_version: Option<String>)
      -> VersionMatchResult

  add_external_source(source: ExternalTrainerSourceSubscription)
      -> Vec<ExternalTrainerSourceSubscription>

ProtonDbService::new(metadata, profiles)

- `import_profile` performs containment **before** calling `writer.import_community`, then unwraps `ProfileCommit::into_output`; `import_profiles` does the same for Lutris. Accept stays directly on `ProfileWriter` in the Tauri adapter. Dismiss moves as-is (30-day retention, disabled-metadata behavior, and exact validation text), then becomes async off the blocking thread.
- Add four fields to `Services`, four `.manage()` calls, and exports in `services/mod.rs` (optionally crate-root reexports matching existing services). Build one local `ProfileWriter` in `Services::new`, clone it into `CommunityService`/`LutrisService` and the `profiles` field; clone `jobs` for community. Keep raw store `.manage()` entries needed by unrelated legacy commands.
- Use a **non-exclusive** `JobSpec::new("community-sync")`. An exclusive global key would make overlapping Browse/UI/startup/native callers fail with user-visible `Conflict`, the regression avoided by M1-33 (`docs/plans/app-onboarding-services/decisions.md` D2). The existing awaited `community_sync` IPC result stays unchanged.

### Sync/offline/cancellation requirements

1. `sync()` must load taps and execute git off the IPC/caller thread, then perform index → offline upsert → `last_sync_at` backfill in that order, warning-only exactly as today. Clear result `extra`. Do not hold an exclusive key.
2. Before sync and external search, honor `AppSettingsData.offline_mode` (and the selected network probe policy) with `AppErrorKind::Unavailable`; this is an intentional change from external search's DTO-only offline response required by the issue. Keep catalog/indexed reads and ProtonDB's cache-first/stale-fallback DTOs available.
3. To make “sync can be cancelled” real, introduce an async tap-sync driver whose git execution is supplied by the app layer. The app runner uses tokio process + `process_group(0)` + `jobs::supervise_child(ctx.cancel_token(), ...)` and `host_command_with_env_and_directory_lifecycle`; core retains subscription validation, git argument/environment policy, workspace indexing and sync-result construction. This avoids a core→app dependency and reuses the platform gateway.
4. Cancellation must short-circuit, not become `CachedFallback`: current `sync_workspace` treats every fetch error as cache fallback when a workspace exists (`$C/community/taps/store.rs:103-120`). Distinguish cancelled from network/git failure and do no index/offline upsert/backfill after cancellation. Wrapping current `sync_many` in `run_job` is sufficient only for non-blocking/shutdown waiting, **not** the cancellation AC.

## 5. Containment design and tests

Use one `ensure_within_workspace(root, candidate)` for both prepare and import, and call it against every resolved tap workspace. Canonicalize root and candidate, require the candidate to be an existing regular `.json` file for prepare/import, and compare path **components** (`candidate.starts_with(root)` after canonicalization), never string prefixes, case folding, or Unicode-normalized names. This rejects `..`, absolute outside paths and symlinks escaping the root while accepting valid nested files. On Linux, case/NFC/NFD-distinct names are distinct; normalizing them would authorize the wrong file, so exact post-canonicalization components are the correct behavior. Pass the validated canonical candidate to preview/import rather than the unchecked original string.

This deliberately closes the current prepare loophole: its comment permits arbitrary file-picker JSON and discards `_is_workspace_path` (`$T/commands/community.rs:169-177`). The YAN-835 containment AC takes precedence, so both prepare and import must reject an absolute path outside every known workspace.

Tests belong beside the service, using real temp directories (and Unix symlinks): reject lexical `..`; absolute outside; direct and intermediate symlinks escaping; sibling prefix (`root-evil`); case-only and NFC/NFD lookalikes that resolve outside or do not match; missing/non-file/non-JSON paths. Accept a nested valid JSON in a known tap. Exercise both prepare and import, including multiple taps where only one contains the file.
