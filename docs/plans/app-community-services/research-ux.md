# YAN-835 frontend / UX research

Paths below are relative to `src/crosshook-native/`. Source was read only; no tests, builds, browser sessions, or source edits were performed.

## Recommendation: keep the existing awaited IPC contract

Move ownership behind the adapters without changing command names, argument casing, response DTOs, error strings, or existing event semantics. `callCommand` forwards the native `invoke` promise without an envelope or normalization (`src/lib/ipc.ts:7-16`). In particular, `community_sync` must still resolve to `CommunityTapSyncResult[]`, not a job ID: the hook immediately iterates that array and then refreshes the index (`src/hooks/useCommunityProfiles.ts:255-276`). Running it as an asynchronous supervised service operation can make the backend nonblocking without changing frontend code.

Do **not** add a cancel button, polling protocol, progress event, or job-ID response as part of this extraction. There is no current sync cancel affordance and the issue asks for backend cancellability, not a new UX. Establish/test cancellation at the service/job boundary while retaining the pending IPC promise. If interactive cancellation is intended as an additional acceptance criterion, it requires an explicitly designed additive IPC/UI contract; do not imply the present UI can cancel a sync.

**Important correction to the proposed premise:** no generic job-cancel Tauri command or frontend job-management hook was found. The Rust API `JobRegistry::cancel(&JobId)` exists (`crates/crosshook-app/src/jobs/registry.rs:219-234`), but current adapter cancellation commands are operation-specific (`src-tauri/src/lib.rs:156,159,235`: `cancel_update`, `cancel_run_executable`, `protonup_cancel_install`). These cannot safely cancel community sync. There is therefore no existing generic “job cancel command” to wire up unchanged.

The existing `run_job` helper explicitly documents that its blocking closure cannot be interrupted and can finish in the background after cancellation (`crates/crosshook-app/src/services/mod.rs:69-80,91-112`). Merely wrapping synchronous git sync in that helper is insufficient evidence that git/process work stops. Backend implementation/tests must establish the intended cancellation semantics, particularly no later indexing/offline upsert presented as a successful cancelled sync. This does not require a frontend change.

### Route wiring is not synonymous with ProtonDB

- `src/components/pages/CommunityPage.tsx:8,19` renders Community Browse (`CommunityBrowser`).
- `src/components/pages/DiscoverPage.tsx:12` renders `TrainerDiscoveryPanel`.
- `src/components/pages/CompatibilityPage.tsx:34-46,101-108` creates its own `useCommunityProfiles` instance, maps manifests to trainer reports, and shows loading/error/empty inline. It does not call ProtonDB or automatically sync taps. The Proton tab is the runtime management panel (`:112-120`).
- ProtonDB guidance is in the **profile editor**, not the Compatibility route: `ProfileFormSections.tsx:70-113` wires lookup/suggestions/accept/dismiss for Steam/Proton launch methods and overwrites the edited profile with the accepted response (`:73-75`). Compatibility route smoke alone therefore does not exercise ProtonDB commands.

## Busy state, progress, cancellation

- Community sync progress is currently one local boolean, not per-tap progress. `setSyncing(true)` precedes IPC and `finally` clears it (`useCommunityProfiles.ts:255-276`). There are no job-event subscriptions or progress DTOs in this hook.
- `CommunityTapManagementSection.tsx:48-63` disables Refresh Index and Sync Taps, and changes the label to “Syncing...”; Add Tap and tap chip actions are disabled while loading/syncing (`:92-113`). URL/branch inputs remain editable. No cancel button or progress percentage is rendered.
- Catalog cards remain separate from sync busy state: `CommunityBrowser.tsx:273-295` passes loading/catalog loading and importing independently. Keep the existing index visible while a sync is pending or fails; do not blank it on job start/cancel.
- On a sync rejection/cancellation, current behavior will be a normal error banner and busy cleanup (`CommunityProfilesSection.tsx:106-115`); success-only refresh/result updates will not happen. Preserve a useful string error (not `[object Object]`). Do not report cancellation as an empty successful result or stale-success notification.
- A route unmount or ignored response is not backend cancellation. `useCommunityProfiles` has initial-load/subscription cleanup but no sync cancellation (`:398-460`). The request-ID guards in discovery/ProtonDB similarly only ignore obsolete responses.
- Lutris scanning uses “Scanning Lutris…” and disables its launch button (`CommunityProfilesSection.tsx:82-89`). In the import modal, Cancel closes the preview and is disabled while importing; it is **not** process/job cancellation (`LutrisImportModal.tsx:351-383`). Preserve that behavior.

## Errors and offline/stale data are existing contracts

No backend error-message substring/equality/regex dependencies were found in the scoped Community/Lutris/Discovery/ProtonDB callers. Most convert `Error.message` or `String(err)` and display it directly (`useCommunityProfiles.ts:271,291,370,389`; `useCommunityCatalog.ts:69`; `useExternalTrainerSearch.ts:75`; `useLutrisImport.ts:5-6,60-62,77`; `useProtonDbSuggestions.ts:51`; `TrainerDiscoveryPanel.tsx:113`). Preserve legacy strings at the Tauri adapter boundary; returning serialized `AppError` objects would regress display even without text parsing.

Exceptions worth retaining:

- Lookup failures log an error and become structured `state: 'unavailable'`, with no raw backend error shown (`useProtonDbLookup.ts:116-130`). A normal offline/cache result should remain a successful DTO rather than a rejected invoke where that is the current command behavior.
- Dismiss failure only `console.warn`s and keeps the optimistic removal (`useProtonDbSuggestions.ts:85-99`). Indexed-profile advisory failure is silently ignored (`useProfilesPageProton.ts:117-119`).
- Community import wizard handles structured launch-validation issues, not backend string matching (`CommunityImportWizardModal.tsx:357-362`; `components/community-import/utils.ts:85` onwards). Preserve that distinction from plain IPC errors.
- Community fallback banner depends on `from_cache` and `last_sync_at` in the last **successful** sync response; it lists cached taps and last successful timestamps (`CommunityBrowser.tsx:89-106,203-220`). Preserve `status: 'cloned' | 'updated' | 'cached_fallback'`, `from_cache`, and nullable/optional `last_sync_at` (`useCommunityProfiles.ts:57-66`). A rejected offline sync retains prior results but does not create a new cache banner.
- External results use structured `cached/cacheAgeSecs/isStale/offline`, not an “Unavailable” string. These select cache-age/outdated labels and “Online search unavailable. Showing local results only.” plus Retry (`ExternalResultsSection.tsx:54-85`; `types/discovery.ts:87-94`). Preserve that response contract while the service represents unavailability internally.
- ProtonDB stale guidance is preserved via `state === 'stale'` or `cache.is_stale`, plus `cache.from_cache` (`useProtonDbLookup.ts:151-165`). `ProtonDbLookupCard.tsx:177-214` already renders distinct loading/stale/unavailable/cache banners.
- Discovery local lists expose `CatalogPage.degraded` (`types/discovery.ts:55-61`) and show `DiscoveryDegradedBanner` (`CommunityProfilesSection.tsx:92-94`). Neither catalog DTO nor raw community index has a per-list stale timestamp. Avoid inventing a new stale schema/UI in this extraction; keep existing cache/offline indicators and flag any stricter stale-marker requirement as a product contract decision.

## Persistence / usability boundary

No frontend persistence or migration is needed. Tap edits remain TOML settings; community indexes/external/ProtonDB cache remain SQLite metadata; sync busy/progress/cancellation and last response state are runtime-only. Do not persist job IDs or local busy state. Preserve offline-readable local indexes and structured cached ProtonDB data; network failure must not erase the already displayed local catalog. Backend unavailability should cross the current string/DTO boundary without new response envelopes. Existing user-facing stale/cache markers above should remain unchanged.
